# 最適化の候補 (検討メモ)

位置づけ: いつか取り組む最適化の候補を、着手前に
整理した検討メモ (2026-11-08)。実装はまだしない。
着手の順番はユーザーの方針で、言語の基本的な拡張
(switch など残りの基本機能) が済んでから。

## 目的

最適化そのものが目的ではなく、目的は Ikesu 側の
実時間再生に置く。現状の物差しは、実機で 3.865 秒の
音源のデコードに 25.3 秒 (約 6.6 倍)。何倍縮んだかを
測れるから工夫に意味が出る、というのがユーザーの
考え方。

## 前提: 先に計測の物差しを作る

- デコーダ単体などのベンチを、virt での計時や
  生成命令数で測れる形にする
- 時間の内訳 (インタプリタのディスパッチが支配的か、
  デコーダの演算が支配的か) で効く最適化が変わる
- 最適化で生成コードは変わるので、セルフホストの
  固定点 digest が変わるのは前提。正しさは test.sh の
  実行テスト (プログラムの出力の一致) で担保する

## 現在の生成形 (2026-11-08 時点の事実)

- 変数はすべてメモリスロット。読むたび ld、書くたび sd
- 式の作業レジスタは t1 (今の値) と t2 だけ。
  t3〜t6 は未使用
- 二項演算で右辺が葉でないと、左の値をスタックへ
  退避・復帰する (sd/ld と sp 調整で 4 命令)
- 定数相手の演算も li で t2 に入れてから演算する
- if/while の条件は、比較結果の 0/1 を t1 に作って
  から beq t1, zero で分岐する

## 候補 (入りやすい順)

1. 命令列の後処理 (peephole): gen の命令リストは
   並行配列のデータなので、encode の前に 1 パス
   舐めるだけでできる。定数畳み込み (parse には
   eval_const の仕組みが既にある)、定数相手の
   即値命令化 (x + 5 → addi、x * 8 → slli)、
   無駄な move や store 直後の同スロット load の除去
2. 条件分岐の融合: 条件文脈では比較の 0/1 を作らず、
   blt/bge 等で直接分岐する。1 条件あたり 1〜2 命令
   減り、ループで効く
3. 式評価の改善: t3〜t6 を作業レジスタに広げ、
   評価順の工夫 (Sethi-Ullman 的) でスタック退避を
   減らす。浅い式木なら退避ゼロにできる
4. 局所変数のレジスタ割り付け: 本命で最大の仕事。
   設計文書が要る大きさ。段階案として
   「アドレスを取られないスカラ局所だけ、
   関数内だけ」から始める
5. ループまわり: ループ不変な計算 (a[i] のアドレス
   計算など) を外へ出す (LICM)、掛け算アドレスを
   漸増に変える強化削減
6. 関数まわり: 小さい関数のインライン展開
   (呼び出しの引数の並べ替えとプロローグの退避が
   消える)、末尾呼び出し
7. その他: 到達不能コードの除去、ジャンプ先への
   ジャンプの解消 (分岐緩和のパスに相乗りできる)

## 経路別の効き方 (見込み)

- ネイティブデコーダ (iwac で直接コンパイル):
  最適化がそのまま効く。内側ループは現在の生成形の
  弱点そのもので、候補 4 が本筋。実時間に届く
  可能性が一番高いのはこちら
- Wasm インタプリタ: インタプリタ自体 (iwac 製の C)
  は速くなるが、Wasm 1 命令をネイティブ数十命令で
  解釈する構造的な overhead は残る。6.6 倍が全部
  埋まるとは見ない。インタプリタ側の工夫
  (ディスパッチ方式など) との合わせ技になる見込み

## Ikesu 側からのメモ: computed goto（2026-11-18、連携）

- Ikesu（Wasm ランタイム）のチューニングの本命は
  computed goto による direct threading と見ている。
  インタプリタのディスパッチを速くする古典的手法で、
  前提として iwac に goto 自体が要る（現状は未対応。
  doc/missing-features.md の小物にも goto はある）
- 現行の ikesu.c（gcc ビルド）は goto を約40か所
  使っている。「Ikesu を IwaC で書く」話が具体化
  したら、その時点で言語機能として検討する。
  今は実装依頼ではなく、将来候補のメモ
- 計測用のカウンタ読み builtin の案は、OS 側に
  perf_read（syscall 33）が実機まで含めて入った
  ため優先度が下がった
- 確認済みの見解: v43 switch / v44 関数ポインタは
  既存の mp3dec / Ikesu を速くしない（重いのは
  ハフマン木たどりと FIR の積和などのデータ処理で、
  ディスパッチはフレームあたり数百回に過ぎない）。
  古典セット全部入りでも 3〜4 倍で、実時間に要る
  約 6.6 倍には届かない見込み

## Ikesu 側からの宿題: ネイティブデコーダの実測と候補 (2026-11-21、連携)

実時間再生に向けた入力情報。着手時期はこちら側の
判断でよい、という断りつきで届いた。

実測の前提:
- TEST (モノラル 3.865 秒) のデコード命令数は
  virt で約 8 億 (高速 DCT 後)。同じファイルの
  minimp3 は wasm で 1.17 億命令で、今のデコーダは
  実装の重さで 1 桁近く余分に食っている
- ステレオ実時間までは virt 見積もりであと約 1.4 倍
- 実機では命令数を 33% 削っても壁時間は ±0.4%
  しか動かなかった (メモリ側が支配的らしい。
  スタック往復の多いコードはここにも響いている
  可能性がある)
- デコーダ側のアルゴリズムの手はほぼ打ち尽くした
  (ハフマン多ビット表は約 1% どまり、高速 DCT は
  実施済み)。残りの大物はコード生成側、という
  切り分け

候補 (デコーダを書いた側から見えたもの):
1. 小さい関数のインライン化: 積和ヘルパー (mulp 等)
   が内側のループでサンプル単位に呼ばれ、呼び出し
   のたびに引数領域の用意がかかる
2. 32 ビット演算のネイティブ生成 (addw/subw/mulw
   等): 添字・インデックス計算が全部 64 ビットで、
   命令数とバイナリの両方に効く見込み
3. ループ内のアドレス計算の巻き上げ: 添字アクセス
   のたびに基底 + オフセットを計算し直している
4. ローカル変数のレジスタ保持: スタックへの
   出し入れの削減

優先順位づけの材料として、段ごとの実機内訳
(再量子化/IMDCT/合成のどこが大半か) は Ikesu 側で
まだ測れていない。測れたらまた連携が来る。
(→ 2026-11-23 に続報が届いた。下の続報を参照)

追記 (2026-11-22): 状況が変わった。OS 側の供給が
DMA 化され (KosabaOS の audio-dma)、nami の
モノラル MP3 が実機で実時間再生できるようになった
(under=0、ユーザーの耳でも「今までの中で一番いい」)。
デコーダ自体は元々デコード 2.0 秒/音 3.865 秒で
実時間より速く、ボトルネックは供給側だった。
よってこの候補群は「デコーダ起因で急ぐ」ものでは
なくなった。ステレオ実時間 (あと約 1.4 倍) を狙う
ときに効く材料として、そのまま残す。

続報 (2026-11-23、Ikesu 側の実機計測): 段ごとの
内訳が届いた。ST44 ステレオ 128k、デコード単体、
K210 の cycles:

- ゼロバンドスキップ前 (総 2.09e9 = 5.36 秒 /
  曲 4.86 秒): 前半 (ビット読み〜再量子化) 19% /
  段4 (IMDCT 等) 27% / 段5 (合成) 54%
- スキップ後 (総 1.84e9 = 4.73 秒、128k は
  デコード単体で実時間 0.973 倍): 前半 22% /
  段4 17% / 段5 61%
- 320k は投影で約 1.02 倍

段5 が全体の 6 割超で、中身は 1 ブロックあたり
行列演算 384 + 窓掛け 512 の積和が中心。基本
演算 1 個あたり約 90 cycles 相当で、これは
アルゴリズムの重さでなく生成コードの姿
(全演算 64bit + 演算ごとの正規化、値の
スタック往復、インライン化なし) の分。
同クラスのネイティブ級デコーダは 30〜40 MIPS
でステレオ実時間とされ、K210 (390MHz) には
アルゴリズム側で約 10 倍の余裕がある計算。

候補の順位づけ直し (内訳を受けたもの):
1. インライン化 (mulp は mp3dec.c 内に呼び出し
   32 箇所、ST44 で動的約 2000 万回)
2. 32 ビット演算のネイティブ生成
3. ループ内アドレス計算の巻き上げ (窓掛けの
   内側で毎タップ地址を組み直している)
4. ローカル変数のレジスタ保持

デコーダ側で効かなかったもの: ハフマン
多ビット表 (約 −1%)、窓掛け係数の対称性
(全表を実測したがペア畳みは存在しなかった)。
効いたのは「仕事そのものを消す」系だけ
(ゼロバンドスキップで段4 −43.9%)。

位置づけ: デコーダ側はビット不変の範囲では
実用上の床に来ていて、コンパイラ側は今の
ブロッカーではない。効いてくるのはその先
(ミキサーやエフェクトの余裕が欲しくなる
段階) で、そのときの本命は上記 1 と 2。
こちらの計画順 (peephole から) は崩さない、
という断りつきで届いた。

## 副次効果

- 生成命令数が減ると、iwac 自身の一括コンパイルの
  命令数 (44,619 / 上限 49,152) にも余裕が出る

## 進め方

候補 1 → 2 → 3 を小さい版として刻み、4 は独立した
版として設計から。一歩ごとにベンチで測る。

方針の確認 (2026-11-22、ユーザー): 急ぎではないが、
最適化も全部入れたい。おいおい計画に従って
順番に進める。

実施状況 (2026-11-23): 段1 の peephole を
v52 で実装した (設計と結果は doc/peephole.md)。
nami では命令数 15,651 → 15,485 (約1.1%減)、
ロード 3,263 → 2,802。段2 の分岐の融合も
v53 で実装した (設計と結果は
doc/branch-fusion.md)。nami では命令数
15,485 → 14,915 (約3.7%減)。段3 の式評価も
v55 で実装した (設計と結果は
doc/expr-eval.md)。nami では命令数
14,915 → 14,285 (約4.2%減)。段4 の
レジスタ割り付けも v56 で実装した
(設計と結果は doc/regalloc.md)。nami では
fp 相対のロード / ストアが 838 → 633
(約25%減)。命令数の総計は退避・復帰の
分だけ増えた (14,285 → 14,939) が、本命は
ループ内の動的なメモリ往復の削減で、
効き目は実機のサイクルで測る。段5 の
ループ最適化も v57 で実装した (設計と
結果は doc/loop-opt.md)。nami では命令数
14,939 → 14,900 で、imdct36 / imdct12 に
効いた。合成 (synth_granule) は割り付けが
s レジスタを使い切っていて入らなかった。
段6 のインライン化も v58 で実装した
(設計と結果は doc/inline.md)。mulp と
sat32 が入れ子で広がり、nami の静的命令数は
14,900 → 17,883 と増えた代わりに、mulp
呼び出し1回あたり約30命令が消える。
これで段1〜段6 は全部入り、到達点の mulp
インライン化まで届いた。動的な効き目は
virt の perf と実機で測る。

段5 の残件 (synth_granule にポインタが
入らない件) は v59 のレジスタートレード
オフで解消した (設計と結果は
doc/reg-tradeoff.md)。

到達点の指定 (2026-11-23、ユーザー): 一般論の
最適化で終わらせず、デコーダの特定メソッド
向けのチューニングを入れたい。第一の対象は
mulp (mp3dec の固定小数点の掛け算ヘルパ、
ST44 1曲で動的約2,000万回)。段6 の設計では
mulp の実体 (本体の形と32か所の呼び出し) を
見て、インライン化に加えて本体の形に合った
生成 (積とシフトの組み合わせ等) が要るかを
判断する。

## 最適化はどの層の仕事か (2026-11-23 の検討メモ)

ユーザーとの検討で整理した層の分担:

- 計画の最適化はほぼ全部コンパイラ (iwac) の仕事。
  置き場所は2か所: (1) gen そのものの改良
  (式評価の改善、レジスタ割り付け、ループ最適化、
  インライン化)、(2) gen の後・encode の前の
  命令列パス (peephole、分岐の融合、
  jump-to-jump 除去)。命令列という「機械語
  一歩手前」の表現があるので、パスを差し込む形に
  できる
- アセンブラ層 (encode と Asari) は最適化の
  置き場にしない。役目は命令列を 1:1 で書き写す
  ことで、この単純さが iwac の分かりやすさの
  源泉。古典的なツールチェーンではアセンブラも
  relaxation をするが、iwac では同等のことを
  命令列の段階でやる方が一貫する。Asari 側の
  融合は AArch64 には効いても本線 (RISC-V) には
  効かない
- リンカ (nori) には「全体の無駄を抜く」方向の
  余地がある: (1) 文字列の重複排除 (今は
  オブジェクトごとのプールをそのまま連結して
  いる。データ削減になり、nori 断片の str_pool
  の圧力にも効く)、(2) 未使用関数の除去
  (gc-sections 的。ただし .eo のコードは TU
  単位のひとかたまりで、落とすと後ろ全部の
  再配置の付け替えが要るので中規模の仕事)、
  (3) 配置順の工夫は K210 では誤差レベル。
  LTO は IR を持たないので対象外
- まとめ: 速くするのはコンパイラ、全体を
  小さくする助けがリンカ、アセンブラは忠実な
  書き写し役、という分担が iwac の形に合う

サイズについての見立て (同日): peephole・分岐
融合・レジスタ割り付けは生成コードを小さくする
方向、インライン化は大きくなる方向 (速さと
引き換え)、ループ最適化はだいたい中立。
最適化器そのもののコードが iwac に増えるので、
差し引きで勝てるかが勝負。生成コードが縮めば
nori 断片の code_pool の圧力は下がるが、
文字列 (エラー文) は最適化では減らない。

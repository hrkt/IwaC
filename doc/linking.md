# 分割コンパイルとリンカの計画

iwac を「ソース全体を一度に抱えて訳す」形から、
「ファイルごとに訳して、後でつなぐ」形へ育てる計画。
狙いはメモリ: 一括方式ではピークがプログラム全体で
決まるが、分割すれば**一番大きな断片**で決まる。
K210 のような小さいボード（データ領域 1MB）でも
セルフホストが見えるようになるのが最終的な景色。

一括コンパイルは捨てない。分割した結果が一括と
一致することが、各段の検証の物差しになる。

## 現状の数字（v29 時点の実測）

iwac が iwac 自身をコンパイルしたときの使用量:

| 表 | 使用 | 上限 | 割合 |
|---|---|---|---|
| 入力バッファ | 260,843 バイト | 262,144 | 99.5% |
| ノード | 11,783 | 16,384 | 72% |
| 命令 | 28,118 | 32,768 | 86% |
| 関数 | 109 | 128 | 85% |
| 変数 | 563 | 1,024 | 55% |
| 文字列プール | 7,065 バイト | 16,384 | 43% |

コンパイルされた iwac の静的データは約2.96MB。
KosabaOS（virt）のデータ領域は 4MB。

## 階段

### 段0: 容量の引き上げ（v30）

この先の仕事（オブジェクト出力など）でソースが
育つため、先に器を広げる。広げた分の静的データが
データ領域 4MB に収まることが条件:

- 入力・展開バッファ: 256KB → 384KB
- ノード: 16,384 → 20,480
- 命令: 32,768 → 40,960（ノードの2倍という
  容量の約束は維持する）
- 関数: 128 → 192
- 静的データは約3.79MB の見込み（実測で確認する）
- shirasu は従来どおり縮小プロファイルで別途作る
- 実施結果（2026-11-03、v30 として完了）: 静的
  データは実測 3,793,581 バイト（4MB に収まる）。
  固定点を再確認（digest len=126910
  sum=0000000000745079 hash=a49c5905e971559d）。
  shirasu の静的データは 271,320 バイト

### 段1: オブジェクト形式の設計（検討済み、2026-11-04）

設計は doc/object-format.md に別文書として書いた。
要点だけここに残す:

オブジェクトファイルの中身は4つ:

- コードのバイト列（機械語そのもの。穴以外は完成）
- データの実体（文字列と、初期値つきグローバルの中身）
- 名前表（このファイルが定義する名前／外に頼る名前）
- 穴のメモ（リロケーション: 後で埋める場所と種類）

穴は4種類（当初見込みの3種類＋1つ）:

- 関数呼び出し（jal の飛び先。同じファイルの関数も
  名前で解決する）
- あってもなくてもよい呼び出し（callopt。
  kosaba_flush 用。なければ nop になる）
- 住所作り（auipc + addi の組。名前つきと自分の
  文字列用で addr / addrstr の2レコード）
- データの中のポインタ（初期値に入った住所は
  iptr レコードとして持つ）

形式は iwac 専用の単純なものにする。世間の ELF
オブジェクトは使わない（読む側＝リンカも自作する
ので、必要最小限の自前形式が分かりやすい）。
今回はさらに、学習用に「読める」ことを優先して
テキスト形式（1行1レコード）とし、1行目に版番号
を持つ。後方互換は維持せず、形式を変えるときは
版番号を上げて作り直す方針。変数の extern は
持たない代わりに、C の仮定義（common）を採用する。

### 段2: iwac のオブジェクト出力（済み、v31・2026-11-04）

1ファイルを訳してオブジェクトを出すモードを足す。
生成層の仕事は「外の名前は最終アドレスではなく
穴として出す」こと。検証は、1ファイルのプログラムで
オブジェクト経由の結果が従来出力と一致すること。

実施メモ（branch `linking` で実装）:
`iwac --kosaba --object file.c` で1ファイルずつ
オブジェクト（拡張子 .iwo）を出す。検証は参照
リンカ（Python の mini-nori、test.sh に同梱）で
行い、単一ファイル・複数ファイル・kosaba_flush
ありの例で一括とバイト一致を確認した。実装で
分かったこと: (1) 関数本体の配置はオブジェクト順
ではなく登録順（doc/object-format.md に反映）、
(2) 宣言だけの関数に本体を作らない、(3) 数字の
住所も配置に依存するので穴（addabs）にした、
(4) kosaba_flush は「このファイルで宣言がある」
場合にだけ呼び出しの形を残す（無いファイルは
一括と一致させるため）。iwac 自身の断片は、
宣言の組み替えが要るものはまだ単独で訳せない
（段4 の仕事として残る）

### 段3: リンカ（nori）

オブジェクトを並べ、名前を引き当て、穴を埋めて、
ELF の表紙を付ける道具を作る。今は iwac の encode が
持っている ELF 書き出しは、最終形を知るリンカ側の
仕事になる。リンカは iwac の言語で書く（OS の上でも
動かすため）。アセンブラ役（命令列→機械語）は
iwac 内に残り、その役の名前は **Asari** とする
（命名は 2026-11-04 に決定。nori は海苔＝糊の
掛け言葉）。

### 段4: 分割セルフホスト

iwac の7断片 + kosaba_rt.c を別々に訳してリンクし、
一括版とバイト一致（固定点）を確認する。ここが
階段の山場。オブジェクトの設計が正しければ、
リンカの出力は一括版と一致するはず。

### 段5: OS 上での駆動（Misoni）

断片の数だけ iwac を起動し、最後にリンカを起動する
「手順を回す係」（ドライバ、make 的なもの）の形を
決める。名前は **Misoni**（味噌煮。2026-11-04 決定）。
材料は揃った（引数付き exec＝OS 側 2aa149b、
終了ステータス＝d28c7b8）。残る制約は exec が1段
までなこと（「シェル → ドライバ → iwac」の2段が
組めない。OS 側 doc/future-notes.md に論点あり）。
ドライバを Nish の機能にする案を含め、OS 側と
相談して決める。

### 段6（将来）: 小メモリでのセルフホスト

断片ごとのピークで K210（データ領域 1MB）に
載るかどうか。shirasu 級に絞った表で iwac の
断片が訳せるかが試金石になる。

## 決めていないこと

- リンカを別プログラムにするか、iwac のモード
  （`iwac --link` のような形）にするか。なお
  リンカの名前は **nori** に決定（2026-11-04。
  アセンブラ役は **Asari**、ドライバは
  **Misoni**。いずれも同日決定）
- オブジェクトファイルの名前・拡張子

## その先の挑戦: オブジェクトの ELF 化

段6 までの先の挑戦として、オブジェクト形式を
世間の ELF リロケータブル（ET_REL）に置き換える
「ELF 化」の席をここに用意しておく（2026-11-04 に
明記）。得られるものは、readelf / objdump で自分の
オブジェクトが読めることと、GNU ld でリンクして
nori と比べる物差し。面倒な所も見えている:
auipc/addi が HI20 / LO12 の別々のリロケーションに
割れて局所ラベルが要ること、callopt（kosaba_flush）
に相当する標準の仕組みがないこと。やるなら nori が
動いて「リンクとは何か」が手に馴染んでから。
形式の版番号で言えば version 2 の仕事になる。

# 分割コンパイルとリンカの計画

iwac を「ソース全体を一度に抱えて訳す」形から、
「ファイルごとに訳して、後でつなぐ」形へ育てる計画。
狙いはメモリ: 一括方式ではピークがプログラム全体で
決まるが、分割すれば**一番大きな断片**で決まる。
K210 のような小さいボード（データ領域 1MB）でも
セルフホストが見えるようになるのが最終的な景色。

一括コンパイルは捨てない。分割した結果が一括と
一致することが、各段の検証の物差しになる。

## 現状の数字（v29 時点の実測）

iwac が iwac 自身をコンパイルしたときの使用量:

| 表 | 使用 | 上限 | 割合 |
|---|---|---|---|
| 入力バッファ | 260,843 バイト | 262,144 | 99.5% |
| ノード | 11,783 | 16,384 | 72% |
| 命令 | 28,118 | 32,768 | 86% |
| 関数 | 109 | 128 | 85% |
| 変数 | 563 | 1,024 | 55% |
| 文字列プール | 7,065 バイト | 16,384 | 43% |

コンパイルされた iwac の静的データは約2.96MB。
KosabaOS（virt）のデータ領域は 4MB。

## 階段

### 段0: 容量の引き上げ（v30）

この先の仕事（オブジェクト出力など）でソースが
育つため、先に器を広げる。広げた分の静的データが
データ領域 4MB に収まることが条件:

- 入力・展開バッファ: 256KB → 384KB
- ノード: 16,384 → 20,480
- 命令: 32,768 → 40,960（ノードの2倍という
  容量の約束は維持する）
- 関数: 128 → 192
- 静的データは約3.79MB の見込み（実測で確認する）
- shirasu は従来どおり縮小プロファイルで別途作る
- 実施結果（2026-11-03、v30 として完了）: 静的
  データは実測 3,793,581 バイト（4MB に収まる）。
  固定点を再確認（digest len=126910
  sum=0000000000745079 hash=a49c5905e971559d）。
  shirasu の静的データは 271,320 バイト

### 段1: オブジェクト形式の設計（検討済み、2026-11-04）

設計は doc/object-format.md に別文書として書いた。
要点だけここに残す:

オブジェクトファイルの中身は4つ:

- コードのバイト列（機械語そのもの。穴以外は完成）
- データの実体（文字列と、初期値つきグローバルの中身）
- 名前表（このファイルが定義する名前／外に頼る名前）
- 穴のメモ（リロケーション: 後で埋める場所と種類）

穴は4種類（当初見込みの3種類＋1つ）:

- 関数呼び出し（jal の飛び先。同じファイルの関数も
  名前で解決する）
- あってもなくてもよい呼び出し（callopt。
  kosaba_flush 用。なければ nop になる）
- 住所作り（auipc + addi の組。名前つきと自分の
  文字列用で addr / addrstr の2レコード）
- データの中のポインタ（初期値に入った住所は
  iptr レコードとして持つ）

形式は iwac 専用の単純なものにする。世間の ELF
オブジェクトは使わない（読む側＝リンカも自作する
ので、必要最小限の自前形式が分かりやすい）。
今回はさらに、学習用に「読める」ことを優先して
テキスト形式（1行1レコード）とし、1行目に版番号
を持つ。後方互換は維持せず、形式を変えるときは
版番号を上げて作り直す方針。変数の extern は
持たない代わりに、C の仮定義（common）を採用する。

### 段2: iwac のオブジェクト出力（済み、v31・2026-11-04）

1ファイルを訳してオブジェクトを出すモードを足す。
生成層の仕事は「外の名前は最終アドレスではなく
穴として出す」こと。検証は、1ファイルのプログラムで
オブジェクト経由の結果が従来出力と一致すること。

実施メモ（branch `linking` で実装）:
`iwac --kosaba --object file.c` で1ファイルずつ
オブジェクト（拡張子 .iwo）を出す。検証は参照
リンカ（Python の mini-nori、test.sh に同梱）で
行い、単一ファイル・複数ファイル・kosaba_flush
ありの例で一括とバイト一致を確認した。実装で
分かったこと: (1) 関数本体の配置はオブジェクト順
ではなく登録順（doc/object-format.md に反映）、
(2) 宣言だけの関数に本体を作らない、(3) 数字の
住所も配置に依存するので穴（addabs）にした、
(4) kosaba_flush は「このファイルで宣言がある」
場合にだけ呼び出しの形を残す（無いファイルは
一括と一致させるため）。iwac 自身の断片は、
宣言の組み替えが要るものはまだ単独で訳せない
（段4 の仕事として残る）

### 段3: リンカ（nori）（済み、2026-11-04、v32）

オブジェクトを並べ、名前を引き当て、穴を埋めて、
ELF の表紙を付ける道具を作る。今は iwac の encode が
持っている ELF 書き出しは、最終形を知るリンカ側の
仕事になる。リンカは iwac の言語で書く（OS の上でも
動かすため）。アセンブラ役（命令列→機械語）は
iwac 内に残り、その役の名前は **Asari** とする
（命名は 2026-11-04 に決定。nori は海苔＝糊の
掛け言葉）。

実装は `nori/nori.c`（独立プログラムとして決定）。
ホストでは gcc、KosabaOS では iwac で訳す。段2の
参照実装（mini-nori）と同じく、一括コンパイルと
バイト一致する出力が物差し。未定義の関数・本定義の
二重・入口の二重・配列の大きさの食い違いはリンク
エラーになる。OS の上でも動かして確認した
（nori.elf が .iwo を読んで ELF を作り、実行できた）。

### 段4: 分割セルフホスト（済み、2026-11-04、v33）

iwac の7断片 + kosaba_rt.c を別々に訳してリンクし、
一括版とバイト一致（固定点）を確認する。ここが
階段の山場。オブジェクトの設計が正しければ、
リンカの出力は一括版と一致するはず。

達成した（バイト一致、OS 上の固定点も再確認）。
やったこと: (1) 言語の追随 — ファイル範囲の
再宣言（変数・配列・関数のプロトタイプ）を C の
仮定義と同じく合併するようにし、初期値の二重は
エラーにした、(2) 共有の宣言を `src/decls.c` に
集め、各断片は「decls.c + 断片」を1つの翻訳単位
としてオブジェクト化する（並びは一括での登録順に
揃え、kosaba_flush と rt の関数の宣言も末尾に
置いて配置順を一致させた）、(3) `--object` は
複数ファイル（連結して1単位）を受け付ける。

### 段5: OS 上での駆動（Misoni）（形を決定、ホスト側は済み、2026-11-04）

断片の数だけ iwac を起動し、最後にリンカを起動する
「手順を回す係」（ドライバ、make 的なもの）の形を
決める。名前は **Misoni**（味噌煮。2026-11-04 決定）。
材料は揃った（引数付き exec＝OS 側 2aa149b、
終了ステータス＝d28c7b8）。残る制約は exec が1段
までなこと（「シェル → ドライバ → iwac」の2段が
組めない。OS 側 doc/future-notes.md に論点あり）。

**実物で確かめた制約**: OS の trap.c は exec の
親の退避先（exec_parent）が1組だけで、exec された
プログラムがさらに exec を呼ぶと -1 が返る
（「exec は 1 段まで」）。つまり Misoni を普通の
ユーザープログラムにはできない。

**決めた形**: 駆動の手順は「マニフェスト」と
いうテキストファイルに書く（`out` で成果物、
`obj <名前.iwo> <file.c>...` で翻訳単位を並べ、
並びがリンク順）。この形式を、ホスト側ドライバと
将来の OS 側で共通にする。

- ホスト側（済み）: `misoni/misoni.sh` が
  マニフェストを読み、iwac と nori を順に起動
  する。iwac 自身のマニフェスト `misoni.txt` で
  作った iwac2.elf が一括とバイト一致すること
  を確認済み
- OS 側（済み、2026-11-06）: Nish 組み込み案は
  「密結合すぎる」とのユーザー判断で見送られ
  （2026-11-05）、代わりに OS 側で exec の
  多段化が実装された（2026-11-06）。これで
  Misoni 本体を普通のユーザープログラムとして
  実装した: `misoni/misoni.c`（iwac の言語）。
  マニフェスト形式はホスト側と共通のまま。
  残っていた「iwac の出力名が hello.elf 固定」の
  論点は、v34 の `--out <名前>` で解消した
  （iwac と nori の両方。大域変数 kosaba_out_name
  を rt が読む）。OS 上の通し確認（QEMU virt）:
  Nish から Misoni を起動し、8つのオブジェクト
  化とリンクで iwac2.elf ができ、その iwac2 で
  hello.c を訳して実行でき、digest 版では
  ホスト一括の digest と一致した。
  なお exec の引数文字列は「プログラム名から
  始まる行全体」を渡すのが OS の約束で、Misoni
  の駆動行もその形にしている

### 段6: 小メモリでのセルフホスト

断片ごとのピークで K210（データ領域 1MB）に
載るかどうか。絞った表で iwac の断片が訳せるか
が試金石になる。

#### 実測（2026-11-06、計測用の印入り iwac で測定）

翻訳単位 = decls.c + 断片、でのピーク:

| 断片 | ノード | 命令 | 文字列 |
|---|---|---|---|
| 02-parse | 6,085 | 12,251 | 5,521 B |
| 03-gen | 3,767 | 10,660 | 473 B |
| 04-encode | 1,842 | 3,778 | 263 B |
| 06-preproc | 1,175 | 2,093 | 604 B |
| その他 | 各 500 以下 | 各 700 以下 | 微量 |

ソースは最大で decls 8.5KB + 02-parse 105KB
≈ 113KB。一括時（ノード 12,637・命令 30,160）の
半分以下にピークが下がる。現行 shirasu
（ノード 2,048・入力 32KB）では 02-parse は
入口で溢れる。

#### 作戦

- **A: 断片プロファイル（本命）** — shirasu と
  同じ流儀で、定数を最大断片の実測＋余裕に
  合わせた第2の小容量プロファイルを作る。
  概算では静的データ ~750KB（GCC ビルド、
  int=4 バイト前提）で 1MB に届く計算
- **B: 断片をさらに刻む** — 突出している
  02-parse を2断片に割ってピークを下げる。
  A が足りない場合の次手
- **C: バッファの節約** — 原文 (src) と展開後
  (exp) の二重持ちを片方にするなど。A の補助
- **D: 工程分割（最後の手段）** — parse を別
  プロセスにして AST をファイルへ落とす。
  新しい中間形式の設計が要る
- **E: OS 側に頼る** — 1MB は OS の設計値。
  判断も実機検証も OS 側の仕事なので、
  IwaC 側の作戦ではなく相談事項として置く

段6 の達成の定義は「断片が 1MB 級のメモリで
訳せること」。リンクした iwac2 自体（データ
4MB）を K210 で走らせる話ではない。検証は
virt で行える（コンパイルは小容量プロファイル、
実行確認は通常領域でよい）。

#### 結果（2026-11-06、作戦A で達成）

- iwac の断片プロファイル `kosaba/build-frag.sh`
  （ノード 8192・命令 16384・再配置 2048・
  変数 512・文字列 8192B・入力/展開 128KB）:
  静的データ **945,648 バイト** < 1MB。
  全断片のオブジェクトが標準 iwac とバイト一致
- nori の断片プロファイル `nori/build-frag.sh`
  （名前 1024・再配置 4096・入力 160KB・
  コード 128KB×2）: 静的データ **756,834
  バイト** < 1MB。リンク結果が標準 nori と一致
- Misoni 本体は 21,982 バイトで元から小さい
- OS 上の確認（QEMU virt）: 断片プロファイルの
  iwac を載せて Misoni を回し、全断片の
  コンパイル＋リンク＋iwac2 の実行が通り、
  digest 版の自己コンパイル digest がホスト
  一括と一致した（固定点）。nori も断片版に
  差し替えた構成でも同様に通した

残るのは K210 実機の 1MB 領域そのものでの
実行確認だけ（実機セッションは OS 側/Hatoba の
管轄）。プロファイルの名前は当面 frag のまま
（shirasu のような正式な命名は保留）。

## その先の挑戦: オブジェクトの ELF 化

段6 までの先の挑戦として、オブジェクト形式を
世間の ELF リロケータブル（ET_REL）に置き換える
「ELF 化」の席をここに用意しておく（2026-11-04 に
明記）。得られるものは、readelf / objdump で自分の
オブジェクトが読めることと、GNU ld でリンクして
nori と比べる物差し。面倒な所も見えている:
auipc/addi が HI20 / LO12 の別々のリロケーションに
割れて局所ラベルが要ること、callopt（kosaba_flush）
に相当する標準の仕組みがないこと。やるなら nori が
動いて「リンクとは何か」が手に馴染んでから。
形式の版番号で言えば version 2 の仕事になる。

（2026-11-07: 対応付けの設計を doc/elf-object.md
に書き切った。callopt は弱い未定義シンボル +
未解決なら nop、という形で表す。GNU ld との
互換は目指さず、物差しは .iwo 経由との最終一致に
置き直した。実装はその次）

## その先の挑戦: Asari の別出し

もう1つの挑戦として、iwac の符号化層（encode。
内部の名前は Asari）を独立プログラムとして
切り出す席を用意しておく（2026-11-06 に明記）。
得られるものは2つ: ツールチェーンの古典的な形
（iwac → Asari → nori を Misoni が回す）の完成と、
C を通さず手書きアセンブリで KosabaOS の
プログラムが書ける入口。

進め方の想定（やると決めたら、でよい）:

- iwac 本体の出口は当面そのまま（内部の encode
  は残す）。Asari は「iwac の命令列をテキストに
  したもの」を入力とし、バイナリを出す独立
  プログラムとして作る
- 物差しはいつものバイト一致: Asari の出力が
  iwac 内部の encode と一致すること（nori に対する
  mini-nori と同じ構図）
- 本当の仕事は、命令列の中の iwac 内部の約束
  （分岐緩和の印、未解決呼び出しのマーカー、
  データ側の置き方）を「仕様」として切り出すこと

（2026-11-07: この仕様を doc/asari.md に書き
切った。受け渡しの形式、AArch64 の対訳表、
x86-64 の壁の場所まで。同日、v38 として実装も
完了: iwac --asari、Asari 本体、test.sh の
バイト一致の物差し、KosabaOS 上でのチェーン
確認まで。残るは Misoni への差し込みだけ）
- その形式を人が書く asm として育てるかどうかは、
  別出しが通ってから決める
- 段6（小メモリのセルフホスト）への効き目は
  薄い見込み（メモリの山は parse / gen の表で、
  encode は薄い）。やる理由は実需より
  ツールチェーンの完成と学びのほう

ELF 化と並ぶ「次の挑戦」の候補。どちらを先に
するかは、そのときの気分と実需で決める。

（2026-11-08: 両方の挑戦が終わり、v42 で
.iwo は引退した。Asari への ELF 書き手の
移植、Misoni への差し込みと --elf 切替、
nori の .iwo 読み口と mini-nori の撤去まで
完了。記録は doc/iwo-retirement.md）

# #include の設計 (v51)

位置づけ: ソースファイルから別のファイルを
取り込めるようにする設計メモ (2026-11-22、
ユーザーが「そろそろ #include では」と提起。
提案自体は 2026-11-19 から候補にあった)。
実装はまだしない。

動機: ヘッダに宣言と #define を置いて複数
ファイルで共有する、C の普通の開発の形が
今は取れない。分割コンパイル (decls.c 方式)
は iwac 自身のための仕組みで、利用者の
プログラムでは「連結するファイル全部に
同じ宣言を書く」か「1 ファイルに全部書く」
しかなかった。可変長引数 (doc/varargs.md)
の設計でも、stdarg.h が無いことが前提の
割り切りになった。

## 現行の入力と前処理 (前提の確認)

- 入力層 (src/05-input.c): コマンドラインの
  ファイルを全部 src_buf (475,136 バイト)
  へ連結して読み込む (load_files /
  append_file)。行連結 (\) の処理もここ
- 前処理 (src/06-preproc.c): src_buf 全体を
  行単位に走査し、#define の登録と展開、
  #ifdef / #ifndef / #else / #endif の枝
  選びを行う。指令の振り分けは kw_eq の
  連なりで、ここに #include の枝を足す

## 設計の芯: 行ループの再帰

- 行ループが `#include` の行に当たったら、
  指定されたファイルを読み込み、その内容に
  対して同じ行ループを再帰で回し、出力
  (前処理済みのテキスト) を元の流れへ
  差し込む
- #define の表は大域に 1 つなので、境界を
  越えて共有される: 取り込まれる側で定義
  したマクロは戻った後も有効で、逆も同じ。
  #ifndef の include guard がそのまま効く
- 入れ子の深さは最大 8。循環取り込みは
  guard があれば自然に止まり、無ければ
  深さの上限でエラーにする

## 解決の規則

- `#include "path"`: 取り込む側のファイル
  のあるディレクトリを先に探し、無ければ
  カレントディレクトリ
- `#include <path>`: カレントディレクトリ
  のみ (システムの置き場という概念は v1
  では作らない。-I オプションは将来の話)
- マクロで組み立てる取り込み (#include
  MACRO の形) は v1 では対象外

## 置き場と上限

- 取り込んだテキストは専用の静的な置き場
  (arena) に読む。合計 128KB まで (ホスト
  側の素のプロファイル)。断片プロファイル
  と shirasu は、いつもの書き換えで小さく
  する (例: shirasu は 16KB)
- KosabaOS 上で動く iwac でも、ファイル
  読みは append_file と同じ IO の口を使う
  ので、そのまま動く。パスの解決は OS 側の
  相対パスの扱いに従う

## 割り切り・既知の制限

- エラー表示の行番号は、取り込みをまたぐと
  ずれる (現行でも #define 展開で行は
  ずれるので、目安という位置づけは同じ)
- #pragma once は作らない。guard で書く
- iwac 自身のソースでは #include を使わない
  (test.sh の検査は従来どおり。言語機能と
  自分のソースの流儀は別、という v50 まで
  と同じ線)

## 検証の形 (test.sh)

- ヘッダに #define と関数宣言を置き、本体
  から取り込んで使う (値が一致すること)
- include guard で二重取り込みが防げる
- 入れ子 (a が b を取り込む)、#ifdef の
  中での取り込み
- 無いファイルはパスを示してエラー、guard
  無しの自己取り込みは深さ上限でエラー
- --kosaba 経路でも 2 ファイル構成の
  プログラムがコンパイルできること
- 既存の出力バイトが変わらないこと (回帰は
  digest で見る)

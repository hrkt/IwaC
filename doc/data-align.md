# v63 設計メモ: データ配置のアライメント (nori と一括 ELF)

状態: 実装済み (2026-11-25、branch `v63`)。発端は
synth チャットからの連携 (synth-bench の切り分け)。

実装の記録: 設計どおり nori (登録時の切り上げ、
layout の arr_base と締め、phdr と詰め物の
書き出し) と一括 (02-parse の一律化、
03-genstmt の str_padded と globals_base、
04-encode の filesz / memsz / phdr3 オフセット /
詰め物の書き出し) を直した。

範囲の確定 (実装時に判明): ベアメタルの
データ開始位置そのものは揃えない。data_base は
LOAD_BASE + コード長で、命令数が奇数だと
全体が 4 ずれるが、ベアメタルのバイナリは
初期のテストがバイト数で固定しており
(例: `65+1` は 20 バイト)、開始を切り上げると
大きさが変わってしまう。v63 の揃えはデータ
領域の中の相対配置 (プールの後ろ・配列間・
変数領域の基底) に効き、kosaba では基底が
ページ境界 (0x40200000) なので相対 = 絶対に
なる。ベアメタルは QEMU 専用で misaligned が
無症状なこともあり、開始位置は従来どおりに
残した。

検証は test.sh の v63 (ベアメタル実行時に
プール先頭からの相対位置で住所チェック +
kosaba 側の一括 / nori バイト一致と詰め物の
バイト列)。

## 問題

nori と iwac 一括 ELF のデータ配置は、どちらも
[文字列プール][配列領域][変数領域] をバイト詰め
する。配列の開始も、配列領域そのものの開始も、
境界に揃えない。

- nori (nori/nori.c): 配列の sym_off は累積
  バイト数 (登録時、507 行付近)。住所は
  DATA_BASE + str_total + sym_off (755 行付近)。
  変数領域は 8 バイト枠だが基底が
  str_total + arr_area なので一緒にずれる
- iwac 一括 (src/02-parse.c、03-genstmt.c、
  04-encode.c): グローバル配列の arr_off は
  累積バイト数。構造体の配列だけ v37 で要素の
  アラインメントに揃える例外がある。住所は
  data_base + str_used + arr_off、変数領域の
  基底は data_base + str_used + arr_used

実例 (synth-bench の C 版、2026-11-25): int32
配列が最終 ELF で 0x4020003d に置かれた
(文字列プールのバイト数がそのまま全体をずらす)。

## なぜ困るか

K210 は misaligned な ld/sd が M シムのトラップ
エミュレーションに落ちる (1 回ごとに割り込みと
復帰の往復)。virt (QEMU) では透過に動くので
気づきにくいが、実機ではワードアクセスする
データが境界ずれだと全アクセスが激重になる。

この制約への回避策として、nami と synth は
「ファイルスコープに char 配列だけを置き、
rd32/wr32 のバイト合成で読み書きする」作法を
採ってきた。synth-bench の実測 (同一アルゴ
リズム、チェックサム全版一致):

- IwaC + バイトパック: 約 2,100 ins/voice/frame
- gcc -O2 (構造体のワードアクセス): 約 230
- IwaC + int32 直接アクセス: 約 200

つまりバイトパックが約 10 倍で、IwaC のコード
生成そのものは gcc と同等。配置を揃えれば、
回避策なしで直接アクセスが実機でも使える。

## 提案: 一律 8 バイトに揃える

揃える単位は要素サイズではなく一律 8 バイト
にする。

- 変数領域 (8 バイト枠) の基底が自動的に揃う
- int64 配列・double 配列・構造体配列 (既存の
  stag_align は最大 8) と混ざっても規則が 1 つ
- コストは配列ごとに最大 7 バイト + 領域の
  開始の切り上げ最大 7 バイト

変更箇所は 2 経路とも「割り当て」「住所計算」
「像の書き出し」の 3 点で、形式 (.eo) は変えない。

### nori 側 (nori/nori.c)

1. 登録時: 配列を置く前に arr_area を 8 の倍数
   へ切り上げてから sym_off を割り当てる。
   全配列の後、arr_area 自体も 8 の倍数へ
   切り上げる (変数領域の基底のため)
2. 住所計算 (layout): 配列領域の基底を
   arr_base = 8 に切り上げた str_total とし、
   配列は DATA_BASE + arr_base + sym_off、
   変数は DATA_BASE + arr_base + arr_area +
   slot*8 とする。文字列自身の住所は従来どおり
3. 書き出し (write_elf): プログラムヘッダの
   filesz / memsz と第 2 セグメントの file
   offset を arr_base 基準に替え、文字列と
   初期値の像の間に切り上げぶんの 0 を埋める。
   初期値の像の書き手は sym_off 順に 0 埋め
   しながら進む既存の作りなので、開始位置を
   arr_base へずらすだけで隙間は自然に 0 になる

### iwac 一括側 (src/)

1. 02-parse.c: グローバル配列の arr_off
   割り当てで、置く前に arr_used を 8 の倍数へ
   切り上げる。構造体配列の v37 の例外処理は
   この一律化に吸収される (stag_align ≤ 8 の
   ため結果は同じか、より揃う)。最後に
   arr_used も 8 の倍数へ切り上げる
2. 03-genstmt.c: arr_addr と globals_base の
   計算で str_used の代わりに 8 切り上げした
   値を使う。stack_top は globals_base から
   導くので自動的に付いてくる
3. 04-encode.c: data_filesz / data_memsz を
   切り上げ込みにし、文字列と配列初期値の間に
   pad の 0 を出す。配列初期値の書き手は
   arr_off 順に 0 埋めする既存の作りなので、
   開始位置の変更だけで済む見込み

### .eo 形式との関係

オブジェクト内のオフセットは従来どおり
(オブジェクト内は iwac の arr_off、nori は
シンボル単位で全域配置を決め直す)。nori 側は
オブジェクト内の初期値バイト列を sym 単位で
取り込む (adopt_ainit) ので、iwac 側の
arr_off が変わっても取り込みは壊れない。
逆に iwac 側だけ・nori 側だけの修正だと、
直っていない経路に罠が残るので、同一版で
両方を直す。

## 影響と検証

- 全プログラムのデータ配置が変わる。計算結果
  (FNV やチェックサム) は変わらないはずで、
  test.sh の期待値がそのまま物差しになる
- データ量の増えは最大で 配列数×7 + 7 バイト。
  iwac 自身の断片 (配列が多い) と nori の
  断片プロファイルで 1MB 判定を実測確認する
- 分割セルフホストの固定点: 両段とも同じ
  nori / iwac を使うので決定的。test.sh 段6
  のオブジェクト一致と固定点で確認する
- 配置が揃ったことの直接確認: int32 配列を
  持つ小さいプログラムを両経路でビルドし、
  readelf で全配列シンボルが 8 の倍数に
  あることを見るテストを test.sh に足す
  (synth-bench の再現条件: 文字列プールの
  バイト数が奇数になるソースで)

## やらないこと

- 文字列プール内部の配置 (char の列なので
  境界は不要。文字列リテラルへのポインタは
  char* としてしか使われない)
- ローカル配列 (フレーム側は既に 8 の倍数に
  切り上げて詰めている)
- 構造体内部の詰め方 (stag_align の既存規則)
- synth 側の大きなローカル配列でプロローグの
  addi が壊れる件 (別問題として記録済み。
  本件とは混ぜない)

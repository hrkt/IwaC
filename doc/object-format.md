# オブジェクト形式の設計（IwaC 段1 の検討）

分割コンパイル（doc/linking.md）の段1として、
オブジェクトファイルの形式を設計する。実装は
段2（v31、iwac のオブジェクト出力）と段3
（v32、リンカ nori）で済み、この文書が仕様の
正本。段4（v33）で `--object` は複数ファイル
（連結して1つの翻訳単位。共有宣言 decls.c +
断片の形）も受けるようになった。この文書は
「仕様としてのドキュメント」だが、学習用でも
あるので、なぜそう決めたかを先に書く。

## 方針

- 分かりやすさを最優先にする。凝った最適化や
  世間の形式の再現はしない
- ただし「広げたいときに広げられる」形にはする。
  具体的には (1) 版番号を持ち、(2) 1行1レコードの
  形にして、新しいレコードは新バージョンで足せる
  ようにする
- 後方互換は維持しない。形式を変えたら版番号を
  上げ、古いオブジェクトはコンパイルし直す。
  オブジェクトはソースから作る中間生成物で、
  正本はソースだから、捨てるコストは小さい。
  互換の面倒を見るくらいなら作り直す、がこの
  プロジェクトの割り切り
- 対象は KosabaOS 用 ELF だけ。ベアメタル
  （生バイナリ）は一括コンパイルの担当のまま

## オブジェクトの中身（4つの材料）

いまの一括コンパイルが最後に持っているものを、
ファイルごとに切り分けたものがオブジェクトになる。

1. コードのバイト列: 機械語そのもの。ただし
   「このファイルだけでは決められない住所」の
   部分は穴（0 埋め）になっている
2. データの材料: このファイルの文字列リテラルの
   バイト列と、グローバル配列の大きさ、初期値の
   あるグローバルの初期値。ゼロだけの領域
   （未初期化グローバルと配列）はバイト列を
   持たず、大きさだけ申告する（v28 の BSS 化と
   同じ考え方）
3. 名前表: このファイルが定義する名前（関数・
   グローバル変数・グローバル配列）と、外に
   頼る名前
4. 穴のメモ（リロケーション）: 穴の場所・種類・
   どの名前（または自分の文字列）への参照か

一括コンパイルとの対応: gen が第2パスで実住所を
埋めていた場所が、そのまま穴になる。埋める役は
リンカへ移る。

## 穴の種類

実測（v30 時点のソース確認）で、決められない
住所は次の場所にだけ現れる。

### call: 関数呼び出し（jal）

呼び出し先は別ファイルかもしれないので、飛び先は
いつも名前でメモする。同じファイルの関数も例外に
しない（「名前は全部リンカが解決する」と決めると
頭の中が1本道になる）。入口の断片から main を
呼ぶのもこの種類。

埋め方: リンカが (相手の住所 − この jal の住所) を
jal の即値フィールドに書く。RISC-V の jal の届く
範囲は ±1MB。届かなければリンカがエラーにする
（届かせる工夫は将来の課題として明示する）。

### callopt: あってもなくてもよい呼び出し

kosaba_flush 専用。実行時ライブラリ（kosaba_rt）
をリンクするかは組み合わせ次第なので、入口の
断片は「あれば呼ぶ、なければ呼ばない」呼び出しを
必要とする。

埋め方: 名前が定義されていれば call と同じ。
されていなければ、その jal を nop
（addi x0, x0, 0）に置き換える。

### addr: 名前つきの住所作り（auipc + addi）

グローバル変数や配列の住所をレジスタに作る場所。
相手は別ファイルかもしれないし、同じファイルでも
最終的な配置はリンカが決めるので、やはり名前で
メモする。`&arr[3]` のような定数のずれは addend
（足し数）として一緒に持つ。

埋め方: 2命令組の住所を pc として、
diff = 相手の住所 + addend − pc、
hi = (diff + 0x800) >> 12、lo = diff − (hi << 12)
を auipc / addi の即値に書く（gen_load_addr と
まったく同じ分け方。v25 の大きな数のバグの
教訓はここでも生きる）。

### addrstr: 自分の文字列への住所作り

文字列リテラルは名前を持たず、そのファイルの
中だけで使われる。相手は「自分の文字列領域の
オフセット」で指す。埋め方は addr と同じで、
相手の住所 = 自分の文字列が置かれた住所 + ずれ。

### addabs: 絶対アドレスへの住所作り

数字で書かれた住所（`(char *)0x10000000` のような
MMIO）を直接読み書きする場所。値は絶対だが、
符号化は auipc + addi の PC 相対なので、コードの
配置がずれると組を作り直さなければならない。
つまり「絶対」でも穴になる。当初の設計では
「そのまま使う」としていたが、段2 の実装時に
配置依存であることに気づき、穴に改めた
（2026-11-04）。

### iptr: データの中のポインタ（初期値）

`char *p = "Hi";` や `int *q = &g;` のように、
グローバルの初期値として住所が入る場所。置き場所
はデータ側なので、コードの穴とは別に、初期値の
記録そのものとして持つ:

- `iptr <変数名> str <ずれ>`: 自分の文字列への
  ポインタ
- `iptr <変数名> sym <名前> <addend>`: 名前つき
  対象へのポインタ

### 穴にならないもの

- ファイル内のジャンプ（ループ・分岐・return の
  パッチ）: 関数の中で閉じるので gen が今まで
  通り自分で解決する。分岐緩和もファイル内で完結
- スタックの初期化（ベアメタル用）: オブジェクト
  の対象外（上の方針の通り）

## 名前表と「仮定義」

ファイルの外のグローバルを使うには、その
ファイルの中で宣言が必要になる。関数はプロト
タイプ（v24）で宣言できる。問題は変数で、iwac の
言語には extern がない。

そこで C の昔ながらの決まり「仮定義（tentative
definition、common とも言う）」を使う:

- 初期値のない宣言 `int g;` は「仮定義」。複数
  ファイルに現れてよい
- 初期値つきの定義は「本定義」。同じ名前の
  本定義は全体で1つだけ（2つあればリンクエラー）
- リンカは仮定義を1つの領域にまとめる。本定義が
  あればそれが実物になる
- 配列の仮宣言 `int a[10];` も同じ扱い。ただし
  大きさが食い違う宣言はリンクエラーにする

なお本物の C では、仮定義は1ファイルの中でも
まとめられる（`int x; int x;` は合法）。iwac の
一括コンパイルは今日、重複を parse でエラーにして
いるので、ここだけ分割の方が本物の C に近くなる。
iwac 自身のソースは宣言が1か所ずつしかないので、
一括と分割で結果は変わらない。

エラー検出の移動もここで決まる:

- 「定義のない関数が呼ばれている」は gen の
  チェックだったが、分割では「未定義の名前」と
  してリンカのチェックになる（オブジェクトを
  作る時点では、相手は別ファイルにいるのが正常）
- 名前の重複定義も、ファイル内は parse が、
  ファイル間はリンカが見張る

## 入口の断片と配置の規則

OS から起動される入口（main を呼び、flush を
呼び、exit する断片）は、main を定義したファイル
のオブジェクトが、自分のコードの先頭に持つ。
リンカへは「先頭の何バイトが入口の断片か」を
申告する（entry レコード）。

リンカの配置はこの順番に決める:

- コード: 入口の断片を一番前に置く。関数の本体は
  「登録順」に並べる（オブジェクトの並び順に、
  各ファイルの func / decl の現れる順をたどり、
  本体のある関数はその場所で定義側のオブジェクト
  から持ってくる）。一括では本体は登録順に並ぶ
  （宣言が先にあった関数は、宣言の位置に本体が
  来る）ので、分割でも同じ並びを再現するための
  規則。2026-11-04 の段2 実装で、オブジェクト順に
  並べる案では一括と一致しないことが分かり改めた
- データ: 全ファイルの文字列 → 全ファイルの
  配列 → 全ファイルのグローバルの順。ファイルの
  並びはオブジェクトの並び順どおり

これは一括コンパイルの並びと一致するように
選んだ。なので分割コンパイルの結果は、一括と
バイト一致させることができる（段4 の固定点
検証がそのまま使える）。オブジェクトの並び順 =
コンパイルしたファイルの並び順、が前提。

入口を持つオブジェクトは全体でちょうど1つ。
0個でも2個以上でもリンカのエラーにする。

## 形式そのもの（テキスト）

バイナリではなくテキストにする。理由は学習用
だから: オブジェクトをエディタで開いて読める、
diff が取れる、リンカのテスト用に手書きできる。
容量は2倍くらいになるが、中間生成物には許せる。

文法は1行1レコード、キーワードで始まる。
数値は10進数（初期値と addend は負もあり）。
コードと文字列のバイト列だけは16進数で書く
（直前の宣言でバイト数が分かっているので、
読み手は必要な分だけ16進の行を読む）。

```
iwacobj 1                  版番号つきの題字（必須・1行目）
target kosaba              対象（当面はこれだけ）
entry <長さ>               入口の断片の長さ（ある場合）
code <バイト数>            以後の16進行がコード
strings <バイト数>         以後の16進行が文字列の実体
arrays <バイト数>          配列領域の合計（BSS、実体なし）
func <名前> <コード内オフセット> <大きさ>  関数の定義
decl <名前>                            関数の宣言だけ
                                       (配置順の控え)
var <名前>                             グローバルの本定義
varc <名前>                            グローバルの仮定義
arr <名前> <配列領域内オフセット> <バイト数>  配列の申告
                                       (常に仮定義として
                                       リンク時に合併される)
init <名前> <値>                       整数の初期値
iptr <名前> str <ずれ>                  初期値=自分の文字列
iptr <名前> sym <名前> <addend>         初期値=名前へのポインタ
call <コード内オフセット> <名前>        穴: 呼び出し
callopt <コード内オフセット> <名前>     穴: 任意の呼び出し
addr <コード内オフセット> <名前> <addend>  穴: 住所作り
addrstr <コード内オフセット> <ずれ>     穴: 自分の文字列
addabs <コード内オフセット> <値>        穴: 絶対アドレス
undef <名前>               外に頼る名前（reloc からも
                           分かるが、読む人のために書く）
end                        終わり
```

定義（func / var / arr など）の現れる順番は
宣言順そのままにする。グローバルのスロット順と
配列の並びは、リンカがこの順番から決める。

### 小さい例

a.c:

```c
int g = 65;
char *msg = "Hi";
int getg() { return g; }
```

a のオブジェクト（コードの16進は概形）:

```
iwacobj 1
target kosaba
code 28
  （getg の機械語。g の住所作りの2命令が穴で 0）
strings 3
  486900
func getg 0
var g
var msg
init g 65
iptr msg str 0
addr 8 g 0
end
```

b.c:

```c
int getg();
int main() { return getg(); }
```

b のオブジェクト:

```
iwacobj 1
target kosaba
entry 32
code 64
  （入口の断片 + main の機械語）
func main 32
undef getg
call 8 main
callopt 12 kosaba_flush
call 40 getg
end
```

入口の断片の中の main への call も、main の中の
getg への call も、同じ「名前でメモする穴」として
並ぶ。リンカは a と b を上記の配置規則で並べ、
名前表を突き合わせて穴を埋め、最後に ELF の
ヘッダを付ける（いま encode が持っている ELF
書き出しは、段3 でリンカ側へ引っ越す）。

## やらないこと（割り切り）と、広げ方

v1 で入れないもの:

- ファイル局所の名前（static の本物）: 同じ名前が
  別ファイルにあっても、今はリンクエラー。一括の
  parse エラーと意味が揃っているので、物差しと
  しても一貫する
- ライブラリ・アーカイブ（.a のようなまとめ）
- デバッグ情報・行番号
- ベアメタル対象、弱い名前（callopt が唯一の例外）
- 後方互換の維持（上記の方針の通り）

後から欲しくなりそうなものと、その入れ方:

- ファイル局所の名前: def 行に印を1つ足す
  （例: `func <名前> <オフセット> local`）。
  レコード形式のまま広げられる
- アーカイブ: リンカが読む「目次ファイル」を
  別に作る話で、オブジェクト形式は無傷
- バイナリ形式: レコードの中身を保ったまま
  載せ替えるか、割り切って version 2 を新設する。
  読み書きするのはコンパイラとリンカだけで、
  影響範囲はそこに閉じる。バイナリ形式の本命は
  世間の ELF リロケータブル（ET_REL）で、
  「ELF 化」として doc/linking.md の末尾に
  挑戦の席を用意した（readelf で読める、GNU ld と
  比べられる、が得られるもの。HI20 / LO12 の
  分離と callopt の置き場が面倒な所）

判断の目安: テキスト形式の遅さ・大きさが実害に
なったら（例: セルフホストでオブジェクトの読み
書きが支配的になったら）バイナリ化を検討する。
それまでは「読める」ことを取る。

## まだ決めていないこと

- オブジェクトファイルの名前と拡張子
  （例: file.o / file.iwo など。段2 で決める）
- リンカを独立プログラムにするか iwac の
  方式（--link）にするか（段3 で決める。
  形式そのものには影響しない）。なお道具の
  名前は決まった（2026-11-04）: リンカは
  **nori**、アセンブラ役は **Asari**
- iwac 自身のソースの共有変数の扱い: 現在は
  01-head.c の static 宣言を連結に頼って共有
  している。分割コンパイル（段4）では、各断片が
  使う名前を宣言し直す必要がある（仮定義の
  仕組みで足りるか、宣言専用の断片が要るか）。
  これは形式ではなくソースの組み替えの話として
  段4 で扱う

# v45 設計メモ: 構造体の値セマンティクス

状態: 設計 (2026-11-16、branch `v45`)。
v37 の構造体 (doc/struct.md) で「v1 で切るもの」
とした値の受け渡しを足す。doc/missing-features.md
の実装予定の3番目。

## 動機

v37 の構造体は「置いてメンバを触る」だけで、
値として受け渡せない:

- 関数へ値で渡せない (ポインタで渡すしかない)
- 関数から値で返せない
- `a = b;` の丸ごと代入ができない
- 初期化子 `struct P p = { 1, 2 };` が書けない

実コード (デコーダの状態、ドライバの設定、
Z80 のレジスタセットのような塊) では、塊を
値として渡して「相手は自分の写しを触る」
書き方が普通に要る。ポインタ渡しだと
「書き換えが呼び出し側へ漏れる」意味の違いも
出る。値の意味を正しく入れるのがこの版の仕事。

## 入れる範囲

1. **丸ごと代入** `a = b;`: 同じタグ同士。
   左辺値の形は変数・配列の要素・メンバ
   (ネストした構造体メンバを含む)・ポインタ
   越し (`*p = *q`、`arr[i] = x`、
   `s.inner = t.inner`)
2. **値渡し** (引数): スカラの引数と混在できる。
   受け側は自分の枠に写しを持つ (書き換えは
   呼び出し側へ漏れない)
3. **値返し** (戻り値): 隠しポインタ (sret)
   方式。下の呼び出し規約を参照
4. **ローカルの初期化子** `struct P p = { ... };`:
   メンバの宣言順。ネストした構造体は `{ }` の
   入れ子、配列メンバは配列の初期化子の形、
   関数ポインタのメンバ (v44) は関数名か 0。
   足りない分は 0 で埋める (C どおり)
5. **関数ポインタ経由の呼び出し** (v44 の
   NODE_ICALL) でも同じ規約で構造体を
   受け渡しできる

## 切る範囲

- **ファイル範囲の構造体初期化子**: 運び口が
  無いため見送る。nori の初期値のモデルは
  「変数 = 1ワード」 (edata は変数ごとに
  先頭の8バイトだけを記録する) で、複数
  スロットにまたがる初期値をリンク経由で
  運べない。直接バイナリなら .data の
  イメージに書けるが、経路で意味が変わる
  形にはしない。ファイル範囲の構造体は
  従来どおり 0 始まりで、初期化子を書いたら
  エラーにする。運び口の拡張 (edata を
  ワード単位にする) は別の段で検討する
- **呼び出し結果への直接のメンバアクセス**
  `f(x).m`: 一度変数に入れてから触る
- **式の位置での構造体の値**: 三項演算子の
  枝、演算の相手など。値が現れるのは
  代入・引数・return・初期化の位置だけ
- **構造体の比較** (`==` など): 従来どおり不可
- 代入は文の位置だけ (式としての `a = b` の
  連鎖はスカラでも扱っていない現行どおり)

## 呼び出し規約 (核心)

現行の規約は「引数は右から評価して16バイト
刻みで積み、呼び出し側が a0〜 へ移して
スタックを戻してから飛ぶ。受け側はプロローグ
で a レジスタを引数の枠へ書く」。スカラだけの
呼び出しはこの形を **A 方式** として1バイトも
変えない (既存プログラムの出力が変わらない)。

構造体の引数を含むか、構造体を返す呼び出しは
**B 方式** にする:

- 引数スロットの数え方はスカラ = 1、
  構造体 = そのスロット数 (ceil(大きさ/8))。
  積み方は従来どおり右から評価して16バイト
  刻み。構造体の引数は「値の住所を作って、
  スロットを逆順に積む」専用の積み方にする
- 構造体を返す場合は、先頭に隠しスロットを
  1つ余分に積む: 戻り値の書き先の住所 (sret)
- 呼び出し側は **pop しない**。受け側の
  プロローグが、fp 相対 (入口の sp の上にある
  引数領域) から引数を自分の枠へ写す:
  スカラは ld → sd、構造体はスロット複写、
  sret は隠しの引数枠へ
- 呼び出し側は、戻ってから引数領域を解放する
  (sp += 総スロット数 × 16)
- 受け側の `return 式;` は、式の構造体を
  sret の先へ複写し、a0 には sret を入れて
  戻る。return 文なしで末尾に来た場合の
  中身は不定 (スカラの値なし return と同じ)

B 方式かどうかは署名だけで決まるので、定義側と
呼び出し側は署名表 (v44 の sig 表:
sig_ret_struct / sig_pstruct) を見て同じ判断を
する。宣言だけの関数も署名表で判断できる
(引数の変数の名簿は本体のある関数だけだが、
署名表は宣言の時点で埋まる)。

戻り値の行き先は呼び出しの現れ方で決める:

- `a = f(x);` の形: a の住所をそのまま sret に
  渡す (余分な複写なし)
- 引数として渡す形 `g(f(x))`: スタックに一時
  置き場 (構造体のスロット数 × 16) を取って
  sret にし、戻ってからその住所で値渡しの
  積み方をして解放する
- 文として捨てる形: 一時置き場を取る (中身は
  使わない)
- `return f(x);` (自関数も構造体を返す):
  自分の sret をそのまま渡す (複写なし)

引数の式の中の呼び出しは、その呼び出し自身の
方式で積み下ろしが完結するので、B 方式の
引数領域と干渉しない (現行の A 方式と同じ
理屈)。

## 複写の道具 (gen)

- `gen_lvalue_addr(node)`: 左辺値の住所を
  t2 に作る。変数は gen_var_addr、メンバ・
  要素は gen_elem_addr、ポインタ越し (DEREF)
  は相手の式の値そのもの
- スロット複写: 送り先の住所と送り元の住所から、
  スロット数だけ `ld t1, 0(src); sd t1, 0(dst);
  両方 +8` を展開する (ループにしない:
  カウンタ用のレジスタ契約を増やさないため。
  構造体は小さい前提で、大きさの上限は
  既存のスロット数の枠に乗る)
- 代入文は gen_stmt の NODE_ASSIGN で、両辺が
  構造体の値なら複写の経路に入る (通常の
  gen_expr では構造体の値は従来どおりエラー)

## 型の検査

- gen 側に `value_struct(node)` を用意する
  (v44 の value_fsig と同じ形で、式の構造体
  タグ + 1 を返す。変数・メンバ・要素・
  ポインタ越し・呼び出し (署名の戻り値) から
  辿る)
- 代入: 両辺のタグが両方とも分かり、食い違えば
  エラー。引数: 署名のタグと実引数のタグを
  照合し、構造体の位置にスカラを渡す (逆も)
  ことをエラーにする。return: 式のタグと
  自関数の戻り値のタグを照合する (現在の
  関数番号は gen 側に gen_in_func の 0/1
  しか無いので、gen_func が関数番号を
  控える小さな追加が要る)
- 検査は v44 と同じ方針: 両方分かる時だけ
  厳密にし、追跡できない形は素通りさせる

## parse の変更

- 値返し・値渡しのエラーを撤去する
  (02-parse.c の「構造体は値で返せません」
  「構造体は値で渡せません」)。引数の構造体は、
  構造体の変数と同じ define の経路で複数
  スロットの引数枠になる
- 代入文は従来どおり NODE_ASSIGN。構造体か
  どうかは gen がタグで判断する
- ローカル初期化子: 宣言の文の中で `{ }` を
  メンバ順に読み、**メンバごとの代入文
  (NODE_ELEM_STORE) の並びへ展開する**
  (新しいノードは増やさない。基底は宣言した
  変数、値は式。ネストは基底をメンバにした
  ELEM_STORE の入れ子、配列メンバは要素
  ごとの ELEM_STORE)。ファイル範囲で
  書いたらエラー
- スタック要否の解析 (expr_needs_stack /
  stmt_needs_stack): 構造体の代入文と
  B 方式の呼び出しは常にスタックを使うので、
  明示的に 1 を返す分岐を足す

## オブジェクト形式への影響

なし。代入・値渡し・値返しは全部コード生成の
話で、初期化子はローカル (代入への展開) だけ
なので、ELF・.ias・nori・Asari は無変更。
同一性の物差し (リンク == 一括、Asari == iwac)
はそのまま効く。

## 容量への影響 (実装時に実測)

呼び出し規約の分岐と複写の道具で数 KB の
見込み。v44 でソースは 422,612 バイト、
src_buf (458,752) までの余りは約 36KB ある。
静的データへの追加は小さい (現在の関数の
控え程度)。

## テスト方針

- 振る舞い: 代入の独立性 (片方を書き換えて
  他方が変わらない)、値渡しの独立性、戻り値、
  スカラとの混在引数、ネストした構造体、
  配列の要素間・ポインタ越しの代入、ICALL
  越しの受け渡し、初期化子 (ネスト・配列
  メンバ・不足分の 0 埋め)
- エラー: タグの違う代入・引数、構造体の
  位置へのスカラ (逆も)、ファイル範囲の
  初期化子、`f(x).m` の直接アクセス
- オブジェクト同一性: 構造体の受け渡しを含む
  プログラムで リンク == 一括、Asari == iwac
- セルフホストの digest 更新
- iwac 自身のソースでは v45 の形は使わない

## 実装の順序

1. 複写の道具 (gen_lvalue_addr とスロット
   複写) と丸ごと代入
2. 値渡し・値返し (parse のエラー撤去、
   B 方式のプロローグと呼び出し側、return)
3. ICALL の B 方式
4. ローカル初期化子 (代入文への展開)
5. test.sh に v45 の節を足して全体を通し、
   ドキュメント一式と digest を更新する

## 実装の記録 (2026-11-17)

設計どおりに段1 (複写と丸ごと代入) → 段2
(値渡し・値返し) → 段3 (ICALL) → 段4
(初期化子) の順で実装した。設計からの差分と、
途中で見つけた問題を残す。

- **引数エリアの「広げ直し」**: 構造体を返す
  呼び出しを引数として渡すとき (g(f(x)))、
  呼び先は sret の先へ 8 バイト刻みの詰めた
  イメージを書くが、引数エリアは 16 バイト
  刻み。受けた後にスロットを後ろから
  広げ直す処理が要った (設計では触れて
  いなかった)。
- **ICALL の評価順**: 間接呼び出しの行き先は
  引数を積み sret を積んだ「後」に評価して
  そのまま jalr する。行き先を先に退避すると
  引数エリアとずれる。
- **引数の枠数**: parse の引数登録が枠数 1
  固定で、多スロットの構造体引数ぶんフレームが
  足りず、保存した fp を上書きしていた。
  登録時に ceil(大きさ/8) 枠を数えるよう
  直した (v37 の前提の残り)。
- **波括弧の省略は不可**: 入れ子の構造体・
  配列メンバには必ず { } を書く (C の省略形は
  受けない)。メモの範囲は「入れ子の { } の
  形」だったので設計内。
- **初期化子の展開形**: 配列メンバの要素は
  「MEMBER を lhs に持つ MELEM」を基底に
  する (parse_postfix が作る形と一致させる)。
  素の構造体基底を渡すと gen_elem_addr の
  想定とずれて別の場所へ書いた。
- **v37 以来の潜在バグ (emit_scale)**: 配列の
  添字の倍率が要素サイズ 2/4/8 でしか効かず、
  16 バイトの構造体の配列で arr[1] が arr[0] の
  後半に重なって書けた。main (v44) でも再現
  することを対照実験で確かめてから直した
  (2 の冪は slli、それ以外は乗算。要素サイズ
  1/2/4/8 の出力は不変)。
- **容量の調整**: ソースが約455KBに
  育ち、セルフコンパイルの実測が命令 57,770 /
  ノード 24,504 / 関数 197 (断片 TU では 201)
  で、バッファ・関数・命令の上限を超え、
  ノードも残り 72 個まで迫った。増量
  (バッファ約 464KB、ノード 25,600、関数 224、
  命令 59,392) を、実測に余裕のある2つの表の
  縮小 (配列初期値プール 65,536 → 49,152 要素:
  最大の実例は Ikesu デコーダの 26,548 要素。
  再配置表 8,192 → 6,144: 最大の実例は
  03-gen 断片の 4,304 件) で相殺し、静的
  データは 4,100,206 バイト (v44 比 −56,800)。
  断片プロファイルは 03-gen の TU の命令数が
  20,244 に達したため命令表を 24,576 へ
  上げた。
- **decls.c の並び順**: 新しい関数のプロトタイプを
  decls.c の2か所で断片内の初出順と違う場所に
  置き、分割セルフホスト (v33 の同一性) が
  崩れた。初期化子の一群は parse_decl_stmt の
  前ではなく parse_funcptr_array_init の後、
  gen_lvalue_addr の一群は emit_patch_jump /
  apply_patches の前ではなく後が正しい位置
  だった。物差し (分割 == 一括) が止めて
  くれたので、初出順に直して一致を確認した。
- **nori 断片プロファイルの追随**: オブジェクトが
  育ち (03-gen.eo が 253,560 バイト、コード合計
  231,080、再配置の実測 6,105 件)、断片版 nori の
  容量も組み替えた。共有バッファ 255,872、
  コード置き場 233,472、再配置表 6,656 へ増やし、
  名前プール 8,192・名前表 768・登録順 1,792・
  配列初期値 1,024 へ縮めて相殺。静的データは
  1,044,726 バイトで 1MB の枠内に収まった
  (実測の内訳は nori/build-frag.sh の頭に記録)。

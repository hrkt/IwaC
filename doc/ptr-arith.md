# v49: ポインタ演算のスケール修正 (バグ修正)

## 発覚と症状 (2026-11-20)

Ikesu チャットからの連携で発覚し、IwaC 側の
scratch で再現確認した。`p + 1` が指す先の
大きさでスケールされず、常にアドレス + 1
バイトになる。int32* で `*p` が隣の要素の
バイト列を読み直した値 (0x1400000A) になる
形で顕在化した。切り分けの結果:

- 壊れている: int64* / int32* / int16* の
  `p + n`、`p - n`、`p++`、`p--`、`p += n`、
  `*(p + n)` (char* はスケール 1 が正解なので
  見かけ上動く)
- 正常: `p[i]` の添字アクセス (gen_elem_addr
  にはスケールがある)、配列の添字、char* の
  演算
- ついでに見つけた同根の問題 3 件:
  (a) 配列名 + 整数 (int32 配列など) は、
  type_node の etype が幅つきになるため
  ADD 後の emit_canon がアドレスを 32 ビット
  に切り詰めていた
  (b) `*(p + 1)` のような計算式アドレスの
  読みは、指す先の型が分かる場合でも常に
  1 バイト読み (LBU) だった (変数が相手の
  *p は v27 で幅対応済み)。Ikesu の再現
  ケース C (`*(p - 1)`) は値が小さい間は
  バイト読みでも偶然一致する
  (c) 幅つき型へのポインタを返す関数
  (int32* を返す等) は、呼び出し側の
  emit_canon が戻り値の住所を切り詰めて
  いた (int64* を返す場合は etype に幅の
  印が無いので無事)。検証用の smoke で
  発覚。呼び出し 3 経路 (直接・間接・
  B 方式) の canon を、署名の戻り値が
  ポインタでも構造体でもないときだけに
  限る
  (d) ポインタの配列 (int32* の配列等) は、
  要素の読み書き自体が幅で切れていた
  (int64* の配列だけ無事)。原因は 2 段:
  要素の型タグ (elem_etype) が基底の型を
  返していたことと、配列の宣言が arr_etype
  を 8 に畳んで要素の指す先の型を消して
  いたこと。要素の ++ の検証で発覚。
  直し: elem_etype に「要素がポインタなら
  8」、宣言の畳み込みをやめて基底の型を
  残す、deref_etype の相手の形を広げる
  (要素・メンバ・計算式)。これで
  *garr[0] や sizeof(*(garr[0])) も正しく
  なる

今まで表に出なかったのは、iwac 本体・nami・
Ikesu が添字アクセス中心で、ポインタ進行は
char* (文字列) しか使っていなかったため。

## 原因

生成 (gen) で要素の大きさ倍をするのは
gen_elem_addr (添字アクセスの住所作り)
だけで、二項演算の + / - と ++ / -- には
スケール処理が入っていなかった。

## 修正の方針

型の見積もりは v48 の sizeof が parse に
作った size_type_of (etype / plevel / struct
を sot_* に返す) を共有に格上げして使う
(decls.c に宣言を足し、02-parse.c の
static を外す)。sizeof と生成で型の規則が
ずれないことが構造で保証される。

新設する道具 (03-gen.c):

- ptr_elem_size(node): ノードの値がポインタ
  なら指す先の大きさ (バイト)、違えば 0。
  size_type_of の結果から: plevel 2 以上は
  8 (指す先はポインタ)、構造体なら
  stag_size、それ以外は etype の下位 4
  ビット。例外 2 件は先に特別扱いする:
  2 次元配列名と ROWADDR は行の歩幅
  (arr_cols × arr_esize)、配列メンバ
  (smem_count > 0) は member_elem_size
- emit_scale_r(reg, esize): 既存の
  emit_scale (t1 専用) をレジスタ一般に
  広げる。emit_scale はそのラッパとして残す

## 修正する場所

1. 二項演算 (gen_expr の ADD / SUB):
   - 左がポインタ・右が整数: t2 をスケール
     してから加減する
   - 左が整数・右がポインタ (ADD のみ):
     t1 をスケールする
   - ポインタ同士の SUB: 引いた後に要素の
     大きさで割る (2 の冪なら算術シフト、
     それ以外は定数との DIV)
   - ポインタが絡む ADD / SUB では
     emit_canon を出さない (アドレスの
     切り詰め防止。上記 (a) の修正)
   - 整数 - ポインタ、ポインタ + ポインタは
     従来どおり (無意味な式には介入しない)
2. 変数の ++ / -- (gen_expr): ポインタ変数
   はステップを指す先の大きさにする。
   即値に収まれば addi、収まらなければ
   定数を a0 に作って加減する (前置は t1、
   後置は a0 が受け先で、そのまま使える)
3. 要素の ++ / -- (EPRE / EPOST): 同じく
   要素がポインタならステップを広げる
4. 計算式アドレスの * 読み (gen_expr の
   DEREF): deref_etype が返す指す先の幅で
   読む (mem_load_op)。deref_etype は変数と
   配列名しか見ていなかったので、相手の形
   (添字・ポインタ添字・メンバ・計算式・
   呼び出し) を広げた。型が分からなければ
   従来どおり 1 バイト (絶対アドレス読みの
   約束はそのまま)
5. ポインタの配列の宣言 (02b-decl):
   arr_etype を 8 に畳むのをやめ、基底の
   型を残す (要素の大きさ arr_esize は 8
   のまま)。elem_etype は段数を見て要素の
   値の型タグを 8 に直す

複合代入 `p += n` は ASSIGN(ADD(VAR, 式))
の形なので 1 で自動的に直る。`p[i] += n`
のような要素への複合代入は今も文として
書けない (対象外)。

## 影響の確認

- スタック使用量は変わらない (スケールは
  レジスタ内演算だけ。a0 は二項演算の
  合成時点と ++ / -- の中で空いている)
- 既存プログラムへの影響: v48 のソース
  (全 10 断片) を旧コンパイラと新コンパイラ
  の両方でオブジェクト化して全てバイト
  一致を確認した (2026-11-20、scratch で
  実施)。iwac 自身のソースが使う範囲では
  生成は変わらない。v49 のソース同士の
  比較では、変更した 2 断片 (02b-decl /
  03-gen) のオブジェクトだけが変わる
  (新しい生成規則が新しいソース行に
  効いたためで、固定点は test.sh が確認
  する)
- Asari 経路は生成を共有するので自動で
  追随する

## テスト (test.sh に v49 節)

- 幅のある型 (int64/int32/int16/uint32) と
  char の p ± n、++ / --、+= / -=
- *(p ± n) の読み (256 以上の値で幅も確認)
- ポインタ同士の差 (要素数で返る)
- 構造体ポインタ (大きさ 24 など 2 の冪で
  ない歩幅 → 乗算経路)、二重ポインタ
- 配列名 + 整数、2 次元配列名 + 整数
- Ikesu の再現ケース B / C 相当
- オブジェクト経路 (リンク一致・Asari 一致)

## 結果と容量の追随 (2026-11-20)

実装は設計どおりで、同族の 4 件 (配列名 + 整数の
アドレス切り捨て、*(p + n) の 1 バイト読み、
ポインタ戻り値の切り捨て、ポインタ配列の要素幅) も
あわせて直した。固定点は len=306851
hash=36de60d0231c2edc。

副作用として 03-gen のオブジェクトが 295,112
バイトに育ち、nori 断片プロファイルの入力上限を
超えた。対策として 03-gen.c の尾部 (文と関数全体の
生成) を 03-genstmt.c へ分割した (連結順・登録順は
不変、分割後の iwac2 は分割前とバイト一致)。
断片プロファイルの組み替えの詳細は
doc/progress.md の v49 の項。

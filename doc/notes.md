# IwaC メモ（決めたこと）

- 2026-11-01: IwaC は KosabaOS のゴールに向けて C コンパイラの
  サブセットを作る別プロジェクト。作業は専用チャット「IwaC」で進め、
  OS 本体は隣の「KosabaOS」チャットで進める。
- 範囲は欲張らない。フルプリプロセッサ等は対象外。
  ただし、行内の特定文字列の置き換え程度の単純な
  `#define` は「本当はそのうちやりたい」ものとして、
  時期未定で計画に置く（2026-11-01）。
- リポジトリ管理は KosabaOS と同じ:
  - リポジトリに入れるのは、自分で書いたものだけ
  - 利用するツールは手元ディスクに保管するが、リポジトリ管理対象外
  - 他の人が書いたものも、リポジトリに丸ごと入れない
  - ドキュメントはリポジトリ内の `doc/` に残す
    （予定・できていること・メモ。環境の作り方もメモとしてここ）
- コマンド名は小文字で `iwac`。
- 内部構成は3層に分けて分かりやすく保つ（ユーザーの希望、
  2026-11-01）: 構文解析して AST にする部分／アセンブラ的に
  機械語一歩手前の命令列にする部分／バイナリに書く部分。
  アセンブラを無くして直接バイナリを出す方針自体は
  「期待以上」としてユーザーが承認。
- 最初のマイルストーンは「一番小さいバイナリを出力して実行する」。
  実行環境は Linux ユーザーモードではなくベアメタル
  （QEMU virt、結果は UART で確認する）。
- iwac 自身のソースでもプリプロセッサは使わない
  (`#include` / `#define` なし。ユーザーの指摘、2026-11-01)。
  必要な外部関数は宣言だけ自分で書く（現在は `write` のみ）。
- ビルドは最初はホストの gcc で行う（ユーザーが gcc を選択）。
  コードは GCC 拡張に頼らない書き方を保ち、将来 clang でも
  セルフホストでも困らない形に寄せる。
  いつかはセルフホストしたいので、iwac 自身のソースも
  「iwac が将来扱える範囲」に寄せて書く意識を持つ
  （例: 数字の読み取りにライブラリ変換を使わず手で書く）。

- アーキテクチャ決定（2026-11-03）: この日の決定3件を
  理由と帰結つきで記録する。

  1. ELF のゼロ領域はファイルに書かない（BSS 化、v28）。
     担当は iwac の書き出し側。
     - 状況: iwac の ELF は約3MB で 99.8% がゼロだった。
       OS のローダはもともと filesz から memsz までを
       ゼロ埋めする仕様
     - 決定: 「OS と iwac のどっちの仕事か」は、既存の
       ローダの約束に合わせる書き手側（iwac）が担う。
       OS は変更しない。PT_LOAD 3本で、ゼロは申告
       だけにする
     - 帰結: iwac2.elf は 126,893 バイトに。メモリ上の
       大きさは不変（ファイルの節約とメモリの節約は
       別の話）

  2. 入口・出口の約束は OS に合わせる（v29。OS 側
     2aa149b / d28c7b8）。
     - 状況: OS に argv を渡す仕組みが無く、iwac は
       決め打ち argv を自前で組み立てていた。終了時に
       成否を伝える手段も無かった
     - 決定: OS が「入口で a0 = argc、a1 = argv
       （文字列と配列はスタック末尾）」「exit の a0 =
       終了ステータス」を約束し、iwac は全面移行する。
       決め打ち argv と静的領域は廃止、crt も統一。
       置き場所の代替案（データ領域の argv 置き場に
       OS が書く）は採らない（従来プログラムの領域に
       触らない方を OS 側が選んだ）
     - 帰結: 起動は `run iwac.elf --kosaba hello.c`。
       v29 以降の iwac は OS 2aa149b 以降が前提に
       なった（逆向きの互換は OS が維持）。ドライバが
       前の段の成否を見られるようになった

  3. 分割コンパイル + リンカは将来の選択肢（未決定）。
     - 動機: 現行は全ソースを一度に抱える（入力上限
       約256KB、静的データ約2.96MB）。ファイル別に
       訳してリンカでつなげば、ピークメモリは最大の
       断片で決まり、K210 級でもセルフホストが見える
     - 役割の絵: アセンブラ役（encode）は iwac 内に
       残る。外に出るのはリンカ（配置・名前解決・
       穴埋め・ELF ヘッダ）と、手順を回すドライバ
       （make 的なもの）。リンカを別プログラムにするか
       iwac のモードにするかは未定
     - 前提の整備状況: 引数付き exec と終了ステータス
       （決定2）が揃い、ドライバを書く土台はできた
     - 残る制約: exec が1段のため「シェル → ドライバ
       → iwac」の2段が組めない。多段化は K210 の
       SRAM 配置で余地なし（OS 側 doc/future-notes.md）。
       ドライバを Nish の機能にする案が向こうにある
     - 命名: 道具は魚・海の言葉で揃える（KosabaOS /
       IwaC / shirasu / Nish / Hatoba）。Ikesu（生簀）は
       Wasm ランタイム用に決まっている名前で、リンカの
       名前ではない。make 的なものの名前は未定
       （seri = 競りを提案中）
     - 命名の続き（2026-11-04、ユーザー決定）:
       アセンブラ役は **Asari**（アサリ）、リンカは
       **nori**（海苔＝糊の掛け言葉。くっつける役に
       ぴったり）。Asari は当面 iwac の中の encode
       層の呼び名で、将来独立させるならその名前で
       出す。ドライバ（make 的なもの）は **Misoni**
       （味噌煮。サバの味噌煮で、KosabaOS を「調理
       する」役。2026-11-04 決定。seri 案は不採用）
     - 共通ライブラリの命名（2026-11-06、ユーザー
       決定）: **libdashi**（出汁）。「Libc とまでは
       言わない小さい共通関数（文字列操作など）」の
       束の名前。出汁＝料理の土台、という意味と、
       「lib da C（C の lib だ）」の言葉遊びの
       二重掛け。形の想定は、宣言＋.iwo を nori で
       つなぐ「オブジェクトの束」。入出力に触る
       ものは rt 側、純粋な関数は libdashi 側、
       という線引き。iwac 本体は対象外

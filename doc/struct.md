# 構造体の設計（v37 の設計、2026-11-07）

iwac に構造体を入れるための設計。レイアウトは
**C 互換**にする（2026-11-07 にユーザーが決定）。
この文書は「仕様としてのドキュメント」。

## 目的と位置づけ

MP3 デコーダのような「C で書かれたもの」を
移植する土台。v35（幅のある整数型）と v36
（typedef）の次の一歩で、依存順は
v35 → typedef → 構造体。

iwac の設計方針は長らく「構造体は入れない」
だった（iwac 自身のソースに不要なため）。
本設計はその方針変更であり、入れる範囲は
移植の実需に絞る。

## 文法として受けるもの

ファイルの範囲（トップレベル）でだけ定義する:

```c
struct Point { int32 x; int32 y; };
struct Flags { char kind; uint32 mask; char name[8]; };
struct Node  { int32 value; struct Node *next; };
```

- メンバの型は、組み込みの型・幅つきの型・
  typedef 名・`struct タグ` のいずれか。
  ポインタ（`*`）と配列（`[数]`）を付けられる
- 自分のタグへのポインタメンバは受け付ける
  （タグをメンバ解析の前に登録するため。
  リンクリストの形）
- 値メンバとして入れる構造体は、定義済みの
  ものだけ（不完全な構造体の値メンバは不可）
- 変数の宣言は型の位置に `struct タグ` と
  書く。`typedef struct Point Point;` の形で
  typedef 名にもできる（v36 の仕組みに乗る）
- 同じタグの再定義は、メンバ構成が完全に
  同じなら受ける（typedef の C11 ルールと
  同じ考え方。分割コンパイルで共有ファイルが
  一括時に重なるため）。違う構成はエラー

変数とアクセス:

```c
struct Point p;              /* グローバル / ローカル */
struct Point pts[16];        /* 構造体の配列 */
p.x = 3;                     /* . でメンバ読み書き */
struct Point *q = &p;
q->y = 4;                    /* -> でポインタ越し */
int32 d = p.x + q->y;
pts[3].x = 1;                /* 配列要素のメンバ */
char c = flags.name[2];      /* 配列メンバの要素 */
sizeof(struct Point)         /* 8（下のレイアウト） */
```

- 引数と戻り値はポインタだけ（`struct Point *`）。
  値渡しはしない
- `sizeof ( 型 )` を定数として受ける（式への
  sizeof は受けない）

## レイアウト（C 互換）

メンバのアラインメントは、その型の自然な
アラインメント（ただし上限 8）:

| 型 | 大きさ | アラインメント |
|---|---|---|
| char | 1 | 1 |
| int16 / uint16 | 2 | 2 |
| int32 / uint32 | 4 | 4 |
| int64 / uint64、従来の型（int / long 等）、ポインタ | 8 | 8 |
| 配列 | 要素の大きさ × 個数 | 要素と同じ |
| 構造体 | 下の規則 | メンバの最大 |

- メンバは宣言順に置き、各メンバのオフセットは
  そのアラインメントの倍数まで切り上げる
  （間はパディング）
- 構造体のアラインメントはメンバの最大値。
  構造体の大きさは、末尾をアラインメントの
  倍数まで切り上げる（末尾パディング。
  配列にしたときの歩幅のため）
- 例: `struct Flags { char kind; uint32 mask;
  char name[8]; }` は kind=0、mask=4、name=8、
  大きさ 16、アラインメント 4

iwac の型の語彙の範囲では、これは gcc の
RISC-V LP64 のレイアウトと一致する
（16 バイト級のアラインメントを持つ型が
無いため）。

## 置き場所

変数の置き場所は既存の仕組みの拡張で済ませる:

- 構造体の変数は 8 バイト枠（スロット）を
  `ceil(大きさ / 8)` 個使う。var_slot の指す
  先頭スロットが基底で、メンバのオフセットは
  バイト単位で足す。基底は常に 8 バイト境界に
  あるため、C のレイアウトの前提（基底の
  アラインメント）と矛盾しない
- グローバルもローカル（フレーム）も同じ
- 構造体の配列は既存の配列の仕組み（arr）に
  載せ、要素の大きさ＝構造体の大きさとする
- 生成の歩幅計算（emit_scale）は 1/2/4/8 以外
  の要素サイズに「定数の掛け算」で対応する
  （構造体の大きさは任意の値になるため）

オブジェクト形式への影響: `var` / `varc`
レコードにスロット数を足す（`var <名前>
<スロット数>`）。形式に互換義務は無い前提で、
nori と test.sh 内の参照リンカ（mini_nori）を
同時に直す。

## 型の表し方

- 構造体の名簿（タグ表）を新設する: タグ名、
  大きさ、アラインメント、メンバの並び
- メンバの記録は「名前・オフセット・etype・
  ポインタ段数・構造体番号（-1 = 構造体でない）・
  配列の個数（0 = 配列でない）」の組
- parse_type の結果に構造体番号の受け渡しを
  足す（parse_type_struct、v35 の etype と
  同じ流儀の並行チャネル）。typedef の表にも
  構造体番号を持たせ、`struct タグ` への
  typedef をそのまま運べるようにする
- 変数・配列の名簿にも構造体番号を並行に持つ
  （var_struct / arr_struct）

## アクセスの生成

新しいノード NODE_MEMBER を足す。意味は
「基底の住所＋メンバのオフセット」:

- `.` の基底は designator（変数・配列要素・
  メンバの連鎖）で、その住所を再帰的に計算する
- `->` の基底は式（ポインタ値）で、値＋
  オフセットが住所になる
- 住所が決まれば、読みはメンバの etype での
  load（幅つきは v35 の幅 load と正規形）、
  書きは NODE_STORE の住所側にこのノードを
  置く形で既存の仕組みに合流する
- メンバが配列なら住所そのものが値（decay）、
  メンバが構造体なら次の `.` の基底になる
- `&`（住所演算子）も同じ住所計算を使う

式の型付け（type_node）では、NODE_MEMBER の
etype はメンバの etype になる。

## v1 で切るもの

- 構造体の値渡し（引数・戻り値）と構造体
  そのものの代入（`a = b;`）→ エラーにする
- 初期化リスト（`struct P p = {1, 2};`、
  グローバルの初期値も含む）→ 構造体の
  グローバルは 0 始まりだけ
- ビットフィールド、共用体（union）、
  無名構造体、定義と宣言を一緒に書く形
  （`struct P { ... } p;`）
- `typedef struct { ... } 名前;`（無名の
  typedef）→ タグを付けて2段階で書く
- `sizeof` の式への適用、宣言子つきの
  `sizeof(int[4])`
- 関数ポインタのメンバ（iwac に
  関数ポインタ自体が無い）

## 実装の記録（2026-11-07、v37 として実装）

- ノードは NODE_MEMBER（基底＋メンバ番号＋
  . / -> の区別）と NODE_MELEM（配列メンバの
  要素）の2つ。生成は gen_elem_addr の仲間に
  入り、読み書き・++ / -- は既存の要素の
  仕組み（ELEM_STORE / EPOST）に合流する
- オブジェクト形式は var / varc に枠数を
  足した（`var <名前> <枠数>`）。nori と
  test.sh の参照リンカ（mini_nori）も追随
- 名簿の上限: タグ32個、メンバ合計160個。
  iwac の標準プロファイルは静的データが
  4MB のデータ領域にあと約17KBしか余裕が
  無く、構造体番号の表は char に +1 符号化
  （0 = 構造体でない）で詰めた。将来データ
  予算が増えたら上限も上げられる
- 配列メンバの要素の歩幅は、2の冪はシフト、
  それ以外は定数の掛け算（行アドレスの
  生成と同じ作り）
- 副産物: 02-parse.c が大きくなり、宣言
  まわり（文の並び・typedef・構造体定義・
  宣言文）を新断片 src/02b-decl.c に分けた
  （断片プロファイルのソース容量対策。
  doc/progress.md の v37 の項）

## 検証の物差し

- レイアウト: パディングの入る形（char の後の
  uint32 等）で、メンバの読み書きが隣を
  壊さないこと。ホスト gcc の offsetof / sizeof
  と同じ値になること（同じソースを gcc で
  訳した確認プログラムと突き合わせる）
- 配列・ネスト・ポインタ越し・typedef 経由の
  各経路で読み書き
- test.sh の全件 PASS（バイト一致の固定点
  含む）。構造体を使わない既存ソースの生成
  コードは不変のはず

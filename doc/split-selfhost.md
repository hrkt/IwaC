# 分割ビルドをセルフホストの正にする計画

設計メモ（branch `split-selfhost`）。まだ実装しない。
承認後に段1から進める。

## 何をするか

固定点の定義（doc/selfhost.md「完了の定義」）の入力を、
現行の「kosaba_rt.c + iwac.c（一括コンパイル）」から
「分割ビルド」へ移す。分割ビルドとは、共有宣言を集めた
src/decls.c を各断片の前に置いて断片ごとにオブジェクト
（.eo）を作り、nori でリンクする形で、駆動は Misoni
（マニフェスト）が担う。iwac2 は分割で作り、iwac2 自身も
分割で自分を作って iwac3 とし、バイト一致で固定点とする。

## なぜか

- 上限の組み換えが版のたびに起きている。縛っているのは
  一括セルフコンパイルで、--stats の実測（2026-11-18）では
  命令 58,258 / 59,392、ノード 24,645 / 25,600、
  断片 TU の関数 204 / 224、変数 1,183 / 1,280。
  ソースが伸びるたびに上限へ当たり、その都度「計測用の
  ビルドを作って測り直す」仕事が発生する。
- 分割基準では縛りは「最大の断片 TU」と「一括入力の実
  プログラム（デコーダ）」になる。断片 TU の命令数は最大
  でも 03-gen の 20,244（v45 実測）で一括の約 1/3、
  ノードも TU 単位では一括より大幅に小さい。ソースの
  伸びが上限へ届くまでの距離が大きく開く。
- 概算の効果: ノード上限 25,600 → 約 12,288 で約 546KB、
  命令上限 59,392 → 24,576 で約 731KB、静的データ合計で
  1.2MB 以上の削減見込み（段3 で実測して確定させる）。
  標準プロファイル（4MB 枠）に余裕が戻り、断片プロ
  ファイルの 1MB 争いも楽になる。
- 実機（K210、データ領域 1MB）でのセルフホストは元々
  断片プロファイル＝分割ビルドが前提で、定義を移すと
  「物差し」と「実機の形」が揃う。

## 消えないもの（範囲の線引き）

- iwac の複数ファイル連結入力は言語機能として残る。
  ユーザープログラムの一括コンパイルは今まで通り。
  変わるのはセルフホストの「正」の定義だけ。
- src_buf / exp_buf はデコーダ（329,300 バイトの
  1ファイル入力）が縛るので、この計画では大きく
  下げない。

## 段立て

### 段1: nori の整合チェック

- 同じ名前のグローバル変数・配列が複数のオブジェクトに
  現れたとき、サイズ（変数はスロット数、配列は要素数と
  要素サイズ）が食い違ったらリンクエラーにする。
  ELF のシンボルサイズで判定できる。
- 目的は、decls.c の「次元のずれ」を捕まえる独立した
  物差しを分割側に用意すること。今は一括とのバイト比較
  がこの役割を果たしていて、定義を移すと消えるため、
  先に受け皿を作る。
- 並び順のずれは対象外。両世代が同じ decls.c を使う
  限り固定点は保たれる（自己無矛盾）ためで、危ないのは
  次元のずれ（書き込み範囲の食い違い＝メモリ破壊）だけ。
- 検証: 正常系は従来どおりバイト一致。decls.c の次元を
  わざとずらした入力で nori が止まること。

### 段2: 定義の移行

- doc/selfhost.md の「完了の定義」を分割ビルドへ
  書き換える。
- test.sh の物差しを組み替える。固定点の確認を
  「分割ビルドの iwac2 が分割ビルドで iwac3 を作り、
  バイト一致＋digest 一致」へ移す。現行の v33 節
  （分割 == 一括の比較）はこの段では残す。
- 移行直後の生成物は従来とバイト同一のはずで、digest
  が変わらないことを確認してから進む。変わっていたら
  移行ではなくバグとして扱う。

### 段3: 上限の TU 基準化

- --stats の実測（断片 TU ごとの最大値＋デコーダの
  一括値）に基づいて、ノード・命令・関数・変数などの
  上限を引き下げる。目安は、命令は最大 TU（03-gen の
  20,244）＋余裕、ノードは最大 TU＋余裕。関数は断片 TU
  の 204 が引き続き縛りで、224 のまま据え置きの可能性
  が高い。
- 静的データの削減量を実測して記録する。digest は
  この段で変わる（通常の変更として selfhost.md へ）。
- kosaba/build-frag.sh・build-shirasu.sh・
  nori/build-frag.sh の追随を確認する（断片・shirasu は
  元々小さいので、主に標準の上限を参照している箇所が
  ないかの確認）。
- 一括セルフコンパイルはこの段で上限を超えるように
  なる。test.sh の一括比較チェックはここで外すか、
  物差しを「デコーダの一括コンパイル」へ付け替える。
  付け替えが本命で、一括経路の回帰検出は実在の最大の
  一括入力であるデコーダが担う。

### 段4: 実機確認

- K210（データ領域 1MB、断片プロファイル）で分割
  セルフホストを通す。virt では段5・段6 で実証済みで、
  残るのは実機セッションのみ。
- 既知の注意点: 実機ではメモリより先にファイル置き場
  （SD）が律速になる可能性がある。中間オブジェクト
  （.eo 9個とマニフェスト）の置き場と往復の時間が論点。

## 判断ポイント（実装前に決めること）

1. 一括比較チェックの外し方: 段2 では残し、段3 で
   デコーダへ付け替える（この計画の案）。
2. decls.c の自動生成は今回の範囲外とする（将来候補。
   並び順の保守は手作業のまま）。
3. 段4 は実機セッションの都合に合わせ、段3 までで
   一旦区切ってよい。

## 完了の定義

- selfhost.md の固定点定義が分割ビルドになり、
  test.sh がその定義で全件 PASS する。
- nori の次元ずれチェックが入り、ずらした入力で
  止まることを確認済み。
- 上限が TU 基準になり、静的データの削減が実測で

## 追記（2026-11-18）: #include を先に入れる案について

検討の結果、この計画の前提にはしない。

- decls.c の並び順の縛りは、一括とのバイト一致という
  物差し由来で、#include を入れても消えない。段2 で
  定義を移せば自然に緩む。
- 次元のずれは、宣言を複製していることが原因で、
  #include でもヘッダ（宣言）と断片側（定義）の二重
  管理は残る。段1 の nori チェックは引き続き要る。
- #include 自体が版 1 つ分の仕事（入力層への組み込み、
  パス解決、ガード、再帰）で、自前ソースで使えるのは
  さらに次の版からになる。容量の痛みの解消が遅れる。
- #include が効くのは一般の複数ファイルプログラムと
  カーネル目標のほうで、独立した判断として扱う
  （カーネル側の棚卸しは、連結モデルへ組み替える
  結論になっている）。

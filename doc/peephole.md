# peephole 最適化の設計メモ (v52 候補)

状態: 設計メモ (2026-11-23)。最適化トラック
(doc/optimization.md の計画順) の段1。ユーザーの
合図で着手する。バージョンは v52 とする
(varargs は設計メモ済みの候補として残る)。

## 実測 (対象パターンの静的カウント)

nami_all.c (mp3dec + nami、現行 iwac の
--asari 出力、全 15,651 命令) を数えた:

- addi が 4,510 (29%): 内訳は sp 調整 1,951、
  mv 1,299、小さい即値 982、nop move 115、
  fp 相対 110、その他 53
- ロード 3,263 (20%)、ストア 1,998 (12%)。
  命令の 3 分の 1 がメモリ往復
- int32 の正規化ペア (slli 32 + srai 32) が
  765 組 = 1,530 命令 (約 10%)。発生源は
  add 350、addi 188、mul 80、sub 78 など

peephole で触れるもの (ウィンドウ内の
静的カウント):

- nop move (addi rd, rd, 0): 115
- store の直後の同じスロットへの load
  (同じレジスタ = load が死んでいる): 314
- 同上 (別レジスタ = 転送で mv にできる): 334
- load した値をそのまま同じスロットへ
  store-back: 24

## v1 の対象パターン

1. nop move の削除
2. dead reload の削除: sd/sw の後、同じ
   スロット (基底レジスタ + オフセット、
   幅も一致) への ld/lw が同じレジスタ宛で、
   間に書き換え・呼び出し・分岐ターゲットが
   無ければ load を消す
3. store forwarding: 同条件で別レジスタ宛
   なら load を mv (addi rd, src, 0) に置換
   (サイズは同じ、メモリ往復が減る)
4. store-back の削除: load した値を間に
   使わず同じスロットへ戻す store を消す

対象は整数の ld/lw/sd/sw のみ (FP は触らない)。

## やらないもの (他の段の仕事)

- 正規化ペア (slli/srai) の除去: add/sub/mul の
  後では正規形 (符号拡張された int32) が意味論上
  必要で、安全に消せるのは発生源のごく一部。
  ここは 32 ビット演算のネイティブ生成
  (addw 等、計画の後の段) の仕事
- sp 調整の統合と push/pop の形そのもの:
  段3 (式評価の改善) の仕事
- 分岐を跨ぐ書き換え、jump-to-jump、分岐の
  反転: 段2 (分岐の融合) の仕事

## 仕組み

置き場所: gen_all の末尾、呼び出し fixup の前。
gen は 2 パス生成なので、両パスで同じ処理が
走り、命令数の変化にデータ住所が追随する。

前提となる命令列の性質 (実装で確認済み):

- 分岐・ジャンプの asm_imm は絶対命令番号
  (飛び先の位置)。関数呼び出しだけは負の印
  (-(関数番号+1) 等) で、後に fixup される
- 命令番号を握る者は他に func_entry[]、
  dfaddr_site[] (関数住所の auipc の位置)、
  obj_flush_site、obj_prefix_insts

手順:

1. 飛び先の集合を集める (分岐・ジャンプの
   imm >= 0 と func_entry の全要素)
2. ウィンドウ走査: パターンは飛び先の命令、
   JAL/JALR/ECALL を跨がない
3. 削除しながら圧縮し、旧→新の対応表を作る
4. 付け替え: 分岐・ジャンプの imm、
   func_entry[]、dfaddr_site[]、
   obj_flush_site、obj_prefix_insts

最大のリスクは付け替え漏れ。付け替え対象を
上の列挙で閉じ、検証 (下記) で検出する。

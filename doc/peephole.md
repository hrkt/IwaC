## 実測 (対象パターンの静的カウント)

nami_all.c (mp3dec + nami、現行 iwac の
--asari 出力、全 15,651 命令) を数えた:

- addi が 4,510 (29%): 内訳は sp 調整 1,951、
  mv 1,299、小さい即値 982、nop move 115、
  fp 相対 110、その他 53
- ロード 3,263 (20%)、ストア 1,998 (12%)。
  命令の 3 分の 1 がメモリ往復
- int32 の正規化ペア (slli 32 + srai 32) が
  765 組 = 1,530 命令 (約 10%)。発生源は
  add 350、addi 188、mul 80、sub 78 など

peephole で触れるもの (ウィンドウ内の
静的カウント):

- nop move (addi rd, rd, 0): 115
- store の直後の同じスロットへの load
  (同じレジスタ = load が死んでいる): 314
- 同上 (別レジスタ = 転送で mv にできる): 334
- load した値をそのまま同じスロットへ
  store-back: 24

## v1 の対象パターン

1. nop move の削除
2. dead reload の削除: sd/sw の後、同じ
   スロット (基底レジスタ + オフセット、
   幅も一致) への ld/lw が同じレジスタ宛で、
   間に書き換え・呼び出し・分岐ターゲットが
   無ければ load を消す
3. store forwarding: 同条件で別レジスタ宛
   なら load を mv (addi rd, src, 0) に置換
   (サイズは同じ、メモリ往復が減る)
4. store-back の削除: load した値を間に
   使わず同じスロットへ戻す store を消す

対象は整数の ld/lw/sd/sw のみ (FP は触らない)。

## やらないもの (他の段の仕事)

- 正規化ペア (slli/srai) の除去: add/sub/mul の

  必要で、安全に消せるのは発生源のごく一部。
  ここは 32 ビット演算のネイティブ生成
  (addw 等、計画の後の段) の仕事
- sp 調整の統合と push/pop の形そのもの:

- 分岐を跨ぐ書き換え、jump-to-jump、分岐の
  反転: 段2 (分岐の融合) の仕事

## 仕組み

置き場所: gen_all の末尾、呼び出し fixup の前。
gen は 2 パス生成なので、両パスで同じ処理が
走り、命令数の変化にデータ住所が追随する。

前提となる命令列の性質 (実装で確認済み):

- 分岐・ジャンプの asm_imm は絶対命令番号
  (飛び先の位置)。関数呼び出しだけは負の印
  (-(関数番号+1) 等) で、後に fixup される
- 命令番号を握る者は他に func_entry[]、
  dfaddr_site[] (関数住所の auipc の位置)、
  obj_reloc_site[] / obj_abs_site[] (データ
  住所の組とオブジェクト出力の穴の位置)、
  obj_flush_site、obj_prefix_insts

手順:

1. 飛び先の集合を集める (分岐・ジャンプの
   imm >= 0 と func_entry の全要素)
2. ウィンドウ走査: パターンは飛び先の命令、
   JAL/JALR/ECALL を跨がない
3. 削除しながら圧縮し、旧→新の対応表を作る
4. 付け替え: 分岐・ジャンプの imm、
   func_entry[]、dfaddr_site[]、
   obj_reloc_site[]、obj_abs_site[]、
   obj_flush_site、obj_prefix_insts

最大のリスクは付け替え漏れ。付け替え対象を
上の列挙で閉じ、検証 (下記) で検出する。

## 結果 (2026-11-23)

実装は src/03-genstmt.c の peep_run (gen_all の
末尾、呼び出し fixup の前)。プロファイルの
書き換えは peep_tgt[24576] のぶん
03-genstmt.c の '[24576]' の個数を 1 → 2 に
更新した (断片・shirasu とも)。

nami_all での実測 (最適化前 → 後):

- 命令数 15,651 → 15,485 (−166、約1.1%)
- ロード 3,263 → 2,802 (−461)。削除と
  mv への転送の合計
- 消せる nop move は 0 に (残る addi rd, rd, 0
  は住所の組の下半分で、消せないもの)

見積もり (約450) より減り幅が小さいのは、
静的カウントが楽観的だったため: 対象の形でも
間の命令がレジスタを書き換える場合は安全側で
止める。パターン4 (store-back) は nami では
0件だった。候補に見えた箇所は全部、load した
値を演算で書き換えてから戻す eval-stack の
型で、消せるものではなかった (実測で確認)。

## 実装で見つけた前提 (アドレスの焼き込み)

最初の実装は test.sh の v25 で落ちた。データ
住所の組 (auipc + addi) は生成時に hi/lo を
焼き込んでいて、auipc の位置が peephole の
削除でずれると住所が狂う (関数の住所は
dfaddr で既に「最後に埋める」形だったが、
データ側は焼き込みだった)。

直し: データ住所も dfaddr と同じく組だけ
置いて控え (置き場は一括では未使用の
obj_reloc を借りる)、gen_all の最後、
peephole の後に bake_daddr が位置から
pc を数え直して埋める。peephole 側は
obj_reloc_site / obj_abs_site も命令番号の
持ち主として付け替え+保護の対象に加えた。
控えが溢れたらその場焼きに切り替えて
peephole を丸ごと止める (位置が動かない
ので正しさは保たれる)。

もう1つ容量の工夫: 飛び先の印は専用の表を
持たず、patch_next の先頭をビット列として
借りる (パッチの鎖は生成が終われば用済み)。
専用表 char[24576] では断片プロファイルの
データが 1MB 枠を 24KB 超えたための措置で、
この形では iwac 断片のデータは v51 と同じ
1,047,512 バイトに収まった。

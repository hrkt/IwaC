# IwaC セルフホスト計画

目標: **iwac が iwac.c 自身をコンパイルできる**こと。
この文書は、そのための作業計画である。全体の見取り図は
doc/roadmap.md の「セルフホストへの階段」にあり、ここには
各段の設計メモと、実装するときに決める点を置く。

## 完了の定義（固定点）

1. gcc でビルドした iwac（ホスト版、または kosaba 版
   iwac.elf）が、kosaba_rt.c + iwac.c をコンパイルして
   iwac2.elf を作る
2. KosabaOS 上で iwac2.elf が同じ入力をコンパイルして
   iwac3.elf を作る
3. **iwac2.elf と iwac3.elf がバイト一致する**（固定点）。
   一致すれば「自分で自分を作れる」ことが証明できる
4. ついでに iwac2.elf が hello.c をコンパイルして
   Hello World が動くこと

## 地ならし（実測、2026-11-02）

- iwac.c は 2760 行・約 116KB。コメントが体積の多くを
  占める（コンパイル対象としては字句で読み飛ばされる）
- iwac.c が使っていないもの: 構造体、switch、三項演算子、
  sizeof、剰余 %（ほぼ未使用）、関数ポインタ、do-while。
  これらは階段に入れない
- 使っている主なものと件数の目安: && 47、|| 38、<< 63、
  for 40、break/continue、++ 87、-- 47、return 274 行、
  関数の引数は最大でも 3 個程度（find_var(name, len) 型）
- グローバル変数は初期化子つき宣言が約 50 件
  （static int REG_ZERO = 0; の類）。配列は int 配列
  （node_kind[512] 等）と char の 2 次元配列
  （var_names[4][32] 等）がある
- main の形は int main(int argc, char **argv)。
  argv[i] の添字アクセス（char** の要素は 8 バイト）が要る
- 唯一のアドレス取得は out_byte の &b（1 か所）

## 共通の決め事

- 一段ずつ進め、前の段の検証（従来プログラムの振る舞い
  不変＋test.sh 全 PASS）が終わるまで次へ行かない
- iwac.c 本体への変更は v25 の容量定数だけに抑える
  （実際はカンマ宣言1行の分割も入った。v25 実施結果に記録）
  （「今ある iwac をコンパイルする」が目標のため。
  容量は言語機能ではなく表の大きさの問題として分ける）
- バイト互換は v20 まで維持する。v21（変数のメモリ化）で
  生成コードの形が変わるため、以降は「振る舞いの互換」
  （QEMU での出力一致）を互換の定義とする
- 型は従来どおり「意味は持たない」が、v21 からは宣言の
  情報として「指す先の大きさ」（char = 1 バイト、それ
  以外 = 8 バイト）とポインタの段数だけを覚える。
  argv[i] の歩幅（8 バイト）と *s の歩幅（1 バイト）を
  区別するために最低限必要な情報がこれ

## 各段の設計メモ

### v16 字句の完成（済み、2026-11-02、0c62fd3）

- ブロックコメント、文字リテラル、型の語彙
  （long / unsigned / signed / short、is_type_word に統一）

### v17 複数ファイル入力

- `iwac a.c b.c ...` の形で、複数のファイルを順に
  つないで1つのソースとして読む。境目には改行を
  1つ挟む（トークンがくっつかないように）
- 引数が2つ以上のときは全部ファイルとして扱い、
  1つでも開けなければエラー（どのファイルか名前を
  出す）。引数が1つのときは従来の規則のまま
  （.c はファイル必須、それ以外は開ければファイル、
  無ければ引数そのものをプログラムとする）
- #define の展開は連結後のソース全体にかかるので、
  前のファイルの #define が後のファイルで使える
- これで v27 の「kosaba_rt.c + iwac.c の連結」が
  cat の力技でなく iwac 自身の機能になる。一般の
  プログラムでも「部品のファイル＋本体のファイル」
  という分け方ができる

### v18 条件付きコンパイル（済み、2026-11-02）

- #ifdef / #ifndef / #else / #endif を前処理
  （expand_defines）に入れた。段ごとの状態
  （いまの枝が有効か・有効な枝が来たか・#else 済みか）
  を積み、無効な範囲の行は出力せず #define も
  登録しない。条件の指令だけは無効な範囲でも数える
- 定義済みマクロ: __IWAC__ は常に、__KOSABA__ は
  --kosaba のときに 1 で定義済み。1つのソースで
  ベア版と OS 版を切り替える用途を想定した
- 実装の都合で、展開器でもブロックコメントの内側を
  追うようにした（コメントの中の行頭の # を指令と
  誤認しないため。有効・無効どちらの範囲でも）
- #if（式の評価）は引き続き対象外

### v19 演算子の完成（済み、2026-11-03）

- 足すもの: `<<` `>>`、`|` `^`、`%`、`!`、`&&` `||`、
  単項マイナス、前置/後置の `++` `--`
- 優先順位の段を C の順に増やす: || → && → | → ^ → &
  → ==/!= → 関係 → シフト → 加減 → 乗除・剰余 → 単項
  → 材料。今の parse_expr（& の段）の上に3段
  （|、^ は & の上下に分かれるので再編が要る）、
  関係と加減の間にシフトの段を挟む
- 命令の追加: OP_SLL / OP_SRL（sll は R 形式 funct3=1、
  srl は funct3=5。算術右シフト sra も funct7 で区別。
  iwac.c は符号付きの >> を使うので sra が本命）、
  OP_OR / OP_XOR、OP_REM（M 拡張。div と対）
- && と || は短絡評価が必須（iwac.c は `p && *p` の
  ような安全確認に使う）。AST は NODE_AND のような
  二項ノードではなく「条件ジャンプ型」で生成する:
  左を評価し、&& なら 0 で枝先へ、|| なら 0 でない
  ときに枝先へ飛び、結果を 1/0 にする。while の条件
  生成と道具を共有できる
- ! は「0 と等しいか」で 1/0 化（== の生成と同じ道具）
- ++/-- は文としての形（i++;）と式の中の形（a[i++]、
  *p++）の両方が iwac.c にある。前置は「増やしてから
  値」、後置は「値を使ってから増やす」。対象は変数と
  ポインタ変数。生成は対象の置き場所を知っている必要が
  あり、v21 のメモリ化と相性が良いが、現行のレジスタ
  変数でも実装は可能（対象レジスタへの addi）
- 実装時に決める: `5 = -3` のような定数の畳み込みは
  しない（実行時計算で統一、従来どおり）

実施結果（2026-11-03）: 計画どおりに実装し、test.sh
全シナリオ PASS。実装上の確定事項:
- 優先順位の段は parse_bitand/bitxor/bitor/land の
  4関数を新設し、parse_expr が || の段になった。
  シフトの段は関係と加減の間。単項の段（parse_unary）が
  ポインタ読みも受け持ち、後置（parse_postfix）の上に
  置いたので `*p++` が `*(p++)` と読める
- && の生成は二項ノード方式でなく分岐方式（設計どおり）。
  左は分岐で消費されるので退避なし。結果の 1/0 化は
  sltu（!= 0 の判定）を共用。! は sltiu 一発
- ++/-- は文の形（parse_stmt_list の先読みに増減文を
  追加）と式の形の両対応。変数がレジスタにいる今は
  addi 2命令で生成できた（v21 のメモリ化では置き場所
  の読み書きに変わる）
- 旧来の「&& はエラー」という test.sh の期待は、
  使えることの確認に置き換えた

### v20 制御構文の完成（済み、2026-11-03）

- for: `for (初期; 条件; 更新) { }`。while への
  読み替えで実装する（初期→条件ループ→本体→更新）。
  初期の位置に宣言（`for (int i = 0;`）が来る形は
  iwac.c で多用されるが、局所変数の宣言そのものは
  v21 の領分。v20 では代入・式の初期化だけを受け、
  宣言つきは v21 で開ける、と区切る
- break / continue: ループの生成中に「脱出先」と
  「継続先」の命令番号を積む場所が要る。ループの
  ネストに対応するため、parse ではなく gen 側で
  スタック状に管理する（while の飛び先書き直しと
  同じ道具立て）。if の中の break も正しく効くこと
- return（値なし・早期）: 関数の出口へのジャンプとして
  生成し、出口で ra 復帰の後始末に合流させる。
  戻り値つきは v22

実施結果（2026-11-03）: 計画どおりに実装し、test.sh
全シナリオ PASS。確定事項:
- for の更新は NODE_FORSTEP で包んで本体リストの最後に
  繋ぐ形にした（gen が歩くときに見つけて continue の
  飛び先をそこに確定する）。更新なしの for では
  continue は条件判定へ直行
- break/continue/return の飛び先リストは patch_next[]
  で命令同士を繋ぐ実装（命令番号がリスト要素）。
  ループの深さごとに先頭を持ち、入れ子の内側だけに
  効くことを確認。while の生成をこの道具で組み直して
  も、従来プログラムの出力はバイト不変だった
- 使える場所の検査は parse 側（parse_loop_depth /
  parse_in_func）。宣言つき for 初期化と戻り値つき
  return は、対応する段（v21 / v22）を案内するエラー
  にした

### v21 変数のメモリ化（済み、2026-11-03）

- 変数の置き場所を一律メモリにする:
  - グローバル変数: 静的領域に 8 バイトずつ割り付ける。
    bare ターゲットでは文字列・配列の後ろ、kosaba
    ターゲットでは ELF のデータ領域（2MB）に載る形
    （memsz の差分。ローダがゼロ埋めする）
  - ローカル変数と引数: スタックフレーム内。関数ごとに
    「フレームの大きさ」を parse で集計し、序文で
    sp を引く（今の ra 退避と合わせて一つの序文にする）
- 記号表の拡張: 変数ごとに「種類（グローバル/ローカル/
  引数）」「場所（静的領域のオフセット、または
  フレーム内のオフセット）」「指す先の大きさ」
  「ポインタ段数」を持つ。スコープは関数単位
  （ブロック単位のスコープは iwac.c が必要としない
  範囲では作らない。同名の局所変数が別の関数に
  あってもよい、までが仕様）
- 生成の変更: 変数の読みは ld、代入は sd が基本。
  「変数レジスタへの割り当て」方式（t3〜t6、最大4個）は
  廃止する。式の評価スタック（t1/t2 と退避）の約束は
  そのまま
- 単項 `&`: 変数・配列要素の住所を値にする。
  グローバルなら静的領域の住所、ローカルなら
  sp + オフセット（実行時に計算）
- この段で生成バイナリの形が変わる（バイト互換は
  ここまで）。検証は全プログラムの「振る舞い」で行う
- 実装時に決める: 引数の受け渡しは a0〜a3 から
  フレームへコピーする形で統一する（v22 と接続）

実施結果（2026-11-03）: 計画どおりに実装し、test.sh
全シナリオ PASS（振る舞いの一致で検証）。確定事項:
- フレームは「入口で sp をフレーム長（16 + 枠数×8 を
  16バイト切り上げ）だけ引き、ra を fp-8、旧 fp を
  fp-16 に退避、fp = sp + フレーム長」。枠 k は
  fp - フレーム長 + 8k。式の評価の sp 上下に影響
  されないよう、ローカルは fp 相対に統一した
- 記号表は1つの表のまま、var_owner（-1=グローバル /
  関数番号）・var_slot・var_bsize・var_plevel を追加。
  find は「自関数のローカル → グローバル」の順。
  宣言は define_var_typed の is_decl で意味を分け、
  代入由来の定義と違い、同名グローバルを隠して
  自スコープに作る（ここを取り違えたのが実装中の
  唯一のバグで、objdump で切り分けた）
- kosaba 向け ELF は従来どおり1セグメントで、
  グローバルは配列と同じく memsz の差分（ゼロ埋め）。
  データセグメントの分離（W^X 対応）は、配列も含む
  従来からの課題として v24（グローバル宣言の段）で
  合わせて扱う
- 引数の受け渡しは a0 から枠へ sd（v22 で a0〜a3 に
  拡張される形）

### v22 関数の完成（済み、2026-11-03）

- 引数 4 つまで（a0〜a3）。呼び出し側は式として
  評価した引数を a0〜a3 に置く。引数が式の中で
  ネストする呼び出し（f(g(x))）では a レジスタの
  退避が要る: 引数の評価順と退避の規則を決める
  （右から評価してスタックに積み、最後に a0〜a3 へ
  順に移す、が単純で正しい）
- 戻り値: return 式; は値を a0 に置いて出口へ。
  呼び出しは式の材料になる（NODE_CALL が値を返す）。
  戻り値を使わない呼び出し文も従来どおり書ける
- 再帰: フレームが関数ごとに独立するので、parse 系・
  gen 系の再帰関数（式のネスト）がそのまま動く。
  検証にフィボナッチ等の再帰プログラムを使う
- main の扱い: kosaba ターゲットで main が引数を
  持つ場合、入口で決め打ちの argv（kosaba/ の crt と
  同じ {"iwac", "--kosaba", "hello.c"} と、その
  ポインタ配列を静的領域に用意）を a0/a1 に渡して
  から呼ぶ。bare ターゲットでは引数なし呼び出しの
  まま（引数つき main の bare 実行は意味を持たない）

実施結果（2026-11-03）: 計画どおりに実装し、test.sh
全シナリオ PASS。確定事項:
- 引数の受け渡しは計画どおりの「右から評価して
  スタックに積み、最後に a0〜a3」方式。a レジスタへ
  移すのが全引数の評価後なので退避は要らなかった。
  右から評価されることは副作用の順序で確認済み
  （C では順序は未規定だが、iwac では右からと決まる）
- argv の置き場所はグローバルの後ろ（文字列 24
  バイト＋ポインタ配列 24 バイト＝memsz に 48）。
  中身は入口の生成コードが実行時に組み立てる方式
  にした（ELF の filesz にデータを埋める方式より、
  encode 側に手を入れずに済む）
- **OS 上での実走確認は v24 送り**: --kosaba 生成
  プログラムの静的データは、現行の1セグメント ELF
  では OS のコード領域（0x40000000 のメガページ、
  読み・実行のみ）に載るため、書き込みが store
  page fault になることを OS のスクラッチコピーで
  実測した。v21 のグローバル書き込みでも全く同じ
  で、argv 固有の問題ではない（ベアメタルでは
  問題にならない）。v24 でデータセグメントを
  0x40200000（読み・書き）へ分離するときに、
  argc/argv の実走まで合わせて確認する

### v23 配列の完成（済み、2026-11-03）

- 要素の大きさ: char の配列は 1 バイト、それ以外
  （int / long 等）の配列は 8 バイト。宣言の型から決める
- 2 次元配列: `型 名前[行][列]`。名前[i] は行 i の
  先頭アドレス（値）、名前[i][j] は要素。生成は
  「基底 + i × 列数 × 要素長 + j × 要素長」
- ポインタの添字: p[i] を *(p + i × 指す先の大きさ)
  として読む/書く。指す先の大きさは v21 で覚えた
  宣言情報から。argv[i] はこれで 8 バイト歩幅になる
- 配列の初期化子（{ 1, 2, 3 }）は iwac.c が使わない
  ので作らない

実施結果（2026-11-03）: 計画どおりに実装し、test.sh
全シナリオ PASS。確定事項:
- 要素の住所計算は読み書き共通の gen_elem_addr に
  まとめた（INDEX / INDEX2 / PINDEX / INDEX_STORE が
  全部使う）。読みは大きさで lbu / ld、書きは sb / sd。
  ×8 は新設の slli 命令（OP_SLLI）
- ポインタの配列（char *names[2]）の要素はポインタ
  なので 8 バイト。char **pp の pp[i] の歩幅も 8
  （argv の形をベアメタルで模擬して確認済み）
- ポインタの加減算（p + 1）の歩幅は従来どおり
  バイト単位のままにした: 計画の対象は添字だけ
  で、iwac 自身のソースのポインタ前進は char* の
  s + 1 しかないため
- 実装中の落とし穴は1つ: 書き込み文の先読み
  （parse_stmt_list）が ']' を1段しか数えず、
  t[i][j] = 式; が文として認識されなかった。
  ']' の後に '[' が続けば数え直すよう直した

### v24 グローバル宣言とプロトタイプ

- ファイル範囲の変数宣言: `型 名前;` と
  `型 名前 = 式;`（初期化子は定数式と文字列のみ
  受ける。初期値は静的領域の初期イメージとして
  バイナリに埋める: bare では文字列の後ろに初期値の
  並びを置き、kosaba では ELF のデータセグメントの
  filesz 側に載せる）
- 関数プロトタイプ: `型 名前(引数の型並び);` の宣言を
  受け付ける。本体が後から定義されれば通常の関数に
  なり、最後まで定義が無ければ「外部」とみなす。
  外部の関数の呼び出しは、単独バイナリでは行き先が
  無いので、リンク時に相当する仕組みとして v27 の
  ランタイム結合（ソースの連結）で解決する。
  定義の無い関数の呼び出しが残ったままなら生成時に
  エラーにする
- グローバル配列の宣言もここでファイル範囲に開ける
- ELF のデータセグメント分離（v21・v22 で先送りに
  なった W^X 対応）もこの段で: 静的データ（配列・
  グローバル・argv）を PT_LOAD 2本目として
  0x40200000（読み・書きの領域）へ分ける。分離後に、
  v22 で保留した main の argc/argv と、グローバル
  書き込みの OS 上での実走確認を合わせて行う

v24 の実施結果（2026-11-03）:

- ファイル範囲の宣言が文リストから外れ、main と
  混在できるようになった（実行文と main の混在は
  従来どおり禁止のまま）。初期化子は定数評価器
  （eval_const: 数・文字列・単項 - !・二項の算術と
  ビット演算）でコンパイル時に計算し、初期イメージ
  （配列のゼロ＋グローバル8バイトずつ、文字列なら
  確定した住所）として埋める。初期化子の無い
  プログラムの bare 出力は v23 とバイト単位で一致
- プロトタイプ: 引数は「型と名前」を集めてから、
  ';' なら宣言（名前は捨てる、省略も可）、'{' なら
  定義（名前を変数登録）。宣言済みの関数への定義は
  名簿の続きとして読み、引数の数の食い違いは
  エラー。呼び出しの印（func_called）と本体の有無
  （func_has_body）で、定義の無い関数の呼び出しを
  生成の入口でエラーにした
- ELF 分離: PT_LOAD 2本（コード 0x40000000 R+X /
  データ 0x40200000 R+W、データのファイルオフセット
  は 4096 境界）。静的データの住所は data_base
  （kosaba 時 0x40200000、bare 時は従来どおり
  コードの後ろ）を基点に確定する
- OS 実走確認（OS のスクラッチコピー＋Nish）:
  main の argc/argv プログラムが 'C55'（'C'＋
  fib(10)）を出して復帰、グローバル書き込みが
  'AB'、初期値つきグローバル＋文字列が 'HXYI'
  （初期イメージの読みと書き換え）。v22 の保留は
  ここで解消した

### v25 容量の調整

- 「ソースの上限 約64KB」とは: iwac はソースファイルを
  固定の箱 src_buf（65,536 バイト）に丸ごと入れてから
  解析する（malloc を使わない設計のため）。ファイルが
  箱より大きいと、読む段階で「ファイルが大きすぎます
  (約64KBまで)」のエラーになり、解析まで進めない。
  iwac.c 自身は 115,639 バイトあるので、今の iwac は
  自分のソースを入口で弾かれてしまう。制限はファイル
  そのものにかかるので、体積の多くを占めるコメントも
  含めて全部が対象になる（読む時点ではコメントかどうか
  分からないため）。64KB という数字は v10 でファイル
  入力を作った当時の想定（hello.c は約1KB）で十分
  だったというだけのもの。#define 展開後の箱 exp_buf
  （131,072 バイト）も連動して確認する
- iwac 本体（src/）側の定数を育てる（この段だけ本体を編集）:
  ノード表 512 → 必要な実測値、命令表 2048 → 同、
  文字列プール 4096 → 同、ソース上限 約64KB → 256KB、
  exp_buf も連動。必要量は事前にホスト版で計測する
  （iwac.c を読ませて使用量を数える道具を一度作る）
- 言語側の上限: 配列の個数（8 → 64）、配列の総量
  （4096 → データ領域に収まる範囲）、変数・関数の
  個数の上限も実測に合わせる
- kosaba のデータ領域は 2MB。iwac の静的データの
  合計（表＋バッファ）が収まることを確認する。
  収まらない場合は OS 側の領域拡張を相談する
  （コード領域 2MB も同様に確認）

- 実測（計測版 iwac: 表を巨大化し使用量を stderr へ
  出す使い捨てビルドで、iwac 自身のソース約212KBを
  --kosaba コンパイル）: ノード 10,951、命令 26,233
  （生成コード約103KB。コード領域 2MB に十分収まる）、
  変数 513（うちグローバル 131）、関数 99、文字列

- 決めた定数（実測の約1.3〜2.5倍）: ノード 16384、
  命令 32768（patch_next も同数）、変数 1024、
  関数 128、引数 8 つまで、配列 128 個 / 合計 4MB /
  個別 1M 要素、文字列プール 16384 / 512 個、
  src_buf 262144（約256KB）、exp_buf 262144
- コンパイルされた iwac の静的データは約2.9MB で、
  kosaba のデータ領域 2MB に入らない。OS 側へ
  データ領域の拡張を相談し、2026-11-03 に決定した:
  virt は案A（データ領域 4MB、スタックは VA
  0x40600000 開始・トップ 0x40800000）で広げる。
  K210 でのセルフホストは目標にしない（汎用 SRAM
  6MB を現行配置で使い切っているため）。セルフ
  ホストの実証は QEMU virt か将来の Milk-V 系で
  行う。→ OS 側の実装も 2026-11-03 に完了した

  スタックトップ VA は virt 0x40800000）。v27 の
  前提はこれで揃った
- 計測の過程で、2026-11-02 の地ならし実測で「不使用」
  とした形が実際は使われていることが見つかり、言語側
  へ追随した: static 修飾子、引数8つ、(void) 引数、
  if / while / for の単一文本体と裸のブロック、
  三項演算子、キャスト（読み捨て。切り詰めに頼る
  箇所は iwac のソースに無いことを前提とする割り切り）、
  複合代入 op=、要素への ++ / -- と単項 &、単項 ~、
  数値リテラルの接尾辞と 10進数上限の int 範囲化、
  エスケープ \r
- 唯一のカンマ宣言（eval_const の `long l, r;`、v24 で
  混入）は言語に足さず、本体側を2つの宣言に分けた
  （本体への変更は容量定数とこの1行だけ）
- 恒常版 iwac で iwac 自身のソースを通すと、今度は
  ローカル配列（`char name_buf[32];` 等）の宣言で
  「その名前は既に使われています」になる。配列に
  スコープが無く、他関数の同名配列と衝突するため。
  これが次段 v26 の主題

### v26 配列のスコープとローカル配列（済み、2026-11-03）

- 配列の名簿に持ち主（arr_owner）を足し、名前の解決を
  変数と同じ流儀にした（自関数の配列 → グローバル
  配列の順。同名のローカル配列が関数ごとに持て、
  ローカルが同名グローバルを隠す）
- ローカル配列は静的領域ではなく関数のフレームに置く
  （v21 の変数のメモリ化と同じ考え方）。置き場所は
  変数の枠の並びの上で、フレーム長に合計
  （func_arr_bytes）が加わる。基底アドレス作りは
  gen_load_arr_base に一本化し（静的な住所か fp 相対
  かを配列ごとに切り替え）、要素の読み書き・行
  アドレス・&要素の全てがそこを通る
- 落とし穴: 初版で配列を枠の並びの下に置いたら引数
  スロットと重なり、再帰のテストで発覚した（引数を
  配列の書き込みで潰して無限再帰）。枠の上に置く
  形に直し、再帰・変数との共存・大きなローカル
  配列（オフセットが addi 範囲外）まで確認した
- iwac 自身のソースのローカル配列: name_buf[32]
  （4関数）、pnames[8][32] と plens / pbs / ppl[8]
  （parse_funcdef）、bytes[22]（gen の中）など
- 結果: iwac 自身のソースは parse を通り切った。
  恒常版で通すと、生成の入口の未定義チェックで
  止まるだけになった。呼ばれているのに定義が無い
  のは外部の4関数（write / open / read / close、
  いずれも iwac のソースで宣言だけしてある OS の
  関数）だけであることを切り分け済み。仮の定義を
  足した予行演習では、自分自身の ELF（3,023,427
  バイト、PT_LOAD 2本）まで生成できた。実物の
  定義は次段 v27 の kosaba_rt.c が埋める
- ローカル配列の無いプログラムの出力は v25 と
  バイト単位で同一（hello.c、hello-kosaba.c で確認）

### v27 セルフコンパイル（済み、2026-11-03）

**固定点を達成した。** ホスト版 iwac が作った
iwac2.elf（3,076,094 バイト、digest 版）と、KosabaOS
上で iwac2 が作った iwac3.elf がバイト単位で一致
（digest len=3076094 sum=000000000074f2a5
hash=579ecc1a0ae79a7f は両者一致、さらに生成物を
シリアル経由で回収して全バイト比較でも一致を確認）。
iwac3 が作る第2世代も同じ digest。あわせて iwac2 が
OS 上で hello.c をコンパイルし Hello, World! が
動くことも確認した（完了の定義 1〜4 を全部満たす）。

揃えた部品:

- 組み込み `syscall3(番号, a0, a1, a2)`: KosabaOS の
  システムコールを直接呼ぶ式（戻り値は a0）。
  KosabaOS 専用で、ベアメタル向けではエラー。
  putc と同じ予約名の扱い。文としても書ける
- `kosaba/kosaba_rt.c`: 外部4関数（write / open /
  read / close）を iwac の言語で実装（kosaba_lib.c と
  同じ約束: fd=2 は putc へ、fd=1 は hello.elf への
  8KB バッファ付き書き込み）。入力の並びは本体の
  断片の後ろ（プロトタイプより前に定義が来ると
  二重定義になるため）
- `kosaba_flush` のフック: KosabaOS 向け入口は main
  の後に同名関数を呼ぶ（GCC 版 crt の約束の移植）。
  rt の書き切りに使う。無いプログラムの出力は不変
- digest 版 rt（`#ifdef IWAC_RT_DIGEST`、定義用の
  1行ファイルを前に挟む）: 出力のバイト数・合計・
  ハッシュをコンソールへ出す。OS のファイルに
  入り切らない約3MB の生成物を、取り出さずに
  ホスト側の digest と比べるための仕掛け

セルフコンパイルで発覚した不具合（いずれも実物の
iwac を自分でコンパイルして初めて出たもの）:

1. **自分のソースの仕様外の書き方**: 要素への複合
   代入 `func_arr_bytes[parse_cur_func] += alloc;`
   （複合代入は変数だけ）。ソース側を通常の代入に
   書き換えた（本体への変更は容量定数のほかこれ
   だけ。「共通の決め事」の例外として記録）
2. **前処理が文字リテラルを守らない**: `'"'` で
   文字列開始と誤認し、行頭状態が壊れて後ろの指令
   行を読めなくなっていた。文字リテラルも丸ごと
   守るよう修正（無効範囲の読み飛ばし側も同じく）
3. **条件分岐の距離**: beq の届く範囲（±4KB）を
   大きな関数が超え、符号化が溢れを黙って切り
   捨てて別の場所へ飛んでいた。届かない分岐は
   「反転した分岐 + jal」に伸ばす緩和を生成に
   入れた（生成を繰り返して収束を確認。届く分岐
   は1命令のままで従来出力は不変）
4. **大きな定数の作り方**: (a) 0x7FFFF800 以上は
   lui の符号拡張で壊れる → addiw に変更し hi/lo
   を long で計算。(b) 0x80000000 以上の16進数は
   auipc 相対（住所作り）で代用していた → 0 埋めで
   広げる gen_load_u32（lui + addiw + slli/srli 32、
   分岐なしで常に同じ形）。(c) グローバルの初期値
   （eval_const）も同じ数の読み方に統一
5. **`*p` の読み書きが常に1バイト**: int* 経由の
   受け渡し（append_file のバイト数）が下1バイト
   に切れて読み込みが壊れた。指す先の型の大きさで
   読み書きするよう修正（絶対アドレスと計算式の
   相手は従来どおり1バイトのまま = 既知の非対称。
   ポインタとして宣言されていない変数（段数 0、
   代入で作られて文字列を持つ昔の使い方）も従来
   どおり1バイト — これは test.sh の print loop の
   回帰で気づいて守った）
6. **表現の一貫性（固定点の前提）**: iwac の型は
   全部64ビットでキャストは読み捨てなので、「int
   に切り詰めたはずの値」の見え方が GCC 製と
   iwac 製で食い違い、出力が作ったコンパイラで
   変わった。約束として揃えた: 16進リテラルは
   parse の時点で int の範囲に畳む、生成の分岐は
   符号つきの値で決める、定数の作り方は分岐なしで
   常に同じ形にする

検証の置き場: OS のファイル置き場は標準で arena
256KB / create 予約 32KB で、約3.0MB の iwac3 は
入り切らない。固定点の確認はスクラッチの OS で
arena 8MB / 予約 4MB に広げて行った（iwac の ELF
はデータの filesz が memsz ほぼそのままになる
ため）。OS 本体に広げるかは OS 側の判断として
相談する。K210 でのセルフホストは目標にしない
（v25 の決定どおり）。

### v28 ELF の BSS 化（済み、2026-11-03）

- v27 の固定点は「約3.0MB のファイル」で確認したが、
  その中身は 99.8% がゼロだった（データの実体は
  文字列とグローバルの初期値だけ）。そこで ELF の
  書き出しを変えた: PT_LOAD を 3本にし、2本目は
  「文字列の実体 + 配列の確保分」、3本目は
  「グローバルの実体 + argv の確保分」。ゼロの部分
  は p_memsz との差分として、OS のローダ（elf.c、
  もともとゼロ埋め対応）に埋めさせる
- iwac2.elf は 3,076,045 → 126,893 バイト（データの
  実体は文字列 7,014 + グローバル 1,144 バイト）。
  OS 上の実行確認: 200,000 バイトのゼロ配列の後ろに
  ある初期値つきグローバルが正しく読めた。固定点も
  新しい書き出しで再確認（digest len=126942
  sum=0000000000753ddc hash=2ea55d80dd8e669a）。
  メモリ上の大きさ（memsz 約2.96MB）は不変なので、
  K210 の話は shirasu のまま
- 副次効果: OS の FS に置くファイルが約127KB になり、
  置き場の圧迫は大きく減った（それでも標準の create
  予約 32KB は超えるので、OS 側の FS 拡大は意味が
  あるまま）。なお本体ソースの合計は 261,944 バイト
  で、ソース上限 262,144 に約200バイトまで接近して
  いる。次に大きな追加をする前に容量の引き上げが
  要る

## リスクと注意

- 再帰の深さ: parse は式のネストで再帰する。iwac.c の
  式は浅いのでスタック 2MB で足りる見込みだが、
  フレームの大きさ次第。固定点の検証で実測する
- 生成コードの大きさ: メモリ化で命令数は増える。
  iwac.c のコンパイル結果がコード領域 2MB に
  収まるかは v25 で計測する
- 検証の資産: 各段で test.sh に確認を足し続ける。
  振る舞いの互換が崩れた段があれば、その段の中で直す

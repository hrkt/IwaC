# 関数ポインタ (間接呼び出し) の設計 (v44)

位置づけ: 基本拡張の2番目 (doc/missing-features.md) の
設計メモ。switch (v43) の次に着手する。実装は
このメモを置いてから別コミットで進める。

## 動機: 命令ディスパッチ

中心の用途はインタプリタの命令ディスパッチ。
Z80 エミュレータを書いてみたい、という話が
2026-11-15 に出た。命令コードでハンドラを引く形は
2つある:

- switch で振り分ける: v43 で書けるようになった。
  ただし比較の連鎖なので、256 命令の振り分けでは
  1命令ごとに最大で数百回の比較になる
- ハンドラ表 (関数ポインタの配列) で引く:
  `table[opcode](...)` の1回の間接呼び出しで済む。
  インタプリタの内側のループではこちらが本命

他にも比較関数の受け渡し (qsort 型)、コールバック、
ドライバの操作表など、C では普通に使う形が
まとめて書けるようになる。

## 書ける形 (v44 の範囲)

typedef が中心の形。Z80 のハンドラ表を例にする:

```c
struct Z80 { int pc; };  /* 状態はポインタで渡す */
typedef int (*handler)(struct Z80 *z);

int op_nop(struct Z80 *z) { return 4; }
int op_halt(struct Z80 *z) { return 4; }

handler main_table[256] = {
    op_nop, op_halt, /* ... */ 0
};

int step(struct Z80 *z, int opcode) {
    handler h = main_table[opcode];
    if (h == 0) return -1;
    return h(z);          /* 間接呼び出し */
}
```

入れる形:

- typedef: `typedef int (*handler)(struct Z80 *z);`
  (v36 で明示的に断っていた関数ポインタの typedef
  を解禁する)
- 変数の宣言: typedef 経由 (`handler h;`) と、
  直接の形 `int (*fp)(int);` の両方
- 配列: typedef 経由 (`handler table[256];`) と、
  直接の形 `int (*table[256])(int);`
- 引数: typedef 経由と直接の形の両方。引数としての
  関数ポインタは「関数ポインタへのポインタ」では
  なく関数ポインタそのもの (C の調整はしない。
  宣言した段数のまま扱う)
- 呼び出し: `fp(x)`、`table[i](x)`、`(*fp)(x)`、
  構造体のメンバやポインタ越し (`z->op(x)`,
  `ops[i](x)`) も、型の追跡が届く範囲で同じ形
- 関数の住所を取る: `h = op_nop;` (名前が住所に
  なる、C と同じ) と `h = &op_nop;` の両方
- 戻り値: typedef 経由なら関数ポインタを返せる
  (`handler pick(int i) { return table[i]; }`)
- 初期化子: ファイル範囲で
  `handler h = op_nop;` (スカラ) と、配列の
  `= { op_nop, op_halt, 0 }` (要素は関数名か 0、
  1次元だけ)。足りない要素は 0 埋め (C と同じ)
- 0 との比較・代入: `h = 0;`、`if (h == 0)` は
  普通のポインタと同じに扱う

切り捨て:

- 関数ポインタを返す関数の直接の宣言子
  (`int (*pick(void))(int)` のような形) は読まない。
  typedef 経由で書く
- 関数ポインタの配列の初期化子は1次元だけ。
  ローカル変数の初期化は今までどおり代入で書く
- 署名の違う関数ポインタ同士の代入・受け渡しは
  エラー (キャストでの読み替えもなし)
- 可変長引数や、引数の型を書かない宣言
  (`int (*fp)()`) はなし。引数は必ず型まで書く

## 型の表現: 署名表 (シグネチャ)

関数ポインタの型は「戻り値の型 + 引数の型の並び」
= 署名で決まる。署名を専用の表に intern する
(同じ署名は同じ番号を共有する):

- 署名表 (上限 128): 戻り値の etype / ポインタ
  段数 / 構造体番号、引数の数、引数ごとの
  etype / ポインタ段数 / 構造体番号
- すべての関数が署名番号を持つ (func_sig)。
  関数定義・宣言を読むときに、その戻り値と
  引数から署名を引く
- 変数・配列・typedef・構造体メンバには「関数
  ポインタなら署名番号 + 1、そうでなければ 0」
  の印 (fsig) を並べて持つ: var_fsig、
  arr_fsig、tdef_fsig、smem_fsig。値そのものは
  8 バイトの住所なので、大きさと正規形は
  etype = 8 のポインタと同じ扱いでよい
- 代入と引数の受け渡しでは fsig の一致を要求
  する (0 の代入だけは例外)。検査は type_node の
  代入と呼び出しの節に足す。今の直接呼び出しが
  引数の「数」だけを見ているのに合わせ、間接
  呼び出しも数は署名と照らして厳密に、個々の
  引数の型は今の流儀どおり緩く見る

## parse の変更

- 宣言子 `(*名前)` の読みを1つの道具にまとめて、
  宣言文 (parse_decl_stmt)、typedef
  (parse_typedef)、関数の引数 (parse_funcdef の
  引数集め) の3か所で使う。`(*名前)` の後ろの
  `( 引数の型の並び )` が署名になり、名前の
  後ろに `[N]` が続けば関数ポインタの配列
- 式の中の関数名: 今は `(` が続かなければ素通り
  してエラーになる。`(` が続かない関数名は
  「その関数の住所」の式 (NODE_FADDR) として
  読む。`&関数名` も同じ節に寄せる
- 呼び出しの後置: parse_primary_node の後置の
  ループ (. や [] を捌く場所) に `(` を足す。
  ループは今の式の型 (構造体・段数) を手元で
  追跡しているので、そこに fsig も一緒に
  追跡させ、fsig が立っている式に `(` が
  続いたら間接呼び出し (NODE_ICALL) として
  読む。引数の数の検査は parse_call_list を
  署名で引く形に一般化して共有する

## gen の変更

新しい節の種類: NODE_ICALL = 59 (間接呼び出し)、
NODE_FADDR = 60 (関数の住所)。decls.c への
鏡写しは NODE_CASE の直後に同じ並びで置く。

- NODE_ICALL: lhs = 呼び先の式、rhs = 引数の
  並び、node_val = 署名番号。生成の順序は直接
  呼び出しと揃える:
  1. 引数を右から評価してスタックに積む
     (gen_call_args を共有)
  2. 呼び先の式を評価して t1 に住所を得る
     (引数の積み下ろしは t1 に触らない)
  3. 積んだ引数を a0〜 へ移してスタックを戻す
  4. `jalr ra, t1, 0` (OP_JALR は戻りに使って
     いる既存の節。rd = ra で出すのは新しい使い方)
  5. a0 → t1、戻り値の正規形は署名の戻り値で
- NODE_CALL を特別扱いしている場所 (式の値の
  退避の要否を見る節、type_node、stmt_needs_stack)
  には NODE_ICALL も並べて足す
- NODE_FADDR: 関数の住所を作る。住所作りの道具
  gen_load_addr_sym に RLOC_FUNC = 4 を足す。
  変数や文字列と違い、関数の住所はコード側で、
  分岐緩和が落ち着くまで位置が決まらない。
  オブジェクト出力では既存の控え (obj_reloc) に
  載せてリンカに任せる。一括出力では、命令列の
  最後に func_entry で JAL を埋めるのと同じ
  段階で、auipc + addi の組の即値を埋める
  (埋める場所の控えを小さな表に持つ)

## オブジェクト・リンカ・Asari

- ELF オブジェクト: 住所の組は関数のシンボルに
  対する PCREL_HI20 / LO12_I の組 (変数の組と
  同じ形、相手が関数シンボルになるだけ)。
  スカラの初期値は .rela.data の R_RISCV_64 が
  関数シンボルを指す形 (文字列の iptr と同型)
- 関数ポインタ配列の初期化子: 要素の住所は
  リンク時にしか決まらないので、.iwac.arrays の
  イメージには 0 を置き、埋める場所を新しい
  .rela.iwac.arrays 節 (R_RISCV_64、相手は関数
  シンボル) で運ぶ。節の並びは .rela.data の
  後ろに足す。nori は読み取りに1節足し、
  arr_area への当てはめで 8 バイトを書く
- .ias の注記: `addr <位置> func <名前>`、
  `fptr <変数> func <名前>` (iptr の対)、
  `afref <配列> <バイト位置> <関数名>` (新規)
  を足す。Asari の ELF 書き手も同じ3つを出し、
  「Asari の .eo == iwac の .eo」の物差しを保つ
- 初期化子の材料: arr_init_pool は数値だけの
  池なので、関数参照は池の位置と関数番号の
  対の小さな別表 (上限 1024) で持つ。parse の
  配列初期化は「ポインタの配列は初期化できない」
  の門を、fsig の立つ配列に限って開ける
- 関数の住所を取ったら func_called に印を付ける
  (本体の無い関数を指すポインタを防ぐため、
  未定義検査の対象は直接呼び出しと同じにする)

## テスト方針

- 振る舞い: 小さな命令ディスパッチ (表引きで
  ハンドラを呼ぶミニインタプリタ) を通しで
  書き、switch 版と同じ出力になることを見る。
  他に typedef と直接の形、コールバック、
  0 のチェック、署名違いの代入エラー、引数の
  数の違いのエラー、未定義関数の住所取りの
  エラー、再帰するハンドラ
- オブジェクト経路: 関数ポインタを使う
  kosaba 向けプログラムで「ELF リンク ==
  一括」と「Asari の .eo == iwac の .eo」を
  確かめる (初期化子つきの表を含む)
- セルフホスト: 固定点と digest を更新する。
  iwac 自身のソースでは v44 の形は使わない
  (OS 上の Misoni ビルドが前の版の iwac で
  新しいソースを読むため)

## 容量への影響 (実装時に実測)

- 静的データ: 署名表と fsig の印、関数参照の
  別表などで +20KB 程度の見込み。データ領域
  4MB に対して余裕はまだ十分
- ソース: parse・gen・encode・asari・nori に
  手が入るので +10KB 前後の見込み。src_buf の
  余裕は v43 時点で約 11.7KB しかなく、実装が
  大きくなると一括セルフコンパイルが上限に
  触れる可能性がある。触れた場合の手は記録済み
  の「src_buf と exp_buf の相乗り」: 展開が
  済めば src_buf は読まれないので、置き場所を
  共有すればデータ量を増やさず上限を上げられる。
  要るかどうかは実装後の実測で判断する

## 実装の順序

1. 署名表と fsig の印、typedef の解禁と宣言子
   (parse)。エラーになる形を先に固める
2. NODE_FADDR と代入・比較 (gen の住所作りと
   type の検査)
3. NODE_ICALL (gen)。振る舞いのテストを通す
4. 初期化子 (スカラと配列) とオブジェクト
   経路 (ELF・nori・Asari)
5. test.sh に v44 の節を足して全体を通し、
   ドキュメント一式と digest を更新する

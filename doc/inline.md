## mulp の実体と、現在の生成形の実測

mp3dec.c の mulp と、その中で呼ばれる sat32:

```c
int32 mulp(int32 a, int32 c)
{
    int64 v;
    v = ((int64)a * c + ((int64)1 << 29)) >> 30;
    return sat32(v);
}

int32 sat32(int64 v)
{
    if (v > 2147483647) return 2147483647;
    if (v < -2147483647 - 1) return -2147483647 - 1;
    return (int32)v;
}
```

呼び出しは mp3dec.c 内に 32 か所。ST44 では
動的約 2,000 万回 (Ikesu 側の計測)。

mulp と sat32 だけの小さいプログラムを現在の
iwac で --asari 出力して数えた実測:

- mulp 本体は 31 命令。そのうち本来の計算は
  lw 2・mul・定数作り 3・add・srai の約 8 命令。
  残りはプロローグ 5、引数の積み直し 2、
  sat32 呼び出しの組 5、正規化 2、出口への
  跳躍と後始末 4、途中値の出し入れ
- sat32 本体は 45 命令。2 つの比較と範囲外の
  定数戻しが本体だが、定数 (2147483647 等) の
  組み立てと汎用の式評価で膨らんでいる
- 呼び出し側 (引数 2 つ) は、引数を右から評価
  してスタックへ積み、a0/a1 へ読み直し、sp を
  戻し、jal、正規化までで約 13 命令 (引数式
  そのものの評価は除く)

つまり 1 回の mulp(...) は約 89 命令で、その
うち本質は積・丸め・シフト・飽和の約 15 命令。
インライン化で本体同士がつながれば約 15〜18
命令になる見込みで、1 回あたり約 70 命令の
削減。動的 2,000 万回に掛けると静的な見積もり
では 14 億命令規模 (ST44 のデコード総 1.84e9
cycles と同じ桁)。ただし命令数 ≠ サイクル
(メモリ待ち等) なので、効き目は従来どおり
perf と実機で測る。

設計判断: 汎用の小関数インライン化で mulp と
sat32 の両方を対象にできれば到達点に届く。
mulp 専用の特殊生成は要らない。本体の形に
合った追加の工夫として、丸め定数 1<<29 の
組み立て (addi + slli の 2 命令 → lui 1 命令)
は定数の組み立て一般の話なので、今回は
範囲外として末尾にメモだけ残す。

## 設計: 計画段での AST 複製 + 変数の付け替え

方式は「gen の入口で計画し、本体の AST を
呼び出し側へ複製する」:

- 計画は関数ごとに、関数の生成の前
  (func_reg_plan と同じ遅延ポイントで、それ
  より先) に 1 回だけ走り、生成の全パス
  (2 パス + 緩和の再生成) で同じ結果を使う
- 対象の呼び出し (NODE_CALL) ごとに:
  1. 被呼び側の引数・ローカル変数を、呼び出し
     側の新しい変数として変数表へ追加する
     (所有者は呼び出し側、スロットは続き番号)。
     戻り値用の変数も 1 つ追加する。
     func_nlocals[呼び出し側] をその分増やす
     ので、フレームの形は通常の変数とまったく
     同じに扱える
  2. 被呼び側の本体 AST を複製する。複製の
     とき、被呼び側の変数への参照を手順 1 の
     新しい変数へ付け替える。大域変数・関数
     への参照はそのまま
  3. 複製した本体がさらにインライン対象の
     呼び出しを含む場合、深さの上限まで再帰的
     に複製・展開する (mulp → sat32 がこれ)
  4. 呼び出しノード → {被呼び関数、引数変数
     の先頭、戻り値変数、複製本体の先頭} を
     対応表に記録する (小さい表を線形探索)
- gen 側の変更は 2 か所だけ:
  - gen_expr の NODE_CALL (A 方式): 対応表に
    あれば、引数を左から順に評価して引数変数
    へ store し、戻り値の受け口 (戻り値変数 +
    終端ラベル) を積んで、複製本体を gen_stmt
    の連鎖で生成し、終端で戻り値変数を t1 へ
    load して通常の呼び出しと同じ正規化を行う
  - gen_stmt の NODE_RETURN: インラインの
    受け口が積まれていれば、値を戻り値変数へ
    store して終端ラベルへ跳ぶ (既存の
    emit_patch_jump の仕組みを流用)。受け口が
    無ければ従来どおり関数の出口へ
- 変数の読み書き・要素アドレス等の生成経路は
  一切変えない。複製変数は呼び出し側の普通の
  ローカル変数なので var_frame_off がそのまま
  効く。これがこの方式を選んだ理由

引数の評価順は、現在の呼び出し (右から評価
してスタックへ積む) と違い左から順になる。
C では引数の評価順は未規定なので意味は変わ
らない。引数式の中に別の呼び出しがあっても、
引数変数は展開ごとに独立なので壊れない。

## 対象の条件 (全部を満たすときだけ展開し、外れたら従来の呼び出し)

被呼び側:

- 本体のある関数 (func_has_body)。A 方式の
  署名だけ (構造体の引数・戻り値は対象外で、
  B 方式の呼び出しには手を付けない)
- 引数・戻り値・ローカルに double が無い
  (戻り値の受け渡しが ft レジスタ経由になる
  ため、今回は割り切る)
- ローカル配列が無い、構造体の値のローカル
  変数が無い、関数ポインタ型の引数が無い
- 本体の AST ノード数が 64 以下、文の数が
  12 以下 (mulp は文 2・sat32 は文 3 で余裕)
- 再帰でない: 呼び出しグラフで自分自身へ
  戻る関数は対象外。関数ポインタ経由の
  呼び出し (NODE_ICALL) を含む本体も、間接的
  に自分を呼ぶ可能性を消せないので対象外
- 本体そのものは通常の関数としても残る
  (展開は追加のコピーで、元の関数は消さない。
  関数ポインタで指される場合や、展開の予算を
  超えた呼び出し側は元の関数を使う)

呼び出し側:

- 深さの上限 3 (mulp → sat32 で 2 段)
- 呼び出し側 1 関数あたりの複製ノード総数に
  上限を設ける (値は実装時に実測して決める。
  nami では mulp 32 か所 × (mulp 本体 + sat32
  本体) で約 1,500 ノードの見込み。ノード池は
  現在 12,288 なので、iwac 自身のコンパイルで
  溢れるようなら池の引き上げが容量の連鎖と
  して要る)

## 他の段との関係

- v56 レジスタ割り付け: 複製変数は計画の歩行
  (呼び出し側の本体 AST) からは見えないので、
  レジスタには乗らずメモリスロットのまま。
  今回は割り切り (将来、歩行に複製本体を
  含める余地はある)
- v57 ループ最適化: 複製本体の中のループは
  変換対象にならない (計画は被呼び側の元の
  ノード番号で引くため)。呼び出し側のループ
  の歩くポインタと複製変数が混ざることは
  ない (変数番号が別)
- v55 の subtree_has_call 等: 呼び出しは
  NODE_CALL のままなので影響なし

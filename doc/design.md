# IwaC 設計書

これは IwaC の設計を残し、成長させていくためのドキュメント。
「なぜこうしたか」を書く場所で、計画の順序は `doc/roadmap.md`、
実際にできたことの記録は `doc/progress.md`、短い決定メモは
`doc/notes.md` に置く。迷ったらここに立ち返り、設計が変わったら
ここも直す。

読んで学ぶことが目的なので、ソースコードにも解説コメントを
厚く書く方針（特に初期のステップ）。

## 1. コンパイラの全体像（3つの層）

iwac はアセンブラを持たず直接バイナリを出すが、内部は
次の3層にはっきり分ける（ユーザーの希望、2026-11-01）:

```text
入力 (プログラム文字列)
  → 第1層 parse:  ソース → AST (抽象構文木)
  → 第2層 gen:    AST → 命令列 (機械語の一歩手前の形)
  → 第3層 encode: 命令列 → 32ビット機械語 → ファイル出力
出力 (RISC-V の生バイナリ)
```

- **AST**: プログラムの意味の構造を木で表したもの。
  `65+1` は「`+` を根、左の子 65、右の子 1」の木になる。
  実装は構造体やポインタを使わず、ノードを4本の並行配列
  （種類・値・左の子・右の子）で持ち、子はノード番号で繋ぐ
  （iwac の言語にまだ無いものは iwac 自身も使わない方針）。
- **命令列**: 命令を「種類・行き先レジスタ・元レジスタ・
  即値」の組として配列に並べたもの。アセンブリ文字列では
  なくデータとして存在する。この層はビット列を知らない。
- **encode**: 命令列の各命令を RISC-V のビット配置に
  変換する。ビット列の知識はこの層だけが持つ。
- 経緯: v0 は全層が混ざっていた。v1 で parse と生成を
  分けた（文法エラーでバイナリが出ない性質はこの分離の
  おかげ）。v1 の直後に構造整理として AST と命令列を
  正式に分離した。おかげで v2（優先順位・かっこ）は
  AST の上だけで考えられ、命令列の確認と符号化の確認も
  独立にできる。
- 字句解析はまだ独立した層ではなく、第1層の中の
  数字読み取り等に含まれている（必要になったら分ける）。
- エラー処理は最小限: 入力が文法に合わなければ、iwac 自身が
  エラーを表示して終わる（変なバイナリを黙って出さない）。

## 2. 実行環境（出力バイナリの約束事）

出力バイナリの「土俵」は、KosabaOS と同じベアメタルに固定する:

- QEMU `virt` マシン、`-kernel` で渡す**生バイナリ**（ELFではない）
- OpenSBI が `0x80200000` に置いて、そこへジャンプしてくる
  （Sモード、起動直後の状態。スタック等は保証されない）
- 出力先は UART (NS16550A、ベースアドレス `0x10000000`)。
  送信レジスタはベース + 0、状態レジスタはベース + 5
- 終わり方は当面 `wfi` で駐車する（戻る先のOSがまだ無いため）

なぜ ELF でも Linux 用でもないか:
一番小さいこと、KosabaOS カーネルと全く同じ起動形式なので
学んだことがそのまま両プロジェクトで通用すること。

将来 KosabaOS 側に ELF ローダやユーザーモードができたら、
出力形式はその時点で再検討する（この設計書も更新する）。

データの配置（v3 から）: バイナリは `[コード][文字列データ]`
の順に並ぶ。文字列は末尾に 0 を付けた形（C の文字列）で
置かれ、その先頭アドレスが文字列リテラルの値になる。
実行は最後の `wfi` で止まるので、後ろのデータが命令として
実行されることはない。文字列のアドレスは、コードの長さが
決まるまで分からないため、第2層は生成を2回行う
（2パス生成: 1回目で命令数を数え、住所を確定して作り直す）。
アドレスの生成には auipc（PC相対）を使う。lui + addi の
絶対アドレス方式では、0x8020xxxx のアドレスが lui の
符号拡張（32ビット→64ビットで上位が 0xffffffff になる）
で壊れ、読み込み例外になることを実測で確認したため。
KosabaOS の C 版が `-mcmodel=medany`（auipc 前提）を
使うのも、同じ理由である。

## 3. レジスタの使い方（コード生成の約束）

バイナリが小さい間は、レジスタの役割を固定して単純に保つ:

| レジスタ | 役割 |
| --- | --- |
| `t0` (x5) | UART ベースアドレス `0x10000000` 専用 |
| `t1` (x6) | 「今の値」: 式の評価結果がここに残る |
| `t2` (x7) | 「次の項」: 演算の相手を一時的に入れる |

- v0 では `t1` に最終バイトを入れ、`sb t1, 0(t0)` で出す。
- 式が育つ (v1 の `+` / `-`) ときもこの形を保つ:
  `t1` に項を、`t2` に次の項を入れて `add` / `sub` で `t1` に重ねる。
- 式がもっと複雑になり `t1` / `t2` だけでは足りなくなったら、
  そのステップでスタックを使う設計に進む
  （スタック置き場は自分で決めて `sp` を初期化する必要がある。
  起動直後は `sp` が保証されないため）。
- 変数（v2 から）は、宣言された順に `t3` (x28) 〜 `t6` (x31)
  のレジスタへ割り当てる。当面は最大4個。変数の値を読むのは
  「そのレジスタから `t1`（式の右辺では `t2`）へ写す」こと、
  代入は「式の結果 `t1` をそのレジスタへ写す」ことで実現する。
  レジスタに住む間はメモリ上の住所を持たない（ポインタで
  指したい変数が要るようになったら、そのときに設計する）。

## 4. 機械語の作り方

- RISC-V (rv64i) の命令は原則 4 バイト固定長で、
  バイナリにはリトルエンディアンで並べる。
- 命令のビット配置（どのビットが命令の種類・レジスタ番号・
  即値か）は、ソースコードの各命令のコメントに図と共に書く。
  意味を忘れたらソースに戻れば分かる状態に保つ。
- iwac は数値を組み立てて 32 ビットの命令を作る方式を取る
  （アセンブリ文字列を経由しない）。アセンブラやリンカに
  頼らない分、命令形式そのものが学習対象になる。
- 制御の流れ（v4 から）: 分岐とジャンプの飛び先は、
  命令列の段階では「命令番号（ラベル）」で表し、encode の
  ときに「その命令からのバイト距離」に変換する
  （RISC-V の分岐は相対アドレスしか持てないため）。
  while は「条件を評価し、0 なら beq で末尾へ飛び、
  本体の後で jal で先頭へ戻る」という命令の並びに落ちる。
- 関数の呼び出し規約（v5 から、v22 で完成）: 引数は
  `a0`〜`a3` (x10〜x13) で最大4つ渡し、戻り値は `a0`
  で返す。呼び出し側は引数を右から評価してスタックに
  積み、全て評価し終えてから `a0`〜`a3` へ移す（この
  順番のおかげで、引数の式の中の呼び出しでも受け渡し
  が壊れない）。呼び出しは `jal ra`、戻りは
  `jalr zero, ra, 0`。呼び出しは式の材料であり、結果
  は `a0` から `t1` へ移して式の値とする。
  関数は入口で戻り先 `ra` と呼び出し側の `fp` を
  フレームに退避し（`sd`）、引数を `a0`〜`a3` から
  自分の引数の枠へ写す。出口で戻す（`ld`）ので、関数
  が関数を呼んでも、再帰でも戻り先と局所変数が
  失われない（フレームは呼び出しごとに独立、v21）。
  スタックはコンパイラが「コード＋文字列の後ろ 4KB
  先」に天井を置いて用意する（起動直後の `sp` は
  保証されないため。材料は auipc 相対）。関数の実体は
  プログラムの実行部の後ろ（`wfi` の後）に並べ、呼び出し
  の飛び先は生成の最後に書き直して確定させる。
  型（`void` / `char` / `int`、`const`、`*`）は構文として
  読むが意味は持たない（値は全部64ビットの数）。ただし
  宣言からは「基本の大きさ」（char=1、それ以外=8）と
  ポインタ段数だけを覚える（v21。ポインタ添字の
  歩幅に使う）。変数のスコープは関数単位（v21）。
- デバイスへのアクセス（v6 から）: デバイスのレジスタは
  「決まった住所のメモリ」として読み書きする（MMIO）。
  `*数値` は絶対アドレス読み、`*先 = 式;` はメモリへの
  書き込み文。住所や大きな数の材料は auipc 相対で作る
  （RAM の住所でも 0x1000xxxx のデバイス住所でも同じ
  作り方で壊れない）。16進数リテラルはアドレス用に
  32ビットまで許し、10進数の項は従来どおり 2047 まで。
  優先順位は v7 で C に合わせた（下記）。iwac の生成
  コードはメモリ読みを省略しないので、C の volatile に
  相当する指定は今は要らない。
- 式の優先順位と評価（v7 から、v19 で完成）: 優先順位は
  C と同じ（固い順に: 材料、後置 `++` `--`、単項と
  ポインタ読み、`*` `/` `%`、`+` `-`、`<<` `>>`、
  `<` `>` `<=` `>=`、`==` `!=`、`&`、`^`、`|`、`&&`、
  `||`）。parse は段ごとの関数に分かれる。
  評価は「結果は t1」方式のままだが、右の子が葉でない
  二項演算では左の結果をスタックへ退避して右を計算する
  一般形にした。スタックの要否は AST を歩いて生成前に
  判定し、要るプログラムだけ sp を用意する（従来の
  プログラムの出力は不変）。掛け算・割り算・剰余は
  M 拡張の mul / div / rem を使う（ターゲット RV64G の
  決定に従う）。除数が 0 の場合の結果は、割り算は -1、
  剰余は被除数（RISC-V の仕様どおり）。シフトは sll と
  sra（`>>` は算術シフトで符号が保たれる）。`&&` `||`
  は二項演算でなく短絡評価で生成する: 左を分岐で判定
  して右を飛ばし、結果を 1 か 0 に直す（左の値の退避は
  要らない）。`!` は sltiu、`-x` は 0 からの引き算。
  `++` `--` の相手は変数だけで、前置は増減後の値、
  後置は増減前の値が式の値になる。
- 条件分岐（v8 から）: `if` / `else`。AST では条件・
  then 本体・else 本体（node_val の場所に置く）を1つの
  ノードに持つ。生成は「条件が 0 なら beq で else（か
  末尾）へ、then 本体の末尾で jal で else を飛び越える」
  という while と同じ飛び先の書き直しで作る。本体は
  `{ }` 必須。else の中身は `{ }` の塊か文1つで、
  `else if` は文1つの応用として自然に動く。
- 制御構文（v20 から）: `for` は while への読み替え
  （初期化は前に1回、更新は本体の最後に専用ノードで
  包んで繋ぐ）。`break` / `continue` / 値なし `return`
  の飛び先は、生成時に分からないので、仮の jal を
  置いて命令番号のリスト（patch_next で繋ぐ）に積み、
  ループや関数の生成の最後にまとめて書き直す。
  リストはループの深さごとに持ち、入れ子でも内側の
  ループだけに効く。continue の飛び先は、while では
  条件判定、for では更新の頭（更新を飛ばすとループが
  終わらなくなるため）。使える場所（ループ内・関数内）
  は parse の時点で検査する。
- 変数の置き場所（v21 から）: 変数は全部メモリに住む
  （レジスタ割り当ては廃止）。グローバルは静的領域
  （文字列・配列の後ろに 8 バイトずつ）、ローカルと
  引数は関数のスタックフレームに置き、fp（フレーム
  ポインタ）相対で読み書きする。フレームは入口で
  「sp をフレーム長だけ引く、ra と旧 fp を退避する、
  fp を張る」という序文で作り、出口で対称に戻す。
  式の評価が sp を上下させるので、ローカルの住所は
  sp でなく fp から数えるのが肝。スコープは関数単位
  （ブロック単位は作らない）: 記号表は1つの表に
  持ち主（グローバルか関数番号）を記録し、参照は
  「自関数のローカル → グローバル」の順に解決する。
  宣言で作る変数は同名の外側を隠し、代入で作る
  変数は見えている変数への代入になる。宣言からは
  型の基本サイズ（char=1、それ以外=8）とポインタ
  段数だけを覚える（歩幅の計算は v23）。
  ファイル範囲の初期化子（v24）は定数だけを受け、
  コンパイル時に評価して静的領域の初期イメージ
  として埋める（実行コードは出ない）。
- セルフホスト（v16 から）: iwac.c 自身をコンパイル
  できるようにする階段を登る。iwac.c の実測で要不要を
  決める（構造体・switch・三項演算子・sizeof は不要）。
  検証の最終形は固定点: iwac が作る iwac と、それが
  作る iwac のバイト一致。
- iwac 本体の OS 版（v15 から）: iwac.c はホスト版と
  完全に同じソース。OS 版はリンクする相手だけを
  差し替える（kosaba/ の crt が入口と決め打ち argv を、
  shim が4つの外部関数の syscall 実装を提供）。
  「ホストへの依存は外注4関数だけ」という設計が、
  移植をこの形に収めた。
- 出力ターゲット（v14 から）: `--kosaba` で KosabaOS の
  ユーザープログラム用に切り替える。言語は同一で、
  変わるのは舞台の約束だけ（配置 0x40000000、ELF 形式、
  putc/exit はシステムコール、スタックは OS 任せ）。
  生成の分岐は gen_all と putc 文、書き出しの ELF
  ヘッダに閉じている。ターゲット指定が無ければ従来の
  ベアメタル出力と完全一致を保つ。
  ELF は v24 から PT_LOAD 2本: コード（0x40000000、
  読み＋実行）とデータ（0x40200000、読み＋書き）。
  静的データの住所はデータ領域を基点（data_base）に
  確定する。ベアメタルでは data_base は従来どおり
  コードの後ろで、出力の並びも変わらない。
- プロトタイプ（v24 から）: 関数は宣言だけを先に
  書ける。宣言の引数は型だけでもよく、名前は捨てる。
  定義は宣言の名簿の続きとして読む。呼ばれた印と
  本体の有無を記録し、定義の無い関数の呼び出しが
  残れば生成の入口でエラーにする（外部関数の解決は
  ソースの連結に委ねる）。
- #define（v13 から）と条件付きコンパイル（v18 から）:
  parse の前に挟む前処理で、行頭の `#define 名前
  置き換え` を単語単位で展開し、`#ifdef` / `#ifndef` /
  `#else` / `#endif` で範囲を選ぶ。文字列・コメント内は
  展開の対象外、展開結果は再走査しない、再定義はエラー。
  定義済みマクロとして `__IWAC__`（常時）と `__KOSABA__`
  （--kosaba 時）を用意する。対象外のままのもの:
  `#include`、引数付きマクロ、`#if`（式の評価）。
  iwac.c 自身は引き続きプリプロセッサ無しで書く。
- main（v12 から）: 名前が `main` の関数は入口になる。
  生成側は入口で main へ jal し、戻りで wfi に落ちる。
  main 自体は通常の関数と同一の生成で、特別な本体の
  扱いは無い。main の有無でプログラム形が切り替わり、
  混ぜ書きは parse の段階でエラーにする。
- 関係演算子（v11 から）: `<` `>` `<=` `>=` は専用の
  優先順位の段（add と eq の間）で読み、結果は 1 か 0。
  生成は slt（符号付き）が中心で、`>` は両辺の入替え、
  `<=` `>=` は反対の比較を xori 1 で反転して作る。
- 入力（v10 から）: プログラムはファイルからも読める。
  引数が `.c` で終わればファイル必須、それ以外は
  「開けるファイルがあればファイル、無ければ引数
  そのもの」。ソースの上限は約256KB（v25 で 64KB から
  拡大。実測の根拠は doc/selfhost.md の v25 実施結果）。空白は改行も含み、
  行コメント `//` が使える。iwac 自身がホストに頼る
  外部関数は write / open / read / close の4つだけで、
  ここが OS 上で動かす際の差し替え点になる。
- 配列（v9 から、v23 で完成）: 変数とは別に、メモリに
  置くデータ。領域は静的データの並び（文字列の後ろ、
  グローバルの前）に静的に確保し、住所は文字列と
  同じ2パスで確定させる（スタックの天井計算には
  配列の使用量も含める。静的データの基点 data_base
  はターゲット節を参照）。要素の大きさは宣言の型で決まる（char は
  1バイト、それ以外とポインタの配列は 8バイト）ので、
  読み書きは大きさで lbu / ld と sb / sd を切り替える。
  2次元配列（名前[i] は行の先頭アドレス、名前[i][j]
  が要素）と、ポインタの添字（p[i] = *(p + i × 指す
  先の大きさ)）も使える。要素の住所計算は読み書き
  共通の gen_elem_addr にまとめてある。配列名その
  ものの値は先頭アドレス（C の「配列はポインタに
  落ちる」規則と同じ）。宣言文自体は実行コードを
  出さない。スコープは無く、配列もプログラム全体で
  名前が一意（v26 でスコープとローカル配列を導入予定）。
  配列の個数（128）と総量（4MB）の上限は v25 で
  実測に合わせて広げた。

## 5. 言語の育て方

- 言語は、コンパイラの教科書の王道に近い順序で少しずつ育てる
  （詳細な順序は `doc/roadmap.md`）。
  数字 → 四則演算とかっこ → 複数の文 → 変数 → 制御構造 →
  関数 → ポインタ・配列・文字と文字列 → Cらしいプログラム形。
- 初期のステップではプログラム全体が「式」であり、その値が
  UART に出るバイトになる。これは学習用の割り切りで、
  最終形ではない。Cらしい形（`main` 関数、文、宣言）に
  移るステップで、出力の仕方も合わせて設計し直す
  （組み込みの出力関数を用意する案が有力。そのときに決める）。
- 対象外を固定して欲張らない: フルプリプロセッサ、float、
  構造体、最適化。これらは設計にも入れない。
  - ただし例外として、行内の特定文字列の置き換えだけの
    単純な `#define` は、将来の小さなステップとして
    やりたいものに挙がっている（`doc/roadmap.md` の
    「将来: 単純な #define」）。`#include` や引数付き
    マクロ、条件分岐は引き続き対象外。それまでの間は
    iwac 自身のソースでも `#define` を使わない。

## 6. iwac 自身の書き方

- 実装言語は C、ビルドは当面ホストの gcc
  (`gcc -std=c11 -Wall -Wextra -O2`)。
- 将来のセルフホスト（iwac で iwac をコンパイルする夢）に
  備え、自分のソースは「iwac が将来扱える範囲」に寄せ、
  GCC 拡張やプリプロセッサの機能に深く依存しない。
  例: v0 の数値読み取りは、ライブラリ変換関数を使わず
  数字を手で読む書き方にした。
- **プリプロセッサは使わない**（2026-11-01、ユーザーの指摘で
  明文化）: `#include` も `#define` も、iwac 自身のソースで
  使わない。「まだ作っていないものを使って作らない」ため。
  標準ライブラリから使うのは `write` だけで、その宣言は
  ヘッダに頼らず自分で書く。宣言はプリプロセッサではなく
  「外にある関数の形」の伝言であり、本体はリンク時に
  ホストのライブラリと繋がる。エラー処理も `fprintf` /
  `exit` に頼らず、戻り値で失敗を伝えて main が
  `write` で表示する形にした。
- ファイル構成: 当初は 1 ファイル (`iwac.c`)。v18 の後、
  本体が約3100行・120KBに育ったところで `src/` の7断片
  （01-head / 02-parse / 03-gen / 04-encode / 05-input /
  06-preproc / 07-main）に分割した。`#include` を使わない
  約束のため、組み立ては「番号順に連結して1つの翻訳単位」
  （build.sh が iwac_all.c を作る）。iwac 自身の複数
  ファイル入力（v17）でも同じ並びを渡せば同じ意味に
  なるので、セルフホストの形とも揃っている。断片は
  単独では完結しない（境界は節の区切りのまま）。

## 7. 検証の方針

- 各ステップに「見える成果」を置き、`test.sh` で再現可能な
  検証にして残す。
- ベアメタル実行の確認は、QEMU のシリアル出力をファイルに
  落として行う。OpenSBI の起動表示が混ざるので、「入力を
  変えると出力のどこがどう変わるか」の差分で確認するのが
  v0 で使った確実な方法。
- 「確認した範囲」と「まだ確認していない範囲」を
  `doc/progress.md` に分けて書く。

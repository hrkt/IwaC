## 2026-11-03: v27（セルフコンパイル）— 階段の12段目、セルフホスト達成

- **固定点を確認した**: ホスト（GCC）版 iwac が
  `src/0*.c` + `kosaba/kosaba_rt.c` をコンパイルした
  iwac2.elf と、KosabaOS（QEMU virt）上で iwac2 が
  同じ入力から作った iwac3.elf が、バイト単位で一致
  （3,076,094 バイト。digest の一致に加え、生成物を
  シリアル経由で回収して全バイト比較でも確認）。
  iwac3 が作る第2世代も同じ digest だった
- あわせて、自己コンパイルされた iwac2 が OS 上で
  hello.c → hello.elf → Hello, World! を通すことも
  確認（セルフホストの完了の定義を全部満たす）
- 足した部品: 組み込み `syscall3(番号, a0, a1, a2)`
  （KosabaOS 専用）、iwac の言語で書いたランタイム
  `kosaba/kosaba_rt.c`（write は fd=2 を putc へ、
  fd=1 を hello.elf への 8KB バッファ付き書き込み）、
  入口の `kosaba_flush` フック（main の後に同名関数
  を呼ぶ。rt の書き切り用）
- セルフコンパイルで実物の不具合が次々に出た
  （いずれも小さいプログラムでは出ないもの）:
  - 自分のソースが仕様外の要素への複合代入
    （`a[i] += x`）を使っていた → 通常の代入に書換え
  - 前処理が文字リテラルを守らず、`'"'` で文字列と
    誤認して後ろの指令が壊れていた → 文字リテラルも
    丸ごと守るよう修正
  - 条件分岐（beq）の ±4KB を超える関数で、飛び先が
    静かに巻き戻っていた → 届かない分岐を「反転 +
    jal」に伸ばす緩和を生成に追加（従来出力は不変）
  - 大きな定数が3か所で壊れていた: lui の符号拡張
    （→addiw + long 計算）、0x80000000 以上の16進数の
    auipc 代用（→0 埋めの gen_load_u32）、グローバル
    初期値の読み方（eval_const を式と同じに統一）
  - `*p` の読み書きが常に1バイトで、int* 経由の
    バイト数が切れてファイル読み込みが壊れた →
    指す先の型の大きさで読み書き
  - 値の表現が GCC 製と iwac 製で食い違い固定点が
    崩れた → 16進リテラルは parse で int の範囲に
    畳み、生成の判断は符号つきの値とマスクで統一
    （「出力は作ったコンパイラによらない」が原則）
- 検証の置き場: OS のファイル置き場の標準値（arena
  256KB / create 予約 32KB）では約3MB の生成物が
  入らないため、固定点の確認はスクラッチ OS で
  arena 8MB / 予約 4MB に広げて実施。OS 本体への
  反映は OS 側の判断として相談する
- test.sh に v27 の確認を追加（syscall3 の対象外
  エラーと ecall 化、前処理の文字リテラル、4KB 超の
  本体を持つ while / if、大きな定数、`*p` の幅、
  ホスト側セルフコンパイルの煙テスト）

## 2026-11-03: v19（演算子の完成）— 階段の4段目

- `<<` `>>`（>> は算術シフト sra）、`|` `^`、`%`、
  単項の `-` `!`、短絡評価の `&&` `||`、前置/後置の
  `++` `--` を実装。優先順位の段を C の全順序に再編
  （|| → && → | → ^ → & → ==/!= → 関係 → シフト →
  加減 → 乗除・剰余 → 単項 → 後置 → 材料）
- 新しい命令: sll / sra / or / xor / rem（第3層に
  R 形式の符号化を追加）。`!` は sltiu、`-x` は
  0 からの引き算、`&&` `||` は分岐で右を飛ばす
  短絡評価（結果は 1 か 0 に直す）
- ポインタ読みは単項の段へ移し、後置の上に置いた
  ので `*p++` が `*(p++)` と読める。`++` `--` は
  文の形（`i++;` `++i;`）と式の形の両対応、相手は
  変数だけ。単項マイナスで `x = -1;` も書ける
- 検証: 新演算子の実行確認（短絡で右の副作用が
  起きないことまで）、優先順位の読み、エラー形
  （数への ++）、従来プログラムのバイト一致。
  test.sh に v19 の確認を追加し、旧来の「&& は

## 2026-11-01: v3（ポインタと文字列）

- 実装したこと:
  - 文字列リテラル（エスケープは \n \t \\ \" の4種）。
    文字列テーブル（プール）に末尾 0 付きで溜め、バイナリの
    コードの後ろに出力する。文字列リテラルの値はその住所
  - `*変数` で指された先の1バイトを読む（NODE_DEREF、
    命令は lbu）。`*s + 1` のように式の材料にもなる
  - ポインタの前進は普通の式 `s = s + 1` で済む
    （ポインタは住所の入った変数にすぎない、が体験できた）
  - 文字列の住所は2パス生成で確定: 1回目の生成で命令数を
    数え、住所 = 配置先頭 + コード長 + プール内位置を決め、
    2回目で作り直す
- つまずきと学び（今回の核心）: 住所の材料を当初
  lui + addi にしたら、実行時に load fault
  （tval = 0xffffffff8020001c）になった。RV64 の lui は
  32ビットの結果を符号拡張するので、0x8020xxxx の住所は
  上位が 0xffffffff に化ける。QEMU の `-d int` 例外ログで
  特定し、auipc（PC 相対）+ addi に変えて解決した。
  KosabaOS の `-mcmodel=medany` が auipc 前提な理由と一致
- 検証:
  - v0〜v2 のプログラム7件は出力バイナリが従来と完全一致
  - QEMU 実行: `s="Hi"; *s`→H、`s="Hi"; s=s+1; *s`→i、
    `s="AB"; *s+1`→B、`s="A"; t="B"; *t`→B（2文字列）、
    `s="A\n"; s=s+1; *s`→改行バイト（エスケープ確認）
  - エラー系: 閉じていない文字列、知らないエスケープ、
    `*5`（* の相手が変数でない）、未代入の変数の * は
    全て終了コード1・出力0バイト
  - `./test.sh` に v3 の確認を追加して PASS（下記コミット時点）

## 2026-11-01: 構造整理 — 内部を3層に分離（AST／命令列／符号化）

- ユーザーの希望: 直接バイナリを出す方針は良い。その上で、
  バイナリを書く部分、アセンブラ的に機械語一歩手前にする

  分かりやすく分けておいてほしい
- やったこと（言語仕様は不変、内部の再構成のみ）:
  - 第1層 parse: ソース → AST（抽象構文木）。
    `65+1` は「`+` を根、左 65、右 1」の木。ノードは

    即値」の組の配列として持ち、アセンブリ文字列にはしない。
    この層はビット列を知らない

    ビット配置の知識はこの層だけが持つ（各命令の式に
    フィールド図のコメント付き）
  - main は parse → gen → write を順に呼ぶだけになった
- 検証:
  - gcc ビルド警告なし、プリプロセッサ行ゼロ
  - 正常系10ケース（`A`、`65`、`B`、`65+1`、`66-1`、
    `50+10+5`、`65 + 1`、`2000+2000`、`1-2-3`、`100-200`）

規則どおり左の型で測るため、sizeof(int16 + int)

## 2026-11-07: v37 構造体

構造体を入れた。レイアウトは C 互換
（アラインメントとパディングは gcc と一致を
確認）。ファイル範囲で struct タグ { ... } ;
と定義し、. と -> でメンバを読み書きする。
構造体の配列・ネスト・配列メンバ・ポインタ
越し・typedef struct・sizeof (型) を受ける。
置き場所は既存のスロット制の拡張で、構造体の

合流する。値渡し・構造体代入・初期化リスト・

受ける（typedef の C11 ルールと同じ理由）。

実装で学んだこと:
- iwac の標準プロファイルは静的データが
  4MB のデータ領域にあと約17KBしか余裕が
  無かった。構造体の名簿はタグ32個・メンバ
  合計160個に絞り、構造体番号の表は char に
  +1 符号化で詰めた（0 = 構造体でない）
- iwac の文法の割り切りを2つ踏んだ: 配列要素
  への複合代入 (+=) は無い、int16 のような
  幅つきの型名は自作のソース（gcc でも訳す）
  には書けない
- 02-parse.c が 138KB に育ち、断片プロファイル
  （1MB）のソースバッファに TU が収まらなく
  なった。文の並び・typedef・構造体定義・
  宣言文を新断片 02b-decl.c に分け、02-parse の
  実測ピークはノード 8,362 → 6,242 に戻った。
  断片プロファイルのデータは 996,128 バイトで
  1MB に収まる。ついでに decls.c の
  smem_names だけ [256][32] のまま残っていて
  分割ビルドで「配列の大きさが宣言ごとに
  違います」になった（寸法を絞るときは
  decls.c 側も一緒に直す）

## 2026-11-07: v35 幅のある整数型

MP3 デコーダのような「C で書かれたもの」を
iwac で動かすための土台として、型の語彙に
int16 / uint16 / int32 / uint32 / int64 /
uint64 を足した。型は etype というタグで
表す: 基本サイズ（1/2/4/8）＋ 符号なしの印
（+16）＋ 幅つきの印（+32）。値は常に
64ビットの正規形（符号つきは符号拡張、
符号なしはゼロ拡張）で保持し、load / store
は幅の命令（lh / lhu / lw / lwu、sh / sw）
で正規形を作る。式の型付けを gen の入口で
行い（type_node）、演算のあとに正規化
（emit_canon）を入れる。除算・剰余・
右シフト・比較は型の符号で命令を出し分ける
（divu / remu / srl、uint64 同士は符号なし
比較）。キャストは幅つきのときだけ本物に
なり（NODE_CAST）、従来のキャストは今まで
どおり読み捨てる。

既存の型は無傷: char と int / long は従来
どおり（iwac の int は 64ビットのまま、
unsigned int の再定義もしない）、既存
ソースの書き直しもしていない。C99 が
stdint で新しい名前を足したのと同じ道。
割り切り: 幅の違う符号つき×符号なしの
比較は、正規形の 64ビット符号付き比較で
代用する。

検証: スクラッチで回り込み・除算・剰余・
論理シフト・配列とポインタの幅アクセス・
キャスト・uint64 の比較まで確認。分割
コンパイルと一括のバイト一致（decls.c の
宣言順の追随が山場だった）も含め、
test.sh は 219 件 ok で PASS（従来 211 件
＋ v35 の 8 件）。固定点の物差しとなる
通常版 iwac2 の digest は len=144190
sum=0000000000860fc4 hash=2a0e500bc1bcd104。
副産物として、libdashi の ds_hex が負数で
崩れる件の根（符号付き専用だった除算と
シフト）は uint64 の本物化で消えた。

プロファイルの追随: 断片プロファイル
（build-frag.sh）は新しい並行表
（node_etype / var_etype）の分で容量置換の
出現回数を更新し、データ 981,752 バイト
（段6 時点から約 36KB 増、それでも 1MB
未満）。shirasu も同じ追随で 382,712
バイト。

同日、残りの仕事の順序も変更した: 言語
拡張を先行し typedef → 構造体 → Asari
別出し → ELF化の順（roadmap 参照）。
構造体のレイアウトは C 互換に決定。

## 2026-11-01: v3（ポインタと文字列）

- 実装したこと:
  - 文字列リテラル（エスケープは \n \t \\ \" の4種）。
    文字列テーブル（プール）に末尾 0 付きで溜め、バイナリの
    コードの後ろに出力する。文字列リテラルの値はその住所
  - `*変数` で指された先の1バイトを読む（NODE_DEREF、

  上位が 0xffffffff に化ける。QEMU の `-d int` 例外ログで
  特定し、auipc（PC 相対）+ addi に変えて解決した。
  KosabaOS の `-mcmodel=medany` が auipc 前提な理由と一致
- 検証:
  - v0〜v2 のプログラム7件は出力バイナリが従来と完全一致
  - QEMU 実行: `s="Hi"; *s`→H、`s="Hi"; s=s+1; *s`→i、

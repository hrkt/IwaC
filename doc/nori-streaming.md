# nori のストリーミング化 (設計メモ)

状態: 設計のみ (2026-11-23)。実装はこのメモを
土台に別途進める。v52 (peephole) のマージが
nori 断片プロファイルの 1MB 枠に引っかかった
ことが発端で、ユーザーが「ドカンと変える」
方を選んだ。

## 発端と実測

nori 断片プロファイル (nori/build-frag.sh) は
静的データ 1MB 未満が狙いで、v51 時点で
1,048,390 バイト (残り 186 バイト) まで
詰んでいた。v52 でコンパイラ自身のコードが
約 +1,895 命令育ち、リンクの実測が4プール
同時に上限を超えた:

- 名前プール: 実測 7,007 (上限 6,912)
- 再配置: 実測 7,724 件 (上限 7,552)
- コード合計: 実測 291,140 (上限 286,720)
- シンボル: 実測 611 (上限 608)

上限を引き直すと約 +25KB で枠に収まらない。
上限の詰め直しは v49・v50・v51 と毎回要って
おり、溜める設計そのものが限界という判断。

## 現状の構造 (なぜ太るか)

nori は全オブジェクトについて、コードを
code_pool に、文字列を str_pool に溜め、
再配置を全体の表 (rel_*、24 バイト/件) に
集めてから、配置済みコードを out_code
(share_buf と相乗り) にもう一式組み立てる。
ピーク時に常駐するもの:

- share_buf 286,720 (in_buf と out_code)
- code_pool 286,720
- 再配置表 7,552 件 × 24 バイト = 181,248
- str_pool 19,456、その他シンボル表など

入力 (= コンパイラ自身のコード) が育つと
全部のプールが連動して太る。ld / lld の
ような普通のリンカは、入力を mmap して
出力は書きながら作り、再配置はコピーの
途中でその場で埋める。溜めるのは主に
シンボル表だけである。

## 新しい構造 (2パス)

オブジェクトファイルを2回読む。ファイルは
argv で渡される実ファイルなので読み直せる
(open / read / close だけで足りる)。

### パスA (収集)

今の read_object から「溜める」部分だけを
外したもの:

- セクション走査、シンボル登録 (名前表・
  seq・esym の鏡)、edata、配列初期値の
  取り込み (ainit)、afix、.data 再配置に
  よる初期値の確定は、今までどおり全部やる
- .text は code_pool に写さない。
  obj_code_len だけ記録する。文字列も
  str_pool に写さず obj_str_len だけ記録
- .text の再配置は表に集めない。その代わり
  検証だけは全部やる (種類・相手の印・
  絶対アドレスの有無・「入口か関数の中に
  収まるオフセットか」)。検証に配置の値は
  要らない (収まるかどうかは sym_off と
  sym_size で判定できる)
- オブジェクトのファイル長を記録する
  (パスB で読み直したときに照合する)

### 配置 (layout)

今は配置と同時に out_code へ写しているが、
写すのをやめて位置決めだけにする
(sym_place / sym_addr / obj_str_final /
out_len の計算と、afix の ainit への書き
込み)。入力は大きさと登録順だけなので、
コードの実体は要らない。

### パスB (書きながら埋める)

write_elf の形を土台に、コード部分を
「読み直して、埋めて、書く」に替える:

- ヘッダは今までどおり out_byte で流す
- 入口の断片、次に関数を seq の順に。
  関数ごとに、そのオブジェクトを
  share_buf に読み直し (読み直しは
  オブジェクト単位でキャッシュする。
  seq は登録順 = オブジェクトごとに
  まとまっているので、読み直しは
  オブジェクト数程度で済む)、esym の
  鏡を作り直し、そのオブジェクトの
  .text 再配置を走査して in_buf の中で
  穴を埋め、関数のバイト列を write する
- 穴の最終位置は、入口ならオフセット
  そのまま、関数内なら sym_place[s] +
  (off - sym_off[s]) で直接出る。
  今の site_final の全シンボル走査は消える
- 文字列はオブジェクト順に、節を読み直して
  そのまま write する (並びは今の
  str_pool の中身と一致する)
- ainit とグローバルの初期値は今までどおり
  (ainit_buf から、初期値は計算して out64)

## 消える置き場・残る置き場

消える:

- code_pool (断片 286,720 / 標準 294,912)
- str_pool (断片 19,456 / 標準 131,072)
- 再配置表 rel_* (断片 181,248 /
  標準 16384 件 × 24 バイト)。パスB は
  走査しながらその場で埋めるので、
  再配置の置き場自体が要らなくなる

残る:

- share_buf: 最大のオブジェクトファイル
  1つ分。実測最大は 02-parse.eo の
  223,656 バイト → 断片 229,376
- 名前表まわり (断片: シンボル上限
  608 → 640 に引き直して約 43,520、
  名前プール 7,168)
- seq (10,752)、esym の鏡 (17,408、
  パスB でも作り直すので残る)
- ainit_buf (断片 128 のまま。配列の
  初期値は合併の判定に実体が要るので
  溜める方を残す。コードの大きさとは
  無関係に、初期値データの分だけ)

断片プロファイルの見積もり合計は
約 314KB。今の 1,048,390 バイトの
約 1/3 で、余裕は約 730KB。縛りは
「リンク全体のコード合計」から
「最大のオブジェクト1つの大きさ」に
移る (こちらははるかに育ちにくい)。

## 割り切りと注意

- エラーの原子性: 検証は全部パスA と
  配置で済むので、「出力を書き始めてから
  失敗」はファイルの読み直し失敗のとき
  だけになる。穴の場所の存在判定も
  パスA で行う (上記のとおり配置の値は
  要らない)
- パスB の穴埋めは失敗しない作りにする
  (場所はパスA で存在を確認済み、住所は
  配置で全て決まっている)。万一の
  ずれ検出として、書く位置が sym_place と
  一致するかを実行時に照合する
- 出力は今の nori とバイト単位で一致
  させる。それが受け入れの物差し
  (下記の検証)。配置の順序 (入口 →
  seq 順) と文字列の並び (オブジェクト順)
  を厳密に保つ
- nori の書き手の約束は今までどおり:
  iwac の言語の範囲で書き、外に頼るのは
  write / open / read / close の4つだけ

## 検証の物差し

1. 断片リンク (iwac の12断片 + rt) で
   旧 nori と新 nori の出力を cmp
2. test.sh の中で nori がリンクする
   もの全部 (セルフホストの固定点が
   最終判定になる)
3. nori/build-frag.sh を新しい置き場の
   構成に合わせて書き換え、断片データ量が
   1MB 枠に余裕を持って収まること
4. test.sh 全体 PASS

# v61 設計メモ: レジスタ変数の直接更新

## 背景

v60 の後で生成コードを読み直した。tau ループ
1 周は約 50 命令で、残りの内訳は:

- 帰納変数の更新 3 つ (di / soff / tau) が
  各 3 命令 (mv で t1 へ出し、addiw、mv で戻す)
- acc の加算が、左辺の読み出しと保持の往復で
  演算の周りに約 5 命令
- 基底アドレスの組み立てとスタック退避
  (約 7 命令、これは席不足が原因で今回の
  対象外。下の「対象外」参照)
- テーブル住所の auipc + addi 0 (実質 nop の
  mv が 1 個ずつ)

このメモは 1 番目と 2 番目 (と 4 番目の
小さい方) を扱う。

## 設計

### A. 文レベルの代入の直接更新

文レベルの代入 `v = v op x` で、v がレジスタ
割り付けされている変数なら、値を t1 経由に
せず、v のレジスタの中で直接演算する。

対象の形 (全部を満たすときだけ):
- 代入先 v: レジスタ割り付けあり、ポインタ
  でない、アドレスを取られていないことは
  問わない (相手が葉だけなら呼び出しが無い)
- 右辺は二項演算で、左辺がちょうど v 自身
- 相手 x は、即値 (addi/addiw の範囲) か、
  レジスタ割り付けされた変数
- v の型は、符号つき int32 (W 形式で正規形が
  保てる) か、幅なしの 64 ビット整数。
  それ以外の幅つき型は正規化をレジスタ内で
  できないので従来経路

効果: `di = di + 1` が 3 命令 → 1 命令
(addiw s7, s7, 1)。

### A2. 相手が式の形

`v = v op X` で X が式のときも、X を先に
t1 へ評価してから `op s_v, s_v, t1` とする。
従来は左辺 v を t1 へ読み、保持レジスタへ
写し、X を評価して、戻して演算し、v へ
書き戻す往復があった。

条件は A に加えて:
- X の部分木に、呼び出し・代入・増減・
  ストアが無いこと (X の評価中に v が
  変わらない保証。従来経路は v を先に
  読むので、X が v を変える式では意味が
  変わってしまうため)
- ポインタ演算でないこと (スケールが絡む)
- ビット演算 (and/or/xor) は、X の型も
  符号つき int32 のときだけ (v60 の正規化
  省略と同じ理由: 相手のパターンの上位が
  結果に漏れるため)

効果: `acc = acc + (表引き × 表引き)` の
周りの往復約 5 命令 → 演算 1 命令。

### 小さい方: 住所作りの addi 0

gen_load_addr は auipc の後に addi (下位
オフセット) を常に出すが、オフセットが 0 の
ときは実質 nop の mv になる。出さないように
する (意味は変わらない)。

### 対象外

- v_hist の基底 (構造体メンバ配列の住所) の
  毎周の組み立てと退避: 消すにはループ不変の
  基底を置く予備の s レジスタが要るが、
  synth_granule は 11 本を使い切っている。
  レジスタを増やす手 (生存区間の分割など) は
  別の大きな段として切り分ける
- 評価器の結果置き場 (常に t1) の見直し:
  A2 はその一番熱い形だけを拾う形にした

## 検証

- test.sh: 直接更新の形 (即値・変数・式、
  int32 と 64 ビット、対象外の型では従来
  経路のまま正しいこと) の機能テスト
- PERFSTG で ST44 を測り直し、nami の
  静的命令数も記録する

## 期待値

tau ループで 1 周あたり約 13 命令の削減
(更新 6 + acc 周り 5 + addi 0 が 2)。
段5 で -10〜-15%、合計で -5〜-10% の
見込み。

## 結果 (2026-11-24)

実装した。A (即値・レジスタ変数の相手) と
A2 (式の相手) の両方。対象の型は、符号つき
int32 に加えて 64 ビット幅 (幅なし・int64・
uint64) まで広げた (acc のような int64 の
蓄積が段5 の熱い所にあったため。符号なしの
割り算と右シフトは符号なし形式を使う)。

PERFSTG (ST44、icount、同一イメージ):
v60 → v61 で合計 -11.4%、段5 は -16.3%。
v58 から通算で合計 -22.5%、段5 -28.3%。
デコードの FNV は不変。nami 静的命令数
16,753 → 16,456。

途中の記録:
- 「小さい方: 住所作りの addi 0」は実装
  しなかった。auipc + addi の組は、peephole
  の後に bake_daddr が即値を埋めるための
  構造で、片方だけ消すと控えの仕組みが
  壊れるため
- 64 ビット幅を対象に含める判断は、壁時計
  方式の A/B では「+46M の悪化」と出たが、
  静的には対象関数の命令が減っていることと
  食い違い、icount で測り直したら段5 の
  -9.6% だった。壁時計方式の括弧は裏タスク
  の混入で、スロットやセッションの癖まで
  拾う。以後の比較は icount を主にする

IwaC プロジェクト

コンパイラの育て方 — v0 から v27 まで

IwaC（いわっく）は、C言語の小さなサブセットを自作するコンパイラです。 普通のコンパイラと違うのは、アセンブラを使わずに、いきなり実行できるバイナリ（機械語）を出すこと。 このページでは、赤ちゃんだった v0 が、少しずつ言葉を覚えて 「文字列を1文字ずつ表示する print loop」をコンパイルできるようになるまでの歩みを、 フェーズごとに図で説明します。

v0

まず「1文字」— 一番小さいバイナリ

目標：iwac が一番小さいバイナリを出して、それが実行できること。 プログラムは「1文字」か「0〜255 の数字」だけ。たとえば A と書くと、 実行したときに画面（UART）に A と出るバイナリができます。

プログラム A から生まれる、たった4つの命令

luiUART（文字の窓口）の住所 0x10000000 を用意する
addi出したい文字 A（番号で言うと 65）を用意する
sbその1バイトを UART の住所に書き込む → 送信される！
wfiやることが無いので止まる（駐車）

命令は1つ4バイトなので、バイナリは 4命令 × 4バイト = 16バイト。 コンピュータの言葉（機械語）は、この命令を数字の並びに直したものです。 iwac は最初から、この数字を自分で組み立てて書き出します。

QEMU で実行すると…（前の表示は起動時の挨拶）A ← この1文字が、作ったバイナリの仕事
生バイナリ機械語を自作 UART 出力16バイト

ここでの学び： 「プログラムを実行する」とは、CPU が命令の数字を1つずつ読んで従うこと。 そして文字を表示するとは、決まった住所に1バイト書くことでした（これを MMIO と言います）。

v1

「式」— 足し算・引き算を“実行時に”計算する

目標：65+1 のような式を書けるようにすること。 ここで大事な決め事をしました：コンパイラは答えを計算しない。 65+1 の答え 66（=文字 B）を出すのは、実行される側のプログラムの中の add（足し算）命令です。

# プログラム
65+1

# iwac が出す命令（実行時にこう動く）
t1 に 65 を入れる
t2 に 1 を入れる
t1 = t1 + t2      # ← 計算はこの add 命令が実行時にやる
t1 を UART に出す  # 66 = 'B'

この「計算は実行時にやる」を守ると、将来、入力が変わっても同じバイナリが正しく計算できます （コンパイラが先回りして答えを埋め込むのとは、決定的に違います）。

実行結果 B（65+1）　A（66-1）　A（50+10+5）

この頃のもう1つの前進：「読む」と「作る」を分けた

プログラムを全部読み終わってからバイナリを作り始めるようにしました。 おかげで、65+ のような書き間違いでは、変なバイナリが一切出ません （エラーで終了し、出力は空っぽ）。

add / sub 命令項は 0〜2047 エラーでは何も出さない

ここでの学び： 項（数字）の上限が 2047 なのは、addi 命令に埋め込める数が 「符号付き12ビット」だから。命令の都合が、言語の仕様に顔を出す瞬間です。

番外編

「まだ作っていないものを使わない」という約束

ある日、iwac 自身のソースコードに #include <stdio.h> と 書いてあるのが見つかりました。でも iwac の言語には、まだプリプロセッサ（#include の仕組み）が ありません。将来「iwac で iwac をコンパイルする（セルフホスト）」夢のためにも、 これは筋が通りません。

そこで、iwac 自身のソースからもプリプロセッサを全部無くしました。 外部の機能は write ひとつだけ、その「形の宣言」だけを自分で書く。 検証スクリプトには「# で始まる行があったら失敗」という見張りも入っています。

将来の小さな宿題： 行の中の決まった文字列を置き換えるだけの単純な #define は、 いつか小さなステップとして作る予定です（#include や複雑なマクロは対象外のまま）。
目標

ここから「print loop をコンパイルする」が目標に

v1 の後、次の目標が決まりました：KosabaOS の print loop をコンパイルできるようになること。 print loop とは、文字列を1文字ずつ送り出すループのことで、KosabaOS の uart_puts という関数がそれです：

void uart_puts(const char *s)
{
    while (*s != '\0') {
        uart_putc(*s);
        s++;
    }
}

短い関数ですが、この中には「変数」「文字列」「ポインタ」「繰り返し」「関数」と、 iwac にまだ無い部品が全部詰まっています。全部入りを一度にやらず、 v2 → v3 → v4 → v5 と1つずつ取りに行く計画にしました（式の掛け算・割り算など、 この目標に要らないものは後回しです）。

v2

「変数と代入」— 値を“持ち回る”

目標：プログラムが「文の並び」になり、変数に値を覚えさせられること。

x = 65;      # x に 65 を覚えさせる（文）
x + 1        # 最後の式 → 66 = 'B'

変数の実体は、CPU の中の引き出し（レジスタ）

t365変数 x の置き場所
t45変数 y の置き場所
t5—あき
t6—あき（変数は最大4個）

代入は「右側を計算して、変数の引き出しへ写すこと」。 変数を使うのは「引き出しから写して来ること」です。 変数の名前と引き出し番号の対応表（記号表）は、コンパイラが管理します。 まだ代入していない変数を使うとエラーになります。

実行結果 B（x=65; x+1）　A（x=60; y=5; x+y）　B（x=65; x=x+1; x ←再代入）

ここでの学び： 「変数」と大げさに言っても、中身は「値の置き場所に名前を付けたもの」。 この設計ではレジスタに住んでいるので、変数はまだメモリ上の住所を持ちません。

v3

「ポインタと文字列」— 住所でメモリを読む

目標：s = "Hi"; *s で H が出ること。

文字列は、バイナリの中でコードの後ろに置く

コード（命令の並び）実行される部分
文字列データ "Hi" + 0コードの後ろに並べる

文字列の「値」は、その先頭の住所です。住所はコードの長さが決まるまで分からないので、 コンパイラは生成を2回やります（1回目で命令の数を数え、住所を確定して作り直す「2パス生成」）。 文字列の最後には 0 を付ける約束（C言語と同じ）で、これが print loop の「終わり」の目印になります。

ポインタ s と、*s（指した先を読む）

H
i
0

↑ s はここを指している（住所が入った変数）。 *s は「指した先の1バイトを読む」こと（命令は lbu）。 s = s + 1 と書けば指す場所が次へ進み、*s は i になります。

実行結果 H（s="Hi"; *s）　i（s=s+1 してから *s）　B（s="AB"; *s+1）

今回の大きかったつまずき： 住所を lui という命令で作ったら、実行時に読み込み例外（load fault）になりました。 原因は、64ビットCPUの lui が結果を「符号拡張」してしまい、 0x8020001c のはずの住所が 0xffffffff8020001c に化けたこと。 例外ログで犯人を特定し、「今いる場所からの距離」で住所を作る auipc に変えて解決しました。 KosabaOS のCプログラムが同じ方式（medany）で作られている理由にも、ここで腑が落ちました。

v4

「while と putc」— print loop の本体が動いた！

目標：繰り返しと、ループの中からの出力ができること。 そして、これが目標の print loop の「本体そのもの」です：

s = "hello\n";
while (*s) {          # 指した先が 0 でない間、くり返す
    putc(*s);         # 今の1文字を出す（組み込みの出力文）
    s = s + 1;        # 次の文字へ進む
}
QEMU で実行すると…hello（＋改行） ← print loop が動いた！

while は、命令の世界では「飛ぶ」ことでできている

① 条件を確かめる：*s を読んで値を見る
↓ 0 でなければ続ける ／ 0 なら beq（分岐）で ④ へ飛ぶ
② 本体：putc(*s); s = s + 1; を実行する
↓ jal（ジャンプ）で ① へ戻る
① に戻って、また条件を確かめる（以下くり返し）
↓ *s が 0 （文字列の終わり）になったら
④ ループを抜けて止まる

コンパイラの命令列の中では、飛び先は「命令の番号」で表します。 ビット列に変換する段で、RISC-V の分岐命令の流儀である「今の命令からの距離」に直します。 本体を全部出してからでないと「抜けた先」の番号が分からないので、 分岐の飛び先は後から書き直して確定させます（アセンブラのラベルと同じ発想です）。

他の実行結果 Hi（putc を2回）　AAA（3回数えるループ）　BBBB（ループの入れ子）
beq（B形式）jal（J形式） 文も AST の仲間に入れ子のループ

ここでの学び： 「繰り返し」という高級な概念も、CPU の世界では「条件を見て、飛ぶか飛ばないか」だけ。 プログラムカウンタ（次に実行する命令の住所）を前後に動かすことが、制御の流れの正体でした。

v5

「関数」— uart_puts が本物の形で動いた！

目標：関数定義・引数・呼び出しができるようになり、目標の関数そのものを書くこと。

void uart_puts(char *s) {
    while (*s != 0) { putc(*s); s = s + 1; }
}
msg = "hello\n";
uart_puts(msg);
QEMU で実行すると…hello（＋改行） ← 関数になった print loop！

関数の「約束事」（呼び出し規約）を決める

a0引数はこのレジスタに入れて渡す。関数は入ってすぐ、自分の変数へ写す
jal ra呼び出し：戻り先の住所を ra に残して、関数へ飛ぶ
sd / ld関数は入るときに ra をスタックへ退避し、出るときに戻す。これで「関数が関数を呼ぶ」入れ子でも戻り先が消えない
jalr戻り：ra の指す場所へ飛んで帰る

スタック（退避用の積み場所）は、起動直後は用意されていないので、 コンパイラがバイナリの後ろの空き地に自分で作ります。 型（void や char *）は今は「形だけ読んで意味は持たない」扱いで、 値は全部ただの数として扱っています。

呼び出しの流れを、1回分だけ追ってみよう

呼ぶ側：引数を a0 に入れる（例：文字列の住所）
↓ jal ra — 「次の命令の住所」を ra にメモして、関数へ飛ぶ
関数：入ってすぐ ra をスタックへ退避し、a0 から引数を受け取る
↓ 本体を実行する（この間、別の関数を呼んでもよい）
関数：ra をスタックから戻す
↓ jalr — ra の指す場所へ飛んで帰る
呼ぶ側：飛ぶ前にメモした場所から、続きを実行する

ポイントは、jal が「ただ飛ぶ」のではなく 「帰り道をメモしてから飛ぶ」命令だということです。 関数の本体そのものは、プログラムの実行部分の後ろ（止まる命令 wfi の後）に 並べて置くので、上から実行してうっかり関数の中に落ちてくることはありません：

実行部（呼び出し側）上から実行される
wfiここで止まる
関数の本体呼ばれたときだけ入る
文字列データ

なぜ ra の退避が要るのか — 入れ子の呼び出し

関数 wrap が、中で別の関数 out2 を呼ぶ場面を考えます。 out2 を呼ぶ jal は、ra を 「wrap の中へ戻る住所」で上書きします。 もし wrap が自分の ra（呼び出し元へ戻る住所）を どこかに退避していなければ、out2 から戻ったあと、 wrap は自分の帰り道を失います。 そこで関数は入ってすぐ、自分の ra をスタックに積みます：

out2 の番（実行中）
使う ra ＝ wrap の中へ戻る住所
wrap の退避分（スタックに積んである）
守られている ra ＝ 呼び出し元へ戻る住所
スタックの土台（コンパイラが用意した空き地）

呼び出しが深くなるほど、退避分が下へ積み重なっていく（だから「スタック＝積み重ね」）

確かめとして、wrap が out2 を呼ぶプログラムを実行すると ちゃんと XX と出て戻って来ます。退避をやめると戻り先が壊れる——というのが、 この仕組みの存在理由です。

ついでに「比較」も：!= と ==

本物の条件 *s != 0 を書くために比較も入れました。 作り方は「引き算して、差が 0 かどうかを見る」。 比較の結果は、成り立てば 1、だめなら 0 の数になります。 たとえば *s != 0 なら：

文字が H（72）のとき： 72 − 0 ＝ 72 → 0 ではない → 結果は 1 → ループは続く
↓ 次の文字へ…をくり返し、文字列の終わり（0）に来たら
文字が 0 のとき： 0 − 0 ＝ 0 → 結果は 0 → ループは終わる
他の実行結果 AB（関数を2回呼ぶ）　XX（関数が関数を呼ぶ）　ABCD（2つの文字列を続けて）　AAA（!= のループ）
呼び出し規約スタックと ra 退避 比較 == / !=型は読み捨て

ここでの学び： 関数とは「飛んで行って、帰って来る」仕組み。そのためには 戻り先を忘れない工夫が要り、入れ子になるほどスタックへの退避が効いてきます。 世の中の「呼び出し規約」は、この約束事を標準化したものです。

v6

uart_putc の本体 — デバイスに触る

目標：最後の組み込みだった putc をやめて、送信待ち（ポーリング）付きの本物の uart_putc を書くこと。

void uart_putc(char c) {
    while (*0x10000005 & 32 == 0) { }   # 状態の窓口を見て、空くまで待つ
    *0x10000000 = c;                   # 送信の窓口へ書く = 送られる
}
uart_puts と組み合わせて QEMU で実行すると…hello（＋改行） ← ポーリング付きの本物で！

デバイスは「決まった住所のメモリ」

UART の窓口は、住所で読み書きする相手です（この仕組みを MMIO と言います）。 v6 で入れたのは、そのための部品です：

*0x10000005絶対アドレス読み：状態レジスタ LSR を読む。* の相手に数を書けるようにした
& 32ビット演算：状態のうち「送信窓口が空いた」の合図ビット（32 = 0x20）だけを取り出す
*0x10000000 = c;メモリ書き込み文：送信レジスタ THR へ書くと、その文字が送られる
0x…16進数：アドレスはこの書き方が自然なので、数として書けるようにした

ポーリングの流れ

LSR（0x10000005）を読む
↓ & 32 — 合図ビットだけを見る
まだ 0（窓口が忙しい）なら、本体の無い while でその場で待つ
↑ くり返し読み直す（合図が立つまで）
32 が立ったら抜けて、THR（0x10000000）へ文字を書く → 送信！

当時の小さな決め事：この時点では式のかっこが無かったので、 & は比較（==）より先に計算することにしていました（本物の C とは逆）。 おかげで *0x10000005 & 32 == 0 と、かっこ無しでポーリングの形が書けました。 —— この暫定ルールは、次の v7 で C の順に戻しました。 なお QEMU の送信は一瞬で終わるので、「待つ」ところが本当に効くのは実機です。

MMIOポーリング ビット演算 &16進数

・ポインタの読み書きが1バイトだけ：昔の「ポインタは文字を指す もの」という前提のまま、*p が常に1バイトしか読み書き していませんでした。ファイルの読み込みバイト数（int へのポインタ 経由）が下1バイトに切れて、読み込みが壊れます。指す先の型の 大きさで読み書きするよう直しました。
・前処理が文字リテラルに弱い：'"'（ダブルクォート という文字）を見て「文字列が始まった」と誤認し、後ろの #define 行が読めなくなっていました。
・作った人で答えが違う：いちばん固定点らしい問題です。iwac の 型は全部64ビット幅でキャストは読み捨て、という割り切りのため、 「32ビットに切り詰めたはずの値」が、GCC で作った iwac の中では 負の数、iwac で作った iwac の中では正の大きな数、という違う姿に なっていました。値のしまい方と読み方に約束を決め、 「出力は、作ったコンパイラによらない」ようにそろえました。

全部直した結果、ホスト版が作った iwac2.elf（3,076,094 バイト）と、 OS の上で iwac2 が作った iwac3.elf がバイト単位で一致しました。 iwac3 が作る次の世代も同じでした。ついでに、自己コンパイルされた iwac2 が OS の上で Hello World をコンパイルして実行できるところまで 確かめました。v16 から登ってきた階段は、これで完走です。

ここでの学び： セルフホストは「究極のテスト」でした。小さいテストでは一生出会わない 不具合が、自分のソースという「大きくて本物の入力」で次々と見つかります。 そして固定点（作る側が変わっても出力が変わらないこと）は、 コンパイラの正しさがいちばん厳しく問われる形です。

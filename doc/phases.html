IwaC プロジェクト

コンパイラの育て方 — v0 から v19 まで

IwaC（いわっく）は、C言語の小さなサブセットを自作するコンパイラです。 普通のコンパイラと違うのは、アセンブラを使わずに、いきなり実行できるバイナリ（機械語）を出すこと。 このページでは、赤ちゃんだった v0 が、少しずつ言葉を覚えて 「文字列を1文字ずつ表示する print loop」をコンパイルできるようになるまでの歩みを、 フェーズごとに図で説明します。

まず全体像：コンパイラって何をするもの？

人間の書いたプログラムを、コンピュータが直接実行できる「機械語」に翻訳する道具です。

舞台の約束：作られたバイナリは、QEMU という「コンピュータを真似るソフト」の中の RISC-V という種類のCPUで動きます。置き場所はメモリの 0x80200000 番地、 出力先は UART（文字を1バイトずつ外に送る窓口）。この舞台は自作OS「KosabaOS」と同じで、 最終目標は「KosabaOS の上で iwac が Hello World をコンパイルすること」です。

v0

まず「1文字」— 一番小さいバイナリ

目標：iwac が一番小さいバイナリを出して、それが実行できること。 プログラムは「1文字」か「0〜255 の数字」だけ。たとえば A と書くと、 実行したときに画面（UART）に A と出るバイナリができます。

プログラム A から生まれる、たった4つの命令

luiUART（文字の窓口）の住所 0x10000000 を用意する
addi出したい文字 A（番号で言うと 65）を用意する
sbその1バイトを UART の住所に書き込む → 送信される！
wfiやることが無いので止まる（駐車）

命令は1つ4バイトなので、バイナリは 4命令 × 4バイト = 16バイト。 コンピュータの言葉（機械語）は、この命令を数字の並びに直したものです。 iwac は最初から、この数字を自分で組み立てて書き出します。

QEMU で実行すると…（前の表示は起動時の挨拶）A ← この1文字が、作ったバイナリの仕事
生バイナリ機械語を自作 UART 出力16バイト

ここでの学び： 「プログラムを実行する」とは、CPU が命令の数字を1つずつ読んで従うこと。 そして文字を表示するとは、決まった住所に1バイト書くことでした（これを MMIO と言います）。

v1

「式」— 足し算・引き算を“実行時に”計算する

目標：65+1 のような式を書けるようにすること。 ここで大事な決め事をしました：コンパイラは答えを計算しない。 65+1 の答え 66（=文字 B）を出すのは、実行される側のプログラムの中の add（足し算）命令です。

# プログラム
65+1

# iwac が出す命令（実行時にこう動く）
t1 に 65 を入れる
t2 に 1 を入れる
t1 = t1 + t2      # ← 計算はこの add 命令が実行時にやる
t1 を UART に出す  # 66 = 'B'

この「計算は実行時にやる」を守ると、将来、入力が変わっても同じバイナリが正しく計算できます （コンパイラが先回りして答えを埋め込むのとは、決定的に違います）。

実行結果 B（65+1）　A（66-1）　A（50+10+5）

この頃のもう1つの前進：「読む」と「作る」を分けた

プログラムを全部読み終わってからバイナリを作り始めるようにしました。 おかげで、65+ のような書き間違いでは、変なバイナリが一切出ません （エラーで終了し、出力は空っぽ）。

add / sub 命令項は 0〜2047 エラーでは何も出さない

ここでの学び： 項（数字）の上限が 2047 なのは、addi 命令に埋め込める数が 「符号付き12ビット」だから。命令の都合が、言語の仕様に顔を出す瞬間です。

構造整理

中身を3つの層に分ける（v1 の直後）

直接バイナリを出す方針はそのままに、コンパイラの中身を3つの層にはっきり分けました。 言語の仕様は変えていないので、合言葉は「出力が前と1バイトも違わないこと」。

AST（抽象構文木）とは？ — 65+1 の「意味の木」

+
／　＼
651

プログラムの意味は「並び」ではなく「木」で考えるのが自然です。 この木があるから、後のフェーズで「繰り返しの中に文が入る」のような入れ子も扱えます。 なお AST の置き場所には、構造体やポインタではなく「番号で繋いだ配列」を使いました （理由は下の番外編と同じです）。

ここでの学び： 第2層の「命令列」は、アセンブリの文字列ではなく、データとして持ちます （命令の種類・レジスタ番号・即値の組）。「どんな命令を出すか」と 「命令をどういうビット列にするか」を、別々の問題として考えられるようになりました。

番外編

「まだ作っていないものを使わない」という約束

ある日、iwac 自身のソースコードに #include <stdio.h> と 書いてあるのが見つかりました。でも iwac の言語には、まだプリプロセッサ（#include の仕組み）が ありません。将来「iwac で iwac をコンパイルする（セルフホスト）」夢のためにも、 これは筋が通りません。

そこで、iwac 自身のソースからもプリプロセッサを全部無くしました。 外部の機能は write ひとつだけ、その「形の宣言」だけを自分で書く。 検証スクリプトには「# で始まる行があったら失敗」という見張りも入っています。

将来の小さな宿題： 行の中の決まった文字列を置き換えるだけの単純な #define は、 いつか小さなステップとして作る予定です（#include や複雑なマクロは対象外のまま）。
目標

ここから「print loop をコンパイルする」が目標に

v1 の後、次の目標が決まりました：KosabaOS の print loop をコンパイルできるようになること。 print loop とは、文字列を1文字ずつ送り出すループのことで、KosabaOS の uart_puts という関数がそれです：

void uart_puts(const char *s)
{
    while (*s != '\0') {
        uart_putc(*s);
        s++;
    }
}

短い関数ですが、この中には「変数」「文字列」「ポインタ」「繰り返し」「関数」と、 iwac にまだ無い部品が全部詰まっています。全部入りを一度にやらず、 v2 → v3 → v4 → v5 と1つずつ取りに行く計画にしました（式の掛け算・割り算など、 この目標に要らないものは後回しです）。

v2

「変数と代入」— 値を“持ち回る”

目標：プログラムが「文の並び」になり、変数に値を覚えさせられること。

x = 65;      # x に 65 を覚えさせる（文）
x + 1        # 最後の式 → 66 = 'B'

変数の実体は、CPU の中の引き出し（レジスタ）

t365変数 x の置き場所
t45変数 y の置き場所
t5—あき
t6—あき（変数は最大4個）

代入は「右側を計算して、変数の引き出しへ写すこと」。 変数を使うのは「引き出しから写して来ること」です。 変数の名前と引き出し番号の対応表（記号表）は、コンパイラが管理します。 まだ代入していない変数を使うとエラーになります。

実行結果 B（x=65; x+1）　A（x=60; y=5; x+y）　B（x=65; x=x+1; x ←再代入）

ここでの学び： 「変数」と大げさに言っても、中身は「値の置き場所に名前を付けたもの」。 この設計ではレジスタに住んでいるので、変数はまだメモリ上の住所を持ちません。

v3

「ポインタと文字列」— 住所でメモリを読む

目標：s = "Hi"; *s で H が出ること。

文字列は、バイナリの中でコードの後ろに置く

コード（命令の並び）実行される部分
文字列データ "Hi" + 0コードの後ろに並べる

文字列の「値」は、その先頭の住所です。住所はコードの長さが決まるまで分からないので、 コンパイラは生成を2回やります（1回目で命令の数を数え、住所を確定して作り直す「2パス生成」）。 文字列の最後には 0 を付ける約束（C言語と同じ）で、これが print loop の「終わり」の目印になります。

ポインタ s と、*s（指した先を読む）

H
i
0

↑ s はここを指している（住所が入った変数）。 *s は「指した先の1バイトを読む」こと（命令は lbu）。 s = s + 1 と書けば指す場所が次へ進み、*s は i になります。

実行結果 H（s="Hi"; *s）　i（s=s+1 してから *s）　B（s="AB"; *s+1）

今回の大きかったつまずき： 住所を lui という命令で作ったら、実行時に読み込み例外（load fault）になりました。 原因は、64ビットCPUの lui が結果を「符号拡張」してしまい、 0x8020001c のはずの住所が 0xffffffff8020001c に化けたこと。 例外ログで犯人を特定し、「今いる場所からの距離」で住所を作る auipc に変えて解決しました。 KosabaOS のCプログラムが同じ方式（medany）で作られている理由にも、ここで腑が落ちました。

文字列リテラルlbu 命令 2パス生成auipc（PC相対）
v4

「while と putc」— print loop の本体が動いた！

目標：繰り返しと、ループの中からの出力ができること。 そして、これが目標の print loop の「本体そのもの」です：

s = "hello\n";
while (*s) {          # 指した先が 0 でない間、くり返す
    putc(*s);         # 今の1文字を出す（組み込みの出力文）
    s = s + 1;        # 次の文字へ進む
}
QEMU で実行すると…hello（＋改行） ← print loop が動いた！

while は、命令の世界では「飛ぶ」ことでできている

① 条件を確かめる：*s を読んで値を見る
↓ 0 でなければ続ける ／ 0 なら beq（分岐）で ④ へ飛ぶ
② 本体：putc(*s); s = s + 1; を実行する
↓ jal（ジャンプ）で ① へ戻る
① に戻って、また条件を確かめる（以下くり返し）
↓ *s が 0 （文字列の終わり）になったら
④ ループを抜けて止まる

コンパイラの命令列の中では、飛び先は「命令の番号」で表します。 ビット列に変換する段で、RISC-V の分岐命令の流儀である「今の命令からの距離」に直します。 本体を全部出してからでないと「抜けた先」の番号が分からないので、 分岐の飛び先は後から書き直して確定させます（アセンブラのラベルと同じ発想です）。

他の実行結果 Hi（putc を2回）　AAA（3回数えるループ）　BBBB（ループの入れ子）
beq（B形式）jal（J形式） 文も AST の仲間に入れ子のループ

ここでの学び： 「繰り返し」という高級な概念も、CPU の世界では「条件を見て、飛ぶか飛ばないか」だけ。 プログラムカウンタ（次に実行する命令の住所）を前後に動かすことが、制御の流れの正体でした。

v5

「関数」— uart_puts が本物の形で動いた！

目標：関数定義・引数・呼び出しができるようになり、目標の関数そのものを書くこと。

void uart_puts(char *s) {
    while (*s != 0) { putc(*s); s = s + 1; }
}
msg = "hello\n";
uart_puts(msg);
QEMU で実行すると…hello（＋改行） ← 関数になった print loop！

関数の「約束事」（呼び出し規約）を決める

a0引数はこのレジスタに入れて渡す。関数は入ってすぐ、自分の変数へ写す
jal ra呼び出し：戻り先の住所を ra に残して、関数へ飛ぶ
sd / ld関数は入るときに ra をスタックへ退避し、出るときに戻す。これで「関数が関数を呼ぶ」入れ子でも戻り先が消えない
jalr戻り：ra の指す場所へ飛んで帰る

スタック（退避用の積み場所）は、起動直後は用意されていないので、 コンパイラがバイナリの後ろの空き地に自分で作ります。 型（void や char *）は今は「形だけ読んで意味は持たない」扱いで、 値は全部ただの数として扱っています。

呼び出しの流れを、1回分だけ追ってみよう

呼ぶ側：引数を a0 に入れる（例：文字列の住所）
↓ jal ra — 「次の命令の住所」を ra にメモして、関数へ飛ぶ
関数：入ってすぐ ra をスタックへ退避し、a0 から引数を受け取る
↓ 本体を実行する（この間、別の関数を呼んでもよい）
関数：ra をスタックから戻す
↓ jalr — ra の指す場所へ飛んで帰る
呼ぶ側：飛ぶ前にメモした場所から、続きを実行する

ポイントは、jal が「ただ飛ぶ」のではなく 「帰り道をメモしてから飛ぶ」命令だということです。 関数の本体そのものは、プログラムの実行部分の後ろ（止まる命令 wfi の後）に 並べて置くので、上から実行してうっかり関数の中に落ちてくることはありません：

実行部（呼び出し側）上から実行される
wfiここで止まる
関数の本体呼ばれたときだけ入る
文字列データ

なぜ ra の退避が要るのか — 入れ子の呼び出し

関数 wrap が、中で別の関数 out2 を呼ぶ場面を考えます。 out2 を呼ぶ jal は、ra を 「wrap の中へ戻る住所」で上書きします。 もし wrap が自分の ra（呼び出し元へ戻る住所）を どこかに退避していなければ、out2 から戻ったあと、 wrap は自分の帰り道を失います。 そこで関数は入ってすぐ、自分の ra をスタックに積みます：

out2 の番（実行中）
使う ra ＝ wrap の中へ戻る住所
wrap の退避分（スタックに積んである）
守られている ra ＝ 呼び出し元へ戻る住所
スタックの土台（コンパイラが用意した空き地）

呼び出しが深くなるほど、退避分が下へ積み重なっていく（だから「スタック＝積み重ね」）

確かめとして、wrap が out2 を呼ぶプログラムを実行すると ちゃんと XX と出て戻って来ます。退避をやめると戻り先が壊れる——というのが、 この仕組みの存在理由です。

ついでに「比較」も：!= と ==

本物の条件 *s != 0 を書くために比較も入れました。 作り方は「引き算して、差が 0 かどうかを見る」。 比較の結果は、成り立てば 1、だめなら 0 の数になります。 たとえば *s != 0 なら：

文字が H（72）のとき： 72 − 0 ＝ 72 → 0 ではない → 結果は 1 → ループは続く
↓ 次の文字へ…をくり返し、文字列の終わり（0）に来たら
文字が 0 のとき： 0 − 0 ＝ 0 → 結果は 0 → ループは終わる
他の実行結果 AB（関数を2回呼ぶ）　XX（関数が関数を呼ぶ）　ABCD（2つの文字列を続けて）　AAA（!= のループ）
呼び出し規約スタックと ra 退避 比較 == / !=型は読み捨て

ここでの学び： 関数とは「飛んで行って、帰って来る」仕組み。そのためには 戻り先を忘れない工夫が要り、入れ子になるほどスタックへの退避が効いてきます。 世の中の「呼び出し規約」は、この約束事を標準化したものです。

v6

uart_putc の本体 — デバイスに触る

目標：最後の組み込みだった putc をやめて、送信待ち（ポーリング）付きの本物の uart_putc を書くこと。

void uart_putc(char c) {
    while (*0x10000005 & 32 == 0) { }   # 状態の窓口を見て、空くまで待つ
    *0x10000000 = c;                   # 送信の窓口へ書く = 送られる
}
uart_puts と組み合わせて QEMU で実行すると…hello（＋改行） ← ポーリング付きの本物で！

デバイスは「決まった住所のメモリ」

UART の窓口は、住所で読み書きする相手です（この仕組みを MMIO と言います）。 v6 で入れたのは、そのための部品です：

*0x10000005絶対アドレス読み：状態レジスタ LSR を読む。* の相手に数を書けるようにした
& 32ビット演算：状態のうち「送信窓口が空いた」の合図ビット（32 = 0x20）だけを取り出す
*0x10000000 = c;メモリ書き込み文：送信レジスタ THR へ書くと、その文字が送られる
0x…16進数：アドレスはこの書き方が自然なので、数として書けるようにした

ポーリングの流れ

LSR（0x10000005）を読む
↓ & 32 — 合図ビットだけを見る
まだ 0（窓口が忙しい）なら、本体の無い while でその場で待つ
↑ くり返し読み直す（合図が立つまで）
32 が立ったら抜けて、THR（0x10000000）へ文字を書く → 送信！

当時の小さな決め事：この時点では式のかっこが無かったので、 & は比較（==）より先に計算することにしていました（本物の C とは逆）。 おかげで *0x10000005 & 32 == 0 と、かっこ無しでポーリングの形が書けました。 —— この暫定ルールは、次の v7 で C の順に戻しました。 なお QEMU の送信は一瞬で終わるので、「待つ」ところが本当に効くのは実機です。

MMIOポーリング ビット演算 &16進数

ここでの学び： デバイスドライバの正体は「決まった住所の読み書きと、合図を待つループ」。 v3 のポインタ読みが、ここでデバイス相手にもそのまま使えました。 これで print loop は、端から端まで iwac で書いたコードになりました。

その先には、OSの側の成長（ユーザーモード、ファイル、シェル）と合流して、 「KosabaOS のシェルから iwac で Hello World をコンパイルして実行する」 という最終目標が待っています。

v7

演算子の優先順位を、C と同じに

目標：「どの演算子から計算するか」の順番を C と同じにして、C の読み方で式が読めるようにすること。

v6 では、かっこが無い代わりに & と比較の順を C と逆にしていました。 でも優先順位は、プログラムの意味そのものを決める大事な決まりです。 そこで先に進む前に、かっこと掛け算・割り算ごと、C の順に揃え直しました。

優先順位の階段（上が先に計算される）

* 読み・( )ポインタ読みとかっこ。一番固い
* /掛け算・割り算
+ -足し算・引き算
== !=比較
&ビット演算。一番ゆるい（C と同じ）
読み方の例 60 + 2 * 3 → 掛け算が先で 66（B）　 2 * (30 + 3) → かっこが先で 66（B）　 ポーリングは (*0x10000005 & 32) == 0 と C と同じ書き方に

ついでに必要になった「スタック評価」

かっこが入ると、(50 + 10) * (1 + 1) のように 「計算の途中結果」と「次の計算」がぶつかる式が書けるようになります。 そこで、左の結果をスタックに退避してから右を計算する、一般的な評価の仕方を入れました。 退避が要る式があるときだけ、コンパイラがスタックを用意します （要らないプログラムの出力は今までと1バイトも変わりません）。

実行結果 x（(50 + 10) * (1 + 1) = 120）　 A（100 / 4 + 40 = 65）　 A（(200 - 60) / (1 + 1) - 5 = 65）
優先順位は C と同じかっこ 掛け算・割り算スタック評価

ここでの学び： 優先順位は「式の読み方の標準仕様」。C と揃えることで、C のコードを そのままの読みで iwac に持って来られるようになりました。 構文解析は「段」を重ねる形になり、段を1つ足せば新しい演算子の置き場が増えます。

v8

if / else — 条件で道を選ぶ

目標：条件が成り立つかどうかで、実行する文を選べるようにすること。

if (x == 5) { putc(65); } else { putc(66); }
QEMU で実行すると… x が 5 なら A、そうでなければ B

流れは「分かれ道」

条件を計算する（結果は 1 か 0）
↓ 0 なら beq で else 側へ飛ぶ
成り立つときの文を実行
↓ 終わったら jal で else を飛び越える
else の文（あれば）を実行して、合流する

while で覚えた「飛び先を後から書き直す」やり方の、そのままの応用です。 else if の連なりも書けて、while の中でも関数の中でも使えます。

他の実行結果 ABA（while の中で i の値によって出す文字を変える）　 ab（関数の中で引数を見て分ける）
if / elseelse if 分かれ道は beq と jal

ここでの学び： 制御構造はどれも「条件つきのジャンプ」の組み合わせ。 while が「戻る分かれ道」なら、if は「行きの分かれ道」です。 道具が揃うと、新しい文は既存の部品の組み合わせで作れるようになります。

v9

配列 — データを並べて持つ

目標：値を1つずつでなく、並べて持てるようにすること。

char buf[8];
buf[0] = 72;  buf[1] = 105;  buf[2] = 0;
uart_puts(buf);
QEMU で実行すると…Hi ← 配列に組んだ文字列を、関数へ渡して表示！

配列って、そもそも何？ — 番号の付いた小箱の並び

char buf[8]; と書くと、メモリの中に1バイト入りの小箱が8個、横一列に並んだ棚が用意されます。 箱には 0 から始まる番号（添字）が付いていて、buf[1] は「buf の棚の1番の箱」を指す書き方です。 上のプログラムを実行したあとの棚は、こうなっています：

0番に 72（文字の H の番号）、1番に 105（i）、2番に 0（文字列の終わりの印）。 残りの箱はまだ空です。変数が「名前の付いた箱1つ」なのに対して、配列は「番号で選べる箱の集まり」。 番号が計算で決められるのが大事な点で、buf[i] や buf[i + 1] のように、 実行の途中で「何番の箱か」が変わるプログラムが書けます。

変数と配列の住みかの違い

変数レジスタの中（最大4個、速いけれど少しだけ）
配列メモリの中（バイナリの後ろの静かな領域。たくさん置ける）

要素の読み書きは「先頭の住所 ＋ 添字」の計算です（要素は1バイトなので、そのまま足せます）。 そして C と同じく、配列の名前そのものの値は「先頭の住所」。 だから文字列リテラルと同じように、関数へ渡したりポインタ変数に入れたりできます。

buf[1] = 105; は、機械語ではどうなる？

① 棚の先頭の住所を用意する：buf の棚がメモリのどこにあるかは、コンパイラが知っている
↓ 添字の 1 を足す（要素は1バイトなので、そのまま足せば1番の箱の住所になる）
② 1番の箱の住所が決まる：先頭 ＋ 1
↓ sb（store byte：1バイト書き込む命令）で、値 105 の下1バイトを置く
③ 書き込み完了：読むときは逆で、同じ住所計算をしてから lbu で1バイト読む

つまり配列の読み書きは、新しい命令ではなく「住所の足し算 ＋ いつもの lbu / sb」の組み合わせでした。 添字が i + 1 のような式でも、足す数が計算結果になるだけで、仕組みは同じです。

棚はバイナリのどこに置かれる？

コード機械語の命令
文字列"hello" など
配列の領域buf の棚はここ
スタック後ろの方から手前に伸びる

棚の住所は、文字列と同じく「コードの長さが決まってから」でないと分かりません。 そこで v3 で覚えた2パス生成（1回目で命令の数を数え、住所を確定して作り直す）が、ここでも働きます。 ちなみに char buf[8]; という宣言の文自体は、機械語を1つも出しません。 宣言は「棚の場所を予約する」約束であって、実行する仕事ではないからです。 スタックの置き場所を決めるときは、配列の領域とぶつからないよう、その分も避けて後ろにずらしています。

「自分で組み立てる文字列」ができるようになった

v3 の文字列リテラル "hello" は、書いた瞬間に中身が決まっていました。 配列の棚は実行の途中で中身を入れ替えられるので、プログラムが自分で文字列を組み立てて、 それを uart_puts(buf) のように関数へ渡せます。 関数から見れば、渡されるのは「住所」ひとつで、リテラルのときと何も変わりません。 これが「配列の名前の値 ＝ 先頭の住所」という決まりのうれしさです。

他の実行結果 CD（計算した添字 b[i + 1]）　 E（p = b; *p = 69; とポインタ経由で書く）
宣言 char buf[16];要素は1バイト 名前 = 先頭アドレス静的領域＋2パス生成

今の制限： 配列は最大8個・合計4096バイトまで。要素は1バイトだけ（int の配列のような 大きい要素はまだ無い）。棚はプログラム全体で共有の1つだけで、関数ごとの棚（局所配列）もまだありません。 宣言した直後の箱の中身は「何が入っているか分からない」ので、使う前に自分で入れるのが約束です （QEMU のメモリは偶然 0 で始まりますが、それに頼るのは本物の C でも禁じ手です）。

ここでの学び： 配列とは「住所の算数」でできたデータ構造です。文字列も、実は 終わりの印（0）付きの文字の配列でした。v3 の文字列と v9 の配列は、 同じ仕組みの表と裏だったのです。

ファイル入力 — iwac hello.c の形に

本物のコンパイラと同じ使い方になりました。ファイルに書けるようになると、 プログラムは行に分かれて読みやすくできて、コメントも残せます。 そこで字句の約束も少し育ちました：改行も空白として飛ばすことと、 // から行末までの行コメントです （割り算の / とは「2つ続いたらコメント」で見分けます。本物の C と同じ決め事）。

// examples/hello.c（リポジトリ同梱の例題）

iwac がホストに頼る関数は、出力の write に open / read / close が加わって4つだけ。 いずれも宣言は自分で書く流儀のままです。将来 KosabaOS の上で iwac を動かすときは、 この4つを OS のシステムコールに差し替えればよい、という置き方になっています。

v11

関係演算子 — 条件が自然に書ける

目標：while (i < 10) と、思った通りに書けること。

i = 0;
while (i < 3) { putc(65); i = i + 1; }  // AAA と出る

今までは「i != 3 の間」のように遠回りしていたループの条件が、そのまま書けるようになりました。 入れたのは < > <= >= の4つ。 優先順位の階段にも C と同じ段（足し算よりゆるく、== より固い場所）へきちんと差し込んだので、 1 < 2 == 1 は「(1<2) がまず成り立ち、それが 1 と等しい」と C と同じ読みになります。

機械語の側は「比べる命令」1つが中心

CPU には slt（左が右より小さければ 1、そうでなければ 0）という命令があります。 残りの3つは、その応用で作りました：

a > bslt で「b < a」を比べる（両辺の入替え）
a <= b「a > b」を作ってから、答えを反転（1 と XOR）
a >= b「a < b」を作ってから反転
< > <= >=slt 命令優先順位の段を追加

ここでの学び： 演算子を増やす作業は「段を1つ差し込む」ことに尽きました。 v7 で優先順位を段の形に組み替えておいたおかげで、新しい段は 隣の段の相手を変えるだけで入ります。設計の良し悪しは、 こういう「後から足すとき」に効いてきます。

v12

main — プログラムに「入口」ができた

目標：int main() { ... } と、普通の C と同じ姿で書けること。

int main() {
    uart_puts("Hello, World!\n");
}
examples/hello.c はこの形に移行済み。実行すると…Hello, World!

仕組みは驚くほど単純です。コンパイラが作るバイナリの先頭に 「main を呼び出す」命令を1つ置き、その直後に「止まる」命令を置く。 main が仕事を終えて戻ってくると、止まる命令に落ちて終わります。 main 自体は普通の関数とまったく同じ作りで、入口で戻り先を退避する作法もそのまま使いました。 新しい仕組みを足すのではなく、今ある「関数の呼び出し」を入口にも使う、という一手です。

約束も C に合わせました：main があるプログラムでは、外側に文を書く 「今までの形」との混ぜ書きはエラー。main が無ければ今までの形もそのまま動きます（二つの形の併存）。 戻り値の int は今までどおり読み捨てで、終了コードのような仕組みはまだありません。

int main()入口 = 関数の呼び出し1つ混ぜ書きは禁止

ここでの学び： 「main が特別」なのは名前だけで、中身は普通の関数でした。 特別扱いはコンパイラの入口の1命令と、parse のときの 「main という名前かどうか」の判定だけ。部品が揃ってくると、 新しい機能がこうして小さな組み合わせで実現できるようになります。

v13

#define — 定数に名前を付ける

目標：0x10000005 のような数字の羅列を、名前で書けること。

#define UART_LSR 0x10000005
#define THRE 32
void uart_putc(char c) {
    while ((*UART_LSR & THRE) == 0) { }
    *0x10000000 = c;
}

コンパイルの前に「前処理」という小さな係が走って、 UART_LSR という単語を 0x10000005 に書き換えてから、 本体のコンパイラへ渡します。書き換えは単語単位で、 文字列の中とコメントの中は書き換えません（本物の C と同じ約束）。

欲張らなかった点も大事です：やるのはこの単純な置き換えだけ。 #include（他のファイルの取り込み）や引数付きマクロは対象外のまま。 置き換えた結果をもう一度書き換えに行く「入れ子」もしない、と同じ名前の再定義はエラー、 という決め事にしました。なお iwac のコンパイラ自身のソースは、 この機能を使わず今までどおりプリプロセッサ無しで書いています （これは「コンパイルされる側のプログラム」のための機能、という整理です）。

#define 名前 置き換え単語単位文字列・コメントは対象外

ここでの学び： プリプロセッサは「コンパイラの前の、小さな別のプログラム」でした。 本体の3層（parse → gen → encode）の手前に「0層目」が1つ増えた形で、 本体には一切手を入れずに済んでいます。層を分けておく設計は、 こういう場所でも効きます。

v14

KosabaOS ターゲット — 合流の第一歩

目標：iwac の作ったプログラムが、自作 OS の上でユーザープログラムとして動くこと。

iwac --kosaba hello-kosaba.c > hello.elf

今までの出力は「OS の無いコンピュータ（QEMU）に直接置く生バイナリ」でした。 v14 では出力先の舞台がもう1つ増えました。言語は同じで、変わるのは舞台の約束だけです：

置き場所0x80200000（更地）→ 0x40000000（OS のユーザー領域）
形式生バイナリ → ELF（OS のローダが読む「配置の申告書」付き）
出力UART 直書き → putc システムコール（OS に頼む）
終わり方wfi で駐車 → exit システムコールで OS に戻る
KosabaOS のシェルで実行すると… kosaba> run uprog.elf
Hello, World! ← iwac 製プログラムが OS の上で動いた！

検証は OS の作業コピーの中で行いました（OS 本体のリポジトリは無変更）。 iwac 製の ELF を OS のファイルシステムに載せ、カーネルの起動キーと シェルの run の両方で実行でき、終わると プロンプトやカーネルにきちんと戻ることまで確認しています。

--kosabaELF 出力 ecall 命令OS と合流

ここでの学び： 「ターゲット」という考え方です。コンパイラの仕事の大部分 （言語の意味を命令に変えること）は舞台に依らず共通で、 舞台ごとの違いは「置き場所・形式・出力と終わりの作法」の 薄い層に閉じ込められました。住所を auipc 相対で作るという v3 の決断が、ここで効いています。

v15

iwac 本体が OS の上で動く — ゴールの形が成立

目標：KosabaOS のシェルからコンパイラを実行して Hello World をコンパイルし、実行すること。

OS のシェルで… kosaba> run iwac.elf ← コンパイラ自身が OS の上で動く
kosaba> run hello.elf
Hello, World! ← OS の中でコンパイルされたプログラム

面白いのは、iwac のソース (iwac.c) には1文字も手を入れていないことです。 iwac が外の世界に頼るのは「ファイルを読み書きする4つの関数」だけ、という 設計だったので、移植の仕事はその4つの「相手」を差し替えることに収まりました：

入口 (crt)OS には引数の仕組みがまだ無いので、決め打ちの argv「iwac --kosaba hello.c」を合成して main を呼ぶ
読み書き (shim)open/read/close は OS のシステムコールへ。出力は create/write で hello.elf というファイルへ

途中、ひとつ発見がありました。OS ではプログラムの置き場所が 「読み+実行のみ（書けない）」で、書き込みできるメモリはスタックだけでした。 手書きの小さなプログラムはそれで済みますが、大きな作業机（静的変数）が 要るコンパイラは置けません。相談を受けた OS 側が「データ専用の 書き込みできる領域」を新設し、iwac 側も配置を合わせたことで、 今は OS 本線でそのまま動きます（プログラムの領域は コード／データ／スタックの3つに分かれました）。

移植 = 差し替えiwac.c 無変更 OS 上でコンパイル発見: 書けない机

ここでの学び： 「外への依存を小さな境目に閉じ込める」設計の値打ちです。ホストの機能への 依存を4関数だけに絞ってあったおかげで、プログラム全体の移植が 「境目の向こう側を作り直す」作業だけで済みました。境目は、 最初に設計するときにこそ効きます。

v16

字句の完成 — セルフホストへの階段の1段目

目標：「iwac が iwac 自身をコンパイルできる」への第一歩として、本物の C ソースの字句を全部読めるようにすること。

新しい目標はセルフホスト（自分自身をコンパイルできるコンパイラ）です。 iwac 本体のソース（約116KB）を実測して「何が足りないか」を洗い出し、 v16 から v26 までの階段を計画しました。構造体や switch のように iwac 本体が使っていないものは、階段に入れていません。

v17

複数ファイル入力 — 部品と本体を分けて渡せる

目標：プログラムを複数のファイルに分けて渡せるようにすること。

「そろそろファイルを複数にしても何とかなるように」という提案で、 階段に差し込んだ段です（以降の段は繰り下げ）。 iwac a.c b.c のように並べると、順につないで （境目には改行を1つ挟む）1つのソースとして読みます。 引数が1つだけのときの規則と出力は、従来とバイト一致です。

$ iwac lib.c main.c > prog.bin   ← 部品のファイル＋本体のファイル
$ iwac kosaba_rt.c iwac.c          ← 将来のセルフコンパイルの形
連結して読む境目に改行 #define はファイル間でも有効開けない名前はエラーに表示

ここでの学び： 入口の道具立ては、言語の機能と同じくらい使い勝手を決めます。 セルフコンパイルの最終段では「OS 用ランタイム＋iwac 本体」の 連結が必要で、cat の力技ではなくコンパイラ自身の機能として 持っておく方が筋が良い、という段です。

条件付きコンパイル — #ifdef で枝を選ぶ

目標：「#ifdef も欲しい」という希望に応え、前処理で範囲を選べるようにすること。

#ifdef / #ifndef / #else / #endif が 使えるようになりました（入れ子は32段まで）。無効になった範囲の行は 捨てられ、その中の #define も登録されません。 コンパイラが用意する定義済みマクロ __IWAC__（常に）と __KOSABA__（--kosaba のとき）があり、 1つのソースでベア版と OS 版を切り替えられます。 併せて、コメントの中の行頭の # を指令と間違えなくなりました。

#ifdef __KOSABA__
  … OS 用の書き方 …
#else
  … ベアメタル用の書き方 …
#endif
#ifdef / #ifndef / #else / #endif入れ子32段 __KOSABA__ で判別#if（式）は対象外

ここでの学び： 条件付きコンパイルは「前処理は単なる文字の置き換え」から 「ソースの形を決める仕組み」への一歩です。無効な範囲でも 条件の指令だけは数え続ける、という決まりが入れ子の正しさを 保ちます。

演算子の完成 — C の顔ぶれが揃う

目標：セルフホストへの階段の4段目。iwac.c が使う演算子を全部使えるようにすること。

<< >>、| ^、%、 単項の - と !、&& ||、 前置/後置の ++ -- が入りました。 優先順位の段も C の全順序に揃え直しました （|| → && → | → ^ → & → ==/!= → 関係 → シフト → 加減 → 乗除・剰余 → 単項 → 後置 → 材料）。 && と || は短絡評価です： 左が決め手になれば、右は評価されません （p && *p のような「まず確かめてから触る」書き方が安全に動きます）。 >> は算術シフトで、負の数をずらしても符号が保たれます。 *p++ は *(p++) と読まれ、文字列を歩く書き方がそのまま通ります。

s = "AB";
putc(*s++);              // *(s++) — 読んでから進む
i = 0;
while (i < 3 && i != 1) {   // 短絡評価と後置 ++
  putc(65 + i);
  i++;
}
x = -1;                  // 単項マイナス
putc(64 + (100 % 7));    // 剰余
<< >> | ^ %- !（単項） && || は短絡評価++ --（文でも式でも） 優先順位は C の全順序

ここでの学び： 演算子を足す作業は、parse の段を増やすことと、生成の道具を増やすことの 2つに分かれます。&& だけは例外で、二項演算の形（両辺を計算してから 組み合わせる）では作れず、分岐で右側を飛ばす「制御の仕組み」で作りました。 式の中に制御が入る、というのは面白い境界です。
